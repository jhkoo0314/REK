# 부동산 매물관리 웹서비스 — Supabase 데이터 모델 v1.0

> 작성일: 2026-08-14  
> 상태: 웹서비스 1차 데이터 설계 기준  
> 기준 문서: `web_service_prd_v1.md`, `development_environment_plan.md`, `user_access_policy_v1.md`

---

## 1. 문서 목적

이 문서는 웹서비스가 Supabase Postgres에 어떤 데이터를 어떤 관계로 저장할지 정의한다.

목표는 “향후 확장 가능한 복잡한 ERP”가 아니라 다음 세 가지다.

1. 현재 Streamlit의 실무 데이터 구조를 안전하게 옮긴다.
2. 같은 호실의 조건 변경, 상담, 계약, 광고를 서로 끊기지 않게 연결한다.
3. 운영 전 RLS를 적용할 수 있도록 모든 업무 데이터에 사무실 조직 소속을 남긴다.

테이블·열·상태값을 새로 추가하거나 바꾸기 전에는 이 문서를 먼저 수정한다.

## 2. 설계 원칙

### 2.1 업무 중심 원칙

- 매물 정보의 중심 구조는 **건물 → 호실 → 매물 회차**다.
- 계약·상담·광고는 건물이나 호실이 아닌 해당 **매물 회차**에 연결한다.
- 일반적인 가격·상태·입주일 변경은 같은 최신 매물 회차를 수정한다.
- 과거 회차, 종료 이력, 계약·상담 이력은 임의로 덮어쓰지 않는다.
- 검색·필터·오늘 할 일에 필요한 값은 메모가 아닌 별도 열로 저장한다.

### 2.2 웹 운영 원칙

- 모든 업무 테이블에는 `organization_id`를 둔다.
- 모든 주요 데이터에는 생성·수정 시각과 작성·수정 사용자를 남긴다.
- Clerk는 로그인과 세션을 담당하고, Supabase에는 업무 권한에 필요한 사용자 연결 정보만 저장한다.
- 개발 단계에는 RLS를 임시 비활성화할 수 있으나, 스키마에는 운영 RLS 적용을 위한 열을 처음부터 포함한다.
- 실제 파일은 데이터베이스에 저장하지 않고, 향후 Supabase Storage에 저장하며 DB에는 경로·메타 정보만 기록한다.

### 2.3 이번에 하지 않는 설계

- 상태값마다 별도 테이블을 만드는 과도한 정규화
- 고객 단위의 복잡한 CRM 통합 모델
- 계약금·잔금의 입금 내역을 여러 건 누적하는 결제 테이블
- 광고 비용·클릭·노출 성과 테이블
- 계약서·신분증 파일 테이블
- 사용자별 세밀한 접근권한 테이블

1차에서는 상태값을 TypeScript 상수와 DB `check` 제약으로 관리한다. 실제 운영 중 상태값을 자주 바꿔야 할 근거가 생길 때만 별도 코드 테이블을 검토한다.

## 4. 공통 열 규칙

### 4.1 기본 식별 열

| 열 | 형식 | 규칙 |
|---|---|---|
| `id` | UUID | 기본키. DB에서 자동 생성 |
| `organization_id` | UUID | `organizations.id` 참조. 모든 업무 테이블에 필수 |
| `created_at` | timestamptz | 최초 저장 시 DB 자동 기록 |
| `updated_at` | timestamptz | 수정 시 DB 자동 갱신 |
| `created_by_member_id` | UUID | 최초 저장한 활성 조직 사용자 |
| `updated_by_member_id` | UUID | 마지막 수정한 활성 조직 사용자 |

`created_at`, `updated_at`은 브라우저 시간이 아니라 DB 시간을 기준으로 기록한다.

### 4.2 금액·날짜·빈값 규칙

- 금액은 모두 `integer`의 만원 단위로 저장한다. 예: 500만원은 `500`.
- 알 수 없는 금액은 `0`이 아니라 `NULL`로 둔다.
- 날짜는 날짜만 의미할 경우 `date`, 정확한 시간 기록은 `timestamptz`를 사용한다.
- 메모는 검색·필터의 대체 수단이 아니다. 상태·날짜·가격은 별도 열로 둔다.
- 전화번호는 화면에서 하이픈 형식으로 정리해 텍스트로 저장한다. 국제 번호 처리나 전화번호 인증은 1차 범위가 아니다.

### 4.3 삭제 규칙

| 대상 | 기본 처리 |
|---|---|
| 건물 | 일반 화면에서 삭제하지 않음. 필요 시 비활성화 |
| 호실 | 잘못 만든 경우에만 명시적 확인 뒤 완전 삭제 가능 |
| 매물 회차 | 정보 오류 종료를 우선, 명시적 확인 시 완전 삭제 가능 |
| 계약·상담·광고 | 각각의 관리 화면에서 명시적 확인 시 삭제 가능 |
| 조직 사용자 | 데이터 삭제가 아닌 비활성화 |

완전 삭제 기능을 구현할 경우, 연결된 기록이 함께 삭제되는지 서비스 화면에서 먼저 알려야 한다.

## 5. 조직과 사용자 테이블

### 5.1 `organizations`

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id` | uuid | 예 | 조직 기본키 |
| `name` | text | 예 | 예: 배방우리부동산 |
| `status` | text | 예 | `active` / `inactive` |
| `created_at` | timestamptz | 예 | 생성 시각 |
| `updated_at` | timestamptz | 예 | 수정 시각 |

1차 운영은 조직 1개만 사용한다. 그러나 향후 본인 사무소를 개업하거나 다른 사무실 데이터를 분리해야 할 때 기존 업무 테이블을 다시 고치지 않도록 처음부터 둔다.

### 5.2 `organization_members`

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id` | uuid | 예 | 내부 사용자 기본키 |
| `organization_id` | uuid | 예 | 소속 조직 |
| `clerk_user_id` | text | 예 | Clerk 사용자 ID. 전역 고유 |
| `display_name` | text | 아니오 | 화면 표시 이름 |
| `role` | text | 예 | `admin` / `staff` |
| `status` | text | 예 | `active` / `inactive` |
| `created_at`, `updated_at` | timestamptz | 예 | 자동 기록 |

제약:

- `clerk_user_id`는 전체에서 중복될 수 없다.
- 같은 조직 안에서 동일 Clerk 사용자를 중복 연결할 수 없다.
- 조직 사용자 연결이 없는 Clerk 계정은 운영 데이터에 접근할 수 없어야 한다.

### 6.1 `buildings`

| 열 | 형식 | 필수 | 설명 |

| `lot_number` | text | 예 | 번지 번호. 예: 1026 또는 1026-1 |
| `lot_address` | text | 예 | 검색용 합친 값. 예: 북수리 1026 |
| `building_alias_note` | text | 아니오 | 다른 표기·별칭 |
| `has_elevator` | text | 아니오 | 있음 / 없음 / 확인 필요 |
| `parking_status` | text | 아니오 | 가능 / 제한적 / 불가 / 확인 필요 |
| `has_cctv` | text | 아니오 | 있음 / 없음 / 확인 필요 |
| `pet_policy` | text | 아니오 | 가능 / 불가 / 협의 / 확인 필요 |
| `move_in_registration_policy` | text | 아니오 | 가능 / 불가 / 협의 / 확인 필요 |
| `short_term_policy` | text | 아니오 | 가능 / 불가 / 협의 / 확인 필요 |
| `common_fee_note` | text | 아니오 | 공통 관리비 참고 |
| `building_highlights` | text | 아니오 | 외부 문구로 활용 가능한 확인된 장점 |
| `internal_note` | text | 아니오 | 내부 메모 |
| `common_entrance_password` | text | 아니오 | 민감 내부정보 |
| `info_status` | text | 예 | 기본등록 / 일부확인 / 확인완료 / 재확인 필요 |
| `last_checked_date` | date | 아니오 | 실제 확인일 |
| `next_check_date` | date | 아니오 | 건물 정보 확인용. 1차 오늘 할 일에는 미포함 |

```text
organization_id + building_name(정규화) + lot_address
```

건물명이 비어 있는 경우에는 화면에서 `건물명 미입력`으로 정규화해 같은 지번의 중복 생성을 막는다. 건물명만 같고 지번이 다르면 자동으로 합치지 않는다.

### 6.2 `units`

호실은 같은 건물에서 대체로 유지되는 고정정보를 저장한다.

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id`, `organization_id` | uuid | 예 | 식별·조직 연결 |
| `building_id` | uuid | 예 | `buildings.id` 참조 |
| `unit_number` | text | 예 | 화면 저장 시 `호` 제거. 예: 302 |
| `floor_number` | integer | 아니오 | 층 |
| `room_type` | text | 아니오 | 원룸 / 투룸 / 투베이 / 쓰리룸 / 쓰리베이 / 주인세대 / 기타 / 확인 필요 |
| `is_separated` | text | 아니오 | 예 / 아니오 / 확인 필요 |
| `direction` | text | 아니오 | 동·서·남·북·방위·확인 필요 |
| `area_status` | text | 아니오 | 면적 확인 / 면적 미확인 |
| `exclusive_area_m2` | numeric | 아니오 | 면적 확인 시만 입력 |
| `has_balcony` | text | 아니오 | 있음 / 없음 / 확인 필요 |
| `has_built_in_closet` | text | 아니오 | 있음 / 없음 / 확인 필요 |
| `has_double_window` | text | 아니오 | 있음 / 없음 / 확인 필요 |
| `storage_status` | text | 아니오 | 좋음 / 보통 / 부족 / 확인 필요 |
| `system_aircon_count` | integer | 아니오 | 대수 |
| `unit_options` | jsonb | 아니오 | 선택 옵션 배열 |
| `other_option_note` | text | 아니오 | 목록 외 옵션 |
| `unit_highlights` | text | 아니오 | 구조상 장점 |
| `unit_cautions` | text | 아니오 | 내부 참고용 유의점 |
| `access_method` | text | 아니오 | 비밀번호 / 열쇠 / 세입자 협의 / 관리인 문의 / 확인 필요 |
| `unit_access_password` | text | 아니오 | 민감 내부정보 |
| `internal_note` | text | 아니오 | 내부 메모 |
| `is_active` | boolean | 예 | 기본 `true` |
| 감사 열 | - | 예 | 공통 열 규칙 적용 |

고유 기준:

```text
organization_id + building_id + normalized_unit_number
```

`302`와 `302호`는 앱 서버에서 같은 정규화 값으로 변환한 뒤 저장한다. `101-1`, `A동 201`과 같은 예외 표기는 원문을 유지하되 동일 표기의 중복만 막는다.

`unit_options`는 1차에만 JSON 배열로 저장한다. 예: `['냉장고','세탁기','에어컨','TV']`. 옵션별 재고나 고급 통계가 실제 필요해질 때만 별도 연결 테이블을 검토한다.

## 7. 매물 회차 테이블

### 7.1 `listings`

매물 회차는 이번 매물의 가격·상태·입주 가능 조건과 확인 업무를 저장한다.

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id`, `organization_id` | uuid | 예 | 식별·조직 연결 |
| `unit_id` | uuid | 예 | `units.id` 참조 |
| `listing_number` | bigint | 예 | 조직별 표시 번호. 화면에서 `M-000001` 형식 |
| `received_date` | date | 예 | 접수일. 기본 저장일 |
| `listing_status` | text | 예 | 아래 상태값 사용 |
| `listing_holder` | text | 예 | 크린·삼성·한빛·국제·개인매물 또는 직접입력 |
| `deposit_manwon` | integer | 아니오 | 보증금(만원) |
| `monthly_rent_manwon` | integer | 아니오 | 월세(만원) |
| `management_fee_manwon` | integer | 아니오 | 관리비(만원) |
| `management_fee_note` | text | 아니오 | 포함 항목 등 |
| `availability_type` | text | 예 | 즉시입주 / 날짜 지정 / 퇴실 후 협의 / 확인 필요 |
| `available_from_date` | date | 조건부 | 날짜 지정일 때 입력 |
| `move_out_due_date` | date | 아니오 | 퇴실 예정일 |
| `lease_term_note` | text | 아니오 | 일반 계약 가능 기간 |
| `short_term_note` | text | 아니오 | 이번 매물의 단기 조건 |
| `cleaning_status` | text | 아니오 | 문제 없음 / 완료 / 필요 / 진행 중 / 확인 필요 |
| `wallpaper_status` | text | 아니오 | 문제 없음 / 완료 / 필요 / 진행 중 / 확인 필요 |
| `repair_status` | text | 아니오 | 문제 없음 / 완료 / 필요 / 진행 중 / 확인 필요 |
| `has_listing_photos` | text | 아니오 | 있음 / 없음 / 확인 필요 |
| `option_change_note` | text | 아니오 | 이번 회차에만 다른 옵션 |
| `listing_note` | text | 아니오 | 이번 매물 메모 |
| `landlord_contact` | text | 아니오 | 민감 내부정보 |
| `tenant_contact` | text | 아니오 | 민감 내부정보 |
| `last_checked_date` | date | 아니오 | 이번 조건 확인일 |
| `next_check_date` | date | 아니오 | 재확인 예정일 |
| `verification_note` | text | 아니오 | 확인할 내용 |
| `closed_date` | date | 아니오 | 종료일 |
| `close_reason` | text | 아니오 | 계약 완료 / 타 부동산 계약 / 임대인 보류 / 정보 오류 / 광고 중단 / 기타 |

| 감사 열 | - | 예 | 공통 열 규칙 적용 |

매물 상태값:

```text
확인 필요 / 퇴실 예정 / 공실 / 광고 가능 / 계약 진행 중 / 계약 완료 / 보류 / 종료
```

### 7.2 매물 회차의 이력 규칙

| 상황 | 처리 |
|---|---|
| 가격·상태·입주일·사진·현장 상태 변경 | 동일 `listings` 행 수정 |
| 계약·상담·광고가 이미 연결된 매물의 조건 변경 | 동일 행 수정, 연결 기록 유지 |
| 현재 매물을 종료 | `is_current=false`, 종료일·사유 기록 |
| 새 운영 회차를 명시적으로 만들 필요가 있음 | 기존 회차 종료 뒤 새 `listings` 행 생성 |
| 오류 매물 | 정보 오류 종료 또는 명시적 완전 삭제 |

실무의 기본 흐름은 “기존 호실의 최신 매물 정보 수정”이다. 새 매물 회차 생성은 자동으로 하지 않으며, 화면에서 명확한 목적을 선택한 경우에만 가능하게 한다.

권장 제약:

```text
한 호실에는 is_current = true 인 매물 회차가 최대 1개
```

이는 Postgres의 부분 고유 인덱스로 구현한다.

| `close_reason` | text | 아니오 | 종료·계약 완료 시 이유 |

| `preferred_area` | text | 아니오 | 희망 지역 |

계약 상태값:


- 계약금·가계약금은 요약 목적이며, 여러 번의 실제 입금 내역을 관리하지 않는다.

## 10. 광고·오늘 할 일·사진 테이블

### 10.1 `listing_advertisements`

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id`, `organization_id` | uuid | 예 | 식별·조직 연결 |
| `listing_id` | uuid | 예 | `listings.id` 참조 |
| `channel_name` | text | 예 | 당근 / 직방 / 네이버 또는 직접 입력 |
| `ad_status` | text | 예 | 미등록 / 준비 중 / 등록 완료 / 중단 / 확인 필요 |
| `last_checked_date` | date | 아니오 | 마지막 광고 확인일 |
| `memo` | text | 아니오 | 내부 참고 |
| 감사 열 | - | 예 | 공통 열 규칙 적용 |

고유 기준:

```text
organization_id + listing_id + channel_name(정규화)
```

같은 매물 회차에 같은 채널을 중복 등록하지 않는다. 광고는 현재 상태만 관리하며, 성과·비용·외부 링크·자동 업로드는 1차 범위가 아니다.

### 10.2 `task_completions`

오늘 할 일은 원본 데이터에서 매번 계산한다. 이 테이블은 계산된 업무의 **완료 체크만** 저장한다.

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id`, `organization_id` | uuid | 예 | 식별·조직 연결 |
| `task_key` | text | 예 | 원본 종류·원본 ID·업무 종류를 조합한 안정 키 |
| `due_date` | date | 예 | 해당 업무의 기준일 |
| `is_completed` | boolean | 예 | 기본 `true` 또는 체크 상태 |
| `completed_at` | timestamptz | 아니오 | 완료한 시각 |
| `completed_by_member_id` | uuid | 아니오 | 처리 사용자 |
| `updated_at` | timestamptz | 예 | 체크·해제 시각 |

고유 기준:

```text
organization_id + task_key + due_date
```

예시 `task_key`:

```text
listing:{listing_id}:recheck
listing:{listing_id}:move_out_d7
contract:{contract_id}:balance_due_d1
consultation:{consultation_id}:next_contact
```

원본 날짜가 바뀌면 다른 `due_date` 조합이 되므로, 새 업무는 자동으로 미완료로 보인다. 완료 체크는 계약·상담·매물의 원본 상태를 자동으로 바꾸지 않는다.

### 10.3 `listing_photos` — 사진 기능 시작 시 생성

사진 업로드 기능이 실제로 시작될 때만 테이블과 Storage 버킷을 만든다.

| 열 | 형식 | 필수 | 설명 |
|---|---|:---:|---|
| `id`, `organization_id` | uuid | 예 | 식별·조직 연결 |
| `listing_id` | uuid | 예 | `listings.id` 참조 |
| `storage_path` | text | 예 | Supabase Storage 경로 |
| `is_primary` | boolean | 예 | 대표 사진 여부 |
| `sort_order` | integer | 예 | 사진 순서 |
| `caption` | text | 아니오 | 내부 식별용 짧은 설명 |
| 감사 열 | - | 예 | 공통 열 규칙 적용 |

사진 파일은 DB에 직접 저장하지 않는다. Storage 경로는 `organization_id/listing_id/파일명` 형태로 관리하며, 운영 단계에서는 Storage에도 조직 범위 접근 정책을 적용한다.

## 11. 관계·무결성 규칙

### 11.1 관계 규칙

| 부모 | 자식 | 규칙 |
|---|---|---|
| 조직 | 조직 사용자 | 조직 삭제는 일반 기능으로 제공하지 않음 |
| 조직 | 건물·호실·매물 등 | 모든 업무 데이터는 같은 조직에 속해야 함 |
| 건물 | 호실 | 건물을 삭제하지 않고 비활성화 우선 |
| 호실 | 매물 회차 | 호실 삭제 시 연결 매물·계약·상담·광고 영향을 안내 |
| 매물 회차 | 상담 | 상담은 일반 상담이면 매물 연결이 비어 있을 수 있음 |
| 매물 회차 | 계약 | 계약은 항상 매물 회차 연결 필수 |
| 매물 회차 | 광고 | 광고는 항상 매물 회차 연결 필수 |

### 11.2 날짜·금액 검사

| 검사 | 기준 |
|---|---|
| 입주 가능 유형이 날짜 지정 | `available_from_date` 필수 |
| 가격 | 음수 금지, 미확인은 `NULL` |
| 임대차 종료일 | 시작일보다 빠를 수 없음 |
| 정식 계약일·추가 계약금·잔금 예정일 | 계약 진행 시작일보다 빠를 수 없음 |
| 가계약금 수령액 | 계약금 전체보다 클 수 없음 |
| 가격 범위 필터 | 최대값이 최소값보다 작으면 조회하지 않음 |

이 검사는 DB 제약으로 가능한 것은 DB에, 사용자 이해가 필요한 오류 메시지는 TypeScript 서버 검증에 둔다.

### 11.3 표시 번호 규칙

| 대상 | 사용자 표시 | DB 저장 |
|---|---|---|
| 매물 | `M-000001` | 조직별 `listing_number` 정수 |
| 계약 | `C-000001` | 조직별 `contract_number` 정수 |
| 상담 | `S-000001` | 조직별 `consultation_number` 정수 |

번호는 수정해도 바뀌지 않으며, 완전 삭제된 번호는 재사용하지 않는다. 조직별 다음 번호 발급 방식은 migration과 서버 저장 로직에서 원자적으로 처리한다.

## 13. Migration·Seed 데이터 운영 규칙

### 13.1 Migration

- 모든 테이블·열·제약·인덱스 변경은 SQL migration 파일로 남긴다.
- Supabase 대시보드에서 수동으로 실행한 SQL도 반드시 migration 파일에 기록한다.
- migration 파일 이름에는 순서와 목적을 쓴다.

예시:

```text
0001_create_organizations_and_members.sql
0002_create_buildings_units_listings.sql
0003_create_consultations_contracts_ads.sql
0004_create_task_completions_and_indexes.sql
```

### 13.2 Seed 데이터

개발 DB에는 다시 만들 수 있는 가상 seed 데이터만 사용한다.

| 데이터 | 예시 |
|---|---|
| 조직 | 테스트부동산 |
| 사용자 | 개발 관리자, 개발 직원 |
| 건물 | 테스트빌 A, 테스트동 100-1 |
| 호실 | 302, 투룸 |
| 매물 | 500 / 45, 공실 |
| 연락처 | `010-0000-0000` |

실제 사무실 매물·실제 연락처·실제 비밀번호는 seed 파일이나 개발 DB에 넣지 않는다.

## 14. RLS 전환을 위한 준비 사항

개발 중 RLS가 꺼져 있어도, 아래 열과 관계는 운영 전환 때 바꾸지 않고 그대로 쓴다.

- 모든 업무 테이블의 `organization_id`
- `organization_members.clerk_user_id`
- `organization_members.status`
- `organization_members.role`
- 생성·수정 사용자 기록

운영 RLS의 기본 의미는 다음과 같다.

```text
로그인한 Clerk 사용자
→ 활성 organization_members 레코드 확인
→ 해당 organization_id 확인
→ 같은 organization_id의 행만 조회·등록·수정·삭제
```

RLS SQL 정책, Clerk JWT 연동 방식, 서버 측 사용자 검증은 `supabase_security_transition_plan.md`에서 확정한다.

|---:|---|---|
| 1 | `organizations`, `organization_members` | Clerk 사용자와 업무 데이터의 기준점 |
| 2 | `buildings`, `units`, `listings` | 매물 등록·수정의 핵심 |
| 3 | 고유 제약·현재 매물 부분 인덱스 | 중복과 데이터 오류 방지 |
| 4 | `consultations`, `consultation_followups` | 상담 업무와 다음 연락 |
| 5 | `contracts` | 계약과 오늘 할 일 일정 |
| 6 | `listing_advertisements`, `task_completions` | 광고 현황과 업무 완료 체크 |
| 7 | `listing_photos` | 실제 사진 업로드가 필요해진 시점 |
| 8 | 운영 RLS 정책 | 개발 기능 안정화와 운영 전환 시점 |

## 16. 수용 기준

### 개발 데이터 모델 수용 기준

- [ ] 가상 조직·개발 사용자·가상 건물·호실·매물을 저장할 수 있다.
- [ ] 같은 건물의 `302`와 `302호` 중복을 막는다.
- [ ] 호실당 현재 매물 회차가 두 개 생기지 않는다.
- [ ] 최신 매물 정보 수정 뒤 상담·계약·광고 연결이 유지된다.
- [ ] 일반 상담은 매물 없이 저장하고 나중에 연결할 수 있다.
- [ ] 계약은 매물 회차 없이 저장할 수 없다.
- [ ] 같은 매물 회차의 같은 광고 채널을 중복 등록할 수 없다.
- [ ] 오늘 할 일 완료 체크가 원본 일정·상태를 바꾸지 않는다.
- [ ] 데이터 초기화 후 seed 데이터로 개발 환경을 다시 만들 수 있다.

### 운영 전환 데이터 모델 수용 기준

- [ ] 모든 업무 테이블에 `organization_id`가 있다.
- [ ] Clerk 사용자 ID와 활성 조직 사용자를 연결할 수 있다.
- [ ] 생성·수정 사용자와 시간이 핵심 업무 데이터에 기록된다.
- [ ] RLS 적용 뒤 다른 조직 행을 읽거나 바꿀 수 없다.
- [ ] 민감한 열은 기본 목록용 조회에서 제외된다.
- [ ] 운영 DB migration이 빈 운영 프로젝트에서 순서대로 정상 적용된다.

## 18. 확정 결론

> 이 서비스의 데이터 중심은 매물 회차다. 건물과 호실은 반복 입력을 줄이는 기반이고, 상담·계약·광고·오늘 할 일은 모두 매물 회차에서 업무가 이어지도록 설계한다. 조직·사용자 열은 지금의 1개 사무실 운영을 복잡하게 만들기 위한 것이 아니라, 실제 웹 운영에서 데이터가 섞이지 않게 하는 최소 안전장치다.
