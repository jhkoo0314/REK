# 부동산 매물관리 웹서비스 — 개발 환경 운영 계획서 v1.0

> 작성일: 2026-08-14  
> 상태: 웹서비스 개발 시작 전 확정안  
> 기준 PRD: `web_service_prd_v1.md`

---

## 1. 문서 목적

이 문서는 개발 중인 화면·코드·테스트 데이터가 실제 업무 데이터와 섞이지 않도록, Clerk·Supabase·Vercel·GitHub의 환경을 나누는 기준을 정의한다.

가장 중요한 원칙은 하나다.

> **개발은 빠르게 진행하되, 개발 중 발생하는 실수 때문에 실제 매물·연락처·비밀번호·계약 기록이 영향을 받지 않게 한다.**

이 문서는 다음 상황에서 사용한다.

- 처음 Next.js 프로젝트를 만들 때
- Clerk와 Supabase 계정을 연결할 때
- Vercel Preview 배포를 만들 때
- RLS를 켜고 실제 운영 데이터로 전환할 때
- 개발 담당자가 바뀌거나 운영 환경을 인계할 때

---

## 2. 환경을 나누는 이유

웹서비스는 한 번의 배포 실수, 잘못된 SQL 실행, RLS 정책 오류만으로도 데이터가 바뀌거나 노출될 수 있다. 따라서 아래 세 가지 환경을 구분한다.

| 환경 | 목적 | 실제 업무 데이터 | 외부 접근 |
|---|---|---:|---|
| 로컬 개발(Local) | 코드를 만들고 빠르게 확인 | 금지 | 개발 PC만 |
| 미리보기(Preview) | 실제 브라우저·모바일에서 변경사항 검토 | 금지 | 초대된 검토자만 |
| 운영(Production) | 실제 사무실 업무 | 허용 | 승인된 실제 사용자만 |

개발과 운영의 데이터베이스, Clerk 키, Vercel 환경변수는 반드시 분리한다. 이름만 다르게 한 같은 프로젝트를 쓰면 안 된다.

## 3. 확정 기술 구성과 역할

| 구성 | 사용 서비스 | 역할 |
|---|---|---|
| 웹 애플리케이션 | Next.js 16 + React + TypeScript 5.x | 화면, 서버 로직, 입력 검증, Excel 생성 |
| UI | Tailwind CSS + shadcn/ui | 표·폼·다이얼로그·필터 중심 화면 |
| 인증 | Clerk | 로그인, 세션, 사용자 관리 |
| 업무 데이터 | Supabase Postgres | 매물, 상담, 계약, 광고, 오늘 할 일의 원본 데이터 |
| 사진 파일 | Supabase Storage | 향후 매물 사진 저장 |
| 배포 | Vercel | Preview와 운영 배포 |
| 소스 관리 | GitHub | 코드 이력, Vercel 자동 배포 기준 |

파이썬 서버는 1차 웹서비스에 두지 않는다. 현재 Streamlit에서 파이썬이 담당하던 일상 계산은 TypeScript 서버 로직으로 옮긴다.

## 4. 계정과 소유권 기준

서비스 계정은 개인 계정에만 묶지 않는다. 향후 담당자 변경과 개업을 고려해, 가능한 한 사무실 또는 본인이 지속 관리할 이메일 주소를 소유자로 둔다.

| 서비스 | 권장 소유자 | 관리자 추가 | 주의사항 |
|---|---|---|---|
| GitHub | 재현님 관리 계정 | 필요 시 공동 관리자 | 코드 저장소를 개인 공개 저장소로 만들지 않음 |
| Vercel | 재현님 관리 계정 또는 팀 | 운영 담당자 | 운영 프로젝트의 배포 권한은 최소화 |
| Clerk | 재현님 관리 계정 또는 팀 | 운영 담당자 | 개발 인스턴스와 운영 인스턴스를 구분 |
| Supabase | 재현님 관리 계정 또는 팀 | 운영 담당자 | 개발·운영 프로젝트를 별도로 생성 |

계정 비밀번호나 API 키를 문서, 카카오톡, 소스코드, Excel에 적지 않는다.

## 5. 환경별 구성 기준

### 5.1 로컬 개발 환경

| 항목 | 기준 |
|---|---|
| 코드 실행 | 개발 PC에서 `npm run dev`로 실행 |
| Clerk | Development 인스턴스의 테스트 키 사용 |
| Supabase | 개발 전용 프로젝트 사용 |
| RLS | 초기 CRUD 화면 구축 기간에는 임시 비활성화 가능 |
| 데이터 | 완전히 가상인 테스트 데이터만 입력 |
| 사진 | 실제 호실 사진·계약서·신분증 업로드 금지 |
| 목적 | 화면·폼·저장 규칙·조회·필터를 빠르게 완성 |

로컬 개발 DB에는 아래처럼 명백히 가상인 데이터를 사용한다.

```text
건물명: 테스트빌 A
주소: 테스트동 100-1
호수: 302
연락처: 010-0000-0000
비밀번호: 입력하지 않음
```

실제 북수리·장재리 매물, 실제 계약자, 실제 임대인 정보는 개발 DB에 입력하지 않는다.

### 5.2 Vercel Preview 환경

Preview는 GitHub에 변경사항을 올렸을 때 생성되는 검토용 웹주소다. 화면을 휴대폰·다른 PC에서 확인하고, 저장·조회 흐름을 검토하는 용도로 쓴다.

| 항목 | 기준 |
|---|---|
| 배포 기준 | `main` 이외의 작업 브랜치 또는 Pull Request |
| Clerk | Development 인스턴스 사용 |
| Supabase | 개발 전용 프로젝트 사용 |
| RLS | 개발 중 임시 비활성화 가능하나, 실제 데이터는 금지 |
| 접근 | Vercel Preview 접근 제한 또는 공유 대상 제한 |
| 목적 | 사용자 경험·반응형·브라우저 동작·저장 흐름 확인 |

Preview 주소는 검토가 필요한 사람에게만 공유한다. 검색엔진 등록, 공개 링크 홍보, 실제 고객 사용은 금지한다.

### 5.3 운영 환경

운영 환경은 실제 사무실 매물과 개인정보를 처리하는 서비스다.

| 항목 | 기준 |
|---|---|
| 배포 기준 | 검증된 `main` 브랜치의 Production 배포 |
| Clerk | Production 인스턴스와 실제 사용자 계정 |
| Supabase | 운영 전용 프로젝트 |
| RLS | 모든 업무 테이블에 반드시 활성화 |
| 데이터 | 실제 매물·상담·계약 데이터만 입력 |
| 접근 | 로그인 필수, 초대된 사용자만 |
| 목적 | 일상 사무실 업무의 단일 원본 서비스 |

운영 환경은 개발용 설정, 테스트 데이터, 개발 키를 절대 사용하지 않는다.

## 7. 환경변수 관리 기준

### 7.1 기본 원칙

- 환경변수 값 자체는 GitHub에 올리지 않는다.
- `.env.local`은 개발 PC에서만 사용하고 Git 추적에서 제외한다.
- Vercel에는 Local/Preview/Production 환경마다 각 값을 별도로 등록한다.
- `NEXT_PUBLIC_`이 붙은 값은 브라우저에 전달될 수 있다는 전제로 관리한다.
- Clerk secret key, Supabase service role key는 서버 전용이며 절대 `NEXT_PUBLIC_`으로 만들지 않는다.
- 키가 노출되었거나 잘못 공유됐다고 판단되면 즉시 교체한다.

### 7.2 1차 환경변수 목록

| 변수 이름 | 용도 | 브라우저 노출 | Local | Preview | Production |
|---|---|---:|:---:|:---:|:---:|
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | Clerk 클라이언트 연결 | 가능 | 개발 키 | 개발 키 | 운영 키 |
| `CLERK_SECRET_KEY` | Clerk 서버 기능 | 불가 | 개발 키 | 개발 키 | 운영 키 |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase 프로젝트 주소 | 가능 | 개발 주소 | 개발 주소 | 운영 주소 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Supabase 브라우저 연결 | 가능 | 개발 키 | 개발 키 | 운영 키 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용 관리 작업 | 불가 | 필요 시만 | 필요 시만 | 필요 시만 |
| `APP_ENV` | 화면·로그 구분 | 가능 | `local` | `preview` | `production` |
| `NEXT_PUBLIC_APP_URL` | 로그인 리디렉션·링크 | 가능 | 로컬 주소 | Preview 주소 | 운영 도메인 |

`SUPABASE_SERVICE_ROLE_KEY`는 RLS를 우회할 수 있으므로, 일반 화면의 조회·저장에 사용하지 않는다. 관리자용 백그라운드 작업 등 명확한 서버 전용 기능이 생길 때만 검토한다.

### 7.3 환경변수 확인 절차

새 환경변수를 추가할 때마다 다음을 확인한다.

1. 브라우저에 공개돼도 되는 값인가?
2. Local·Preview·Production 각각에 맞는 값이 입력됐는가?
3. 실제 키 값이 코드·문서·커밋 메시지에 포함되지 않았는가?
4. Preview가 운영 Supabase나 운영 Clerk를 가리키지 않는가?
5. 키 교체가 필요할 때 어디에서 바꿀지 운영 문서에 기록했는가?

## 8. GitHub 브랜치와 Vercel 배포 흐름

### 8.1 최소 브랜치 규칙

| 브랜치 | 용도 | 배포 결과 |
|---|---|---|
| `main` | 검증된 코드만 보관 | Vercel Production 후보 |
| `feature/*` | 기능 개발 | Vercel Preview |
| `fix/*` | 오류 수정 | Vercel Preview |

예시:

```text
feature/auth-login
feature/listings-crud
feature/today-tasks
fix/listing-date-validation
```

### 8.2 작업 흐름

1. `main`에서 기능 브랜치를 만든다.
2. 로컬 개발 환경에서 테스트 데이터를 사용해 구현한다.
3. GitHub에 올려 Vercel Preview를 생성한다.
4. Preview에서 데스크톱·모바일·로그인·저장 흐름을 확인한다.
5. 관련 테스트 기준을 통과하면 `main`에 반영한다.
6. 운영 전환 전까지는 `main`의 Production 배포도 개발 Supabase와 개발 Clerk만 사용한다.
7. 운영 전환 체크리스트를 통과한 뒤에만 Production 환경변수를 운영 서비스로 바꾼다.

코드를 `main`에 반영했다는 사실만으로 실제 운영 전환이 완료된 것은 아니다.

## 9. Supabase 개발 모드 운영 기준

### 9.1 RLS 임시 비활성화의 허용 범위

초기에는 화면과 데이터 흐름을 빠르게 검증하기 위해 개발 Supabase 프로젝트의 RLS를 임시로 끌 수 있다.

허용 목적:

- 테이블 생성과 관계 확인
- Next.js CRUD 구현
- 입력 검증·목록·필터·오늘 할 일 계산 확인
- Clerk 로그인 화면과 서비스 진입 흐름 확인

허용하지 않는 목적:

- 실제 업무 데이터를 빠르게 먼저 넣기
- 운영 도메인에서 사용자에게 테스트하게 하기
- 권한 설계를 영구적으로 생략하기

### 9.2 개발 DB의 데이터 초기화 기준

개발 DB는 언제든 지우고 다시 만들 수 있어야 한다.

- 테스트 데이터 생성용 SQL 또는 seed 스크립트를 둔다.
- 실제 데이터가 없는지 확인한 뒤에만 테이블 초기화·재생성한다.
- 테이블 구조 변경은 migration 파일로 남긴다.
- 대시보드에서 수동 SQL을 실행했다면, 같은 변경을 migration에도 반영한다.

### 9.3 개발 DB에서 저장하지 않는 데이터

- 실제 전화번호와 이름
- 공동현관·방문 비밀번호
- 열쇠 위치
- 실제 매물 사진
- 계약서·신분증·입금 내역
- 실제 계약금·잔금 금액과 특정 계약자 정보

## 10. Clerk 개발 모드 운영 기준

### 10.1 개발 중 구현 범위

- 로그인 화면
- 로그아웃
- 로그인하지 않은 사용자 접근 차단
- 로그인한 사용자 이름 또는 이메일 표시
- Clerk 사용자 ID를 서버에서 읽을 수 있는 구조

### 10.2 개발 중 보류하는 범위

- 실제 직원 초대 운영
- 관리자/직원별 상세 메뉴 차단
- 다중 조직 선택 화면
- 소셜 로그인
- 2단계 인증

### 10.3 테스트 계정 기준

- 개발용 테스트 계정을 2개 이상 만든다.
- 한 계정은 관리자 예정 사용자, 한 계정은 직원 예정 사용자로 구분한다.
- 실제 사무실 이메일을 써도 되지만, 운영 계정과 혼동되지 않게 개발 인스턴스에서만 사용한다.
- 로그인 테스트에 쓰는 계정과 DB 테스트 데이터는 실제 업무 데이터와 무관해야 한다.

## 11. 운영 전환 게이트

다음 세 단계가 모두 끝나기 전에는 실제 데이터를 운영 Supabase에 입력하지 않는다.

### 게이트 A — 기능 안정화

- [ ] 로그인·로그아웃·보호된 경로 동작 확인
- [ ] 매물 신규 등록·최신 정보 수정·종료 처리 확인
- [ ] 상담·계약·오늘 할 일·광고 현황 확인
- [ ] 입력 오류 시 저장되지 않고 입력값이 유지되는지 확인
- [ ] 데스크톱과 모바일의 핵심 흐름 확인
- [ ] 테스트 데이터만 사용했는지 재확인

### 게이트 B — 운영 보안 적용

- [ ] 운영 Clerk 인스턴스 생성 및 Production 키 준비
- [ ] 운영 Supabase 프로젝트 생성
- [ ] 운영 DB에 migration만 적용
- [ ] 모든 업무 테이블에 `organization_id` 적용

| 상황 | 즉시 조치 | 재발 방지 |
|---|---|---|
| Preview가 운영 DB를 가리킴 | Preview 환경변수를 개발 DB로 즉시 교체, 접근 기록 확인 | 환경별 이름·키 분리와 배포 전 확인 |
| 실제 개인정보가 개발 DB에 입력됨 | 해당 데이터를 삭제하고 노출 범위 확인 | 테스트 데이터 템플릿만 사용 |
| API 키가 GitHub에 올라감 | 키 폐기·재발급, 커밋 이력 처리 | `.env.local` 제외, secret 스캔 도구 검토 |
| 개발 DB를 초기화함 | 테스트 데이터 seed로 복구 | 운영 DB와 완전 분리 유지 |
| RLS를 끈 채 운영 전환하려 함 | 실제 데이터 입력 중단, 운영 전환 게이트 B 수행 | 운영 배포 체크리스트 필수화 |
| Clerk 키를 잘못 연결함 | 로그인 환경을 확인하고 올바른 인스턴스 키로 교체 | 앱 상단에 현재 환경 표시 |

## 15. 확정 결론

개발의 속도를 위해 RLS를 임시로 끌 수는 있다. 그러나 그 편의는 아래 두 조건이 지켜질 때만 허용된다.

1. 개발 Supabase 프로젝트에는 가상 테스트 데이터만 있다.
2. 실제 운영 전환 전에 개발·운영 프로젝트를 분리하고 RLS를 완성한다.

이 원칙을 지키면 지금은 빠르게 만들고, 나중에는 실제 사무실 업무에 필요한 수준으로 안전하게 전환할 수 있다.
