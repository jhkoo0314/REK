# 부동산 매물관리 웹서비스 — Production 배포·운영 시작 체크리스트 v1.0

## 1. 문서 목적

이 문서는 개발·Preview 검토가 끝난 웹서비스를 실제 사무실 업무에 쓰기 직전에 확인하는 최종 체크리스트다.

이 서비스는 기존 Streamlit SQLite 데이터를 Supabase로 이관하지 않는다. Production 보안과 기능 검증을 마친 뒤, 웹서비스에서 건물·호실·매물·상담·계약을 새로 등록해 운영을 시작한다. 기존 SQLite는 과거 기록을 확인할 때만 쓰는 읽기 전용 백업으로 보관한다.

### 운영 시작 원칙

- 실제 데이터는 Production에만 입력한다.
- Production Supabase의 RLS는 활성화된 상태로 시작한다.
- Preview·Dev에는 실제 고객, 연락처, 계약금, 출입 정보, 매물 사진을 넣지 않는다.
- 한 번에 모든 업무를 옮기지 않고, 새로 들어오는 매물부터 웹서비스에 등록한다.
- 보안·매물 P0 오류가 남아 있으면 운영을 시작하지 않는다.

## 3. 역할과 책임

| 역할 | 배포 전 | 배포 중 | 운영 시작 후 |
| --- | --- | --- | --- |
| 운영 책임자(admin) | 승인, 실제 계정·조직 확인, 최종 업무 테스트 | 첫 로그인·첫 등록 확인 | 사용자 관리, 오류 우선순위 결정 |
| 개발 책임자 | 코드·migration·환경 변수·보안 점검 | Production 배포와 로그 확인 | 오류 수정, 배포 되돌리기 판단 지원 |

소규모 사무실에서는 한 사람이 여러 역할을 맡을 수 있다. 다만 최종 승인과 실제 업무 시나리오 확인은 가능하면 서로 다른 계정으로 한 번씩 수행한다.

## 4. 배포 전 체크리스트

### 4.1 계정·환경 분리

- [ ] Clerk Production 인스턴스가 Clerk Development와 분리되어 있다.
- [ ] Supabase Production 프로젝트가 Supabase Dev와 분리되어 있다.
- [ ] Vercel Production 환경 변수가 Preview/Development 값과 분리되어 있다.
- [ ] Production 도메인과 Clerk 허용 리다이렉트 URL이 일치한다.
- [ ] Preview URL이 Production Clerk·Supabase에 연결되지 않는다.
- [ ] 실제 데이터와 테스트 데이터가 같은 데이터베이스에 섞이지 않는다.

### 4.2 비밀값과 배포 설정

| 항목 | 확인 기준 | 완료 |
| --- | --- | --- |
| Clerk Publishable Key | Production용 공개 키가 올바른 환경에만 등록 | [ ] |
| Clerk Secret Key | 서버 전용이며 `NEXT_PUBLIC_` 접두사가 없음 | [ ] |
| Supabase URL | Production 프로젝트 URL | [ ] |
| Supabase Publishable Key | Production 공개 키 | [ ] |
| Supabase Secret/service-role Key | 필요한 제한된 서버 작업에만 등록, 일반 CRUD에 미사용 | [ ] |
| Git | `.env.local`과 비밀값 파일이 커밋되지 않음 | [ ] |
| Vercel | Production 브랜치와 자동 배포 대상 확인 | [ ] |
| 배포 주소 | HTTPS로 열리고 의도한 도메인으로 이동 | [ ] |

### 4.3 코드·DB 구조

- [ ] `main` 브랜치의 코드가 Preview에서 검토한 버전과 동일하다.
- [ ] Production에 적용할 DB migration 파일 목록을 확인했다.
- [ ] Migration을 적용해도 기존 Production 데이터가 없는 새 환경에서 오류가 나지 않는다.
- [ ] `organizations`, `organization_members`, `buildings`, `units`, `listings` 등 필요한 테이블이 생성된다.
- [ ] 상태·금액·날짜의 제약 조건이 적용되어 있다.
- [ ] 생성·수정 시각과 사용자 정보가 저장된다.
- [ ] 개발용 샘플 계정, 자동 로그인, 테스트 문구가 Production 빌드에 남아 있지 않다.

## 5. Production 보안 전환 체크리스트

### 5.1 Clerk–Supabase 연결

- [ ] Clerk와 Supabase의 공식 Native Integration을 Production 인스턴스끼리 연결했다.
- [ ] Clerk Production 계정으로 로그인한 요청이 Supabase에서 사용자 식별자(`sub`)를 확인할 수 있다.
- [ ] 운영 조직과 첫 admin 멤버십을 생성했다.
- [ ] 운영 staff 계정은 초대 기반으로만 생성한다.
- [ ] 멤버십이 없거나 비활성인 사용자는 업무 데이터에 접근할 수 없다.

### 5.2 RLS와 조직 분리

- [ ] 모든 업무 테이블에서 RLS가 활성화되어 있다.
- [ ] `organizations`, `organization_members`의 조회·관리 권한이 역할 기준에 맞다.
- [ ] `buildings`, `units`, `listings`의 SELECT/INSERT/UPDATE/DELETE 정책이 적용되어 있다.
- [ ] `consultations`, `consultation_followups`, `contracts`, `listing_advertisements`, `task_completions` 정책이 적용되어 있다.
- [ ] INSERT와 UPDATE에 `WITH CHECK` 기준이 있어 다른 조직 ID로 바꾸는 시도를 막는다.
- [ ] 같은 조직의 active admin/staff는 일반 업무 CRUD가 가능하다.
- [ ] 다른 조직 사용자, inactive 사용자, 미로그인 사용자는 조회·저장이 불가하다.
- [ ] 일반 업무 요청이 Supabase 비밀 키로 RLS를 우회하지 않는다.

### 5.3 민감 정보와 사진

- [ ] 매물·상담·계약 목록 API에 연락처·계좌·출입 정보가 기본 포함되지 않는다.
- [ ] 오류 메시지·서버 로그·URL에 개인정보나 비밀값이 남지 않는다.
- [ ] 사진 기능을 넣는 경우 Storage 버킷은 private이다.
- [ ] 사진 기능을 넣는 경우 조직별 경로와 Storage RLS를 적용했다.
- [ ] 사진 기능을 아직 넣지 않았다면 Storage 키·공개 버킷을 미리 만들지 않는다.

## 6. 기능 수용 체크리스트

### 6.1 매물 P0

- [ ] 건물 검색 후 기존 건물을 선택하고 새 호실·매물을 등록할 수 있다.
- [ ] 새 건물·새 호실·새 매물을 순서대로 등록할 수 있다.
- [ ] 같은 호실의 현재 매물 중복을 막거나 기존 매물로 안내한다.
- [ ] 건물명·주소·호실·매물번호 검색이 동작한다.
- [ ] 상태·유형·가격대·입주 가능일 필터가 동작한다.
- [ ] 가격·관리비·상태·입주 가능일 빠른 수정이 동작한다.
- [ ] 일반 수정이 새 매물을 자동 생성하지 않는다.
- [ ] 매물 상세의 기본 정보와 목록의 핵심 값이 일치한다.
- [ ] 모바일에서 매물 검색·상세 확인·간단 수정이 가능하다.

### 6.2 대시보드·상담·계약·광고 P1

- [ ] 오늘·지연 업무가 업무 유형별로 표시되고 상세로 이동한다.
- [ ] 완료 체크가 원본 매물·상담·계약 상태를 임의로 바꾸지 않는다.
- [ ] 상담에 매물·이력·다음 연락일을 연결할 수 있다.
- [ ] 계약에 매물·상담·일정·입금 확인을 연결할 수 있다.
- [ ] 계약 완료·취소 시 매물 상태 변경 여부를 사용자가 선택한다.
- [ ] 계약 완료 매물의 게시 중 광고를 확인할 수 있다.
- [ ] 광고 채널 상태를 기록할 수 있다.
- [ ] 광고 문구 생성·복사는 매물 데이터를 자동 변경하지 않는다.

### 6.3 최종 수용 테스트 결과

- [ ] `web_test_acceptance_v1.md`의 Blocker 0건이다.
- [ ] `web_test_acceptance_v1.md`의 Critical 0건이다.
- [ ] Major는 모두 수정했거나, 운영 책임자가 수동 절차와 보완 시점을 승인했다.
- [ ] admin과 staff가 각각 실제 업무 시나리오를 통과했다.
- [ ] Production 후보 환경에서 조직 분리·RLS 테스트를 완료했다.

## 7. 실제 운영 시작 순서

### 단계 1 — 시작 선언 전 확인

- [ ] 이 문서의 4~6장 체크리스트를 모두 확인한다.
- [ ] 기존 Streamlit SQLite 원본을 읽기 전용 백업으로 보관한다.
- [ ] “이 시점 이후 새로 들어오는 매물부터 웹서비스에 등록한다”는 내부 기준을 정한다.
- [ ] 첫 등록을 담당할 admin과 staff 계정을 확인한다.

### 단계 2 — Production 배포

| 순서 | 실행 | 확인 결과 |
| --- | --- | --- |
| 1 | `main`의 승인된 버전을 Production에 배포 | Production URL 정상 열림 |
| 2 | admin 로그인 | 대시보드 접근 가능 |
| 3 | staff 로그인 | 일반 업무 접근 가능, 사용자 관리 접근 불가 |
| 4 | 멤버십 없는 계정 확인 | 업무 데이터 접근 불가 |
| 5 | 다른 조직 테스트 계정 확인 | 운영 조직 데이터 접근 불가 |

### 단계 3 — 첫 실제 데이터 등록

기존 데이터를 옮기지 않는다. 신규 업무가 생길 때 아래 순서로 웹서비스에 직접 등록한다.

| 순서 | 사용자 행동 | 확인할 결과 |
| --- | --- | --- |
| 1 | 건물 검색 또는 새 건물 등록 | 중복 건물 없이 건물 선택/생성 |
| 2 | 호실 선택 또는 새 호실 등록 | 올바른 건물에 연결 |
| 3 | 매물 조건·상태·입주 가능일 입력 | 매물 목록과 상세에 정확히 표시 |
| 4 | 문의가 있으면 상담 등록 | 매물 연결과 다음 연락일 확인 |
| 5 | 계약이 진행되면 계약 등록 | 일정·입금·상태 확인 |
| 6 | 광고를 올리면 채널 상태 기록 | 계약 완료 시 종료 확인 가능 |

### 단계 4 — 초기 운영 확인

- [ ] 첫 실제 매물의 등록·검색·수정이 모두 정상이다.
- [ ] 첫 상담의 다음 연락일이 대시보드에 표시된다.
- [ ] 첫 계약의 일정·입금·매물 연결을 확인했다.
- [ ] 등록한 광고의 채널 상태가 매물 상세와 광고 현황에서 일치한다.
- [ ] 운영 중 발생한 오류는 등급(Blocker/Critical/Major/Minor)과 함께 기록한다.

## 9. 비상 시 업무 연속성 기준

웹서비스와 기존 Streamlit은 데이터가 자동 동기화되지 않는다. 따라서 장애 시 두 시스템에 같은 업무를 무작정 동시에 입력하면 데이터가 더 혼란스러워진다.

### 9.1 판단 순서

1. 문제가 로그인/전체 접속/특정 기능 중 어디에 있는지 기록한다.
2. 이미 웹서비스에 입력한 새 업무 기록이 있는지 확인한다.
3. 해당 기능만 사용 중지할지, 전체 업무를 잠시 기존 Streamlit으로 되돌릴지 결정한다.
4. 기존 Streamlit으로 임시 전환해야 하면, 전환 시점 이후의 핵심 업무를 별도 임시 기록으로 남긴다.
5. 웹서비스 복구 후 임시 기록을 검토하여 한 번만 반영한다.

### 9.2 임시 전환 시 기록할 최소 항목

| 업무 | 반드시 남길 항목 |
| --- | --- |
| 신규 매물 | 건물·호실·보증금·월세·관리비·상태·입주 가능일 |
| 가격/상태 변경 | 매물 식별, 이전 값, 변경 값, 변경 시각 |
| 상담 | 고객 식별명, 문의 조건, 연결 매물, 다음 연락일 |
| 계약 | 매물, 계약 상태, 주요 일정, 입금 확인 상태 |
| 광고 | 매물, 채널, 게시/종료 상태 |

복구 시에는 “웹서비스에 이미 저장된 것”과 “임시 기록으로만 남은 것”을 먼저 구분한다. 중복 입력이 확인되기 전에는 자동 일괄 반영하지 않는다.

| 로그인 | admin·staff가 정상 로그인하는지 | 실패 시 계정·리다이렉트·멤버십 확인 |
| 매물 | 새 등록과 빠른 수정이 저장되는지 | Critical이면 해당 기능 사용 중지 |
| 업무 목록 | 오늘 할 일과 다음 연락일이 보이는지 | 계산 기준·날짜 확인 |
| 권한 | staff가 사용자 관리에 접근하지 못하는지 | 즉시 수정 |
| 보안 | 다른 조직 데이터가 보이지 않는지 | 발견 시 운영 중지 수준 대응 |
| 데이터 품질 | 새 매물의 가격·상태·입주일이 실제와 일치하는지 | 원인 확인 후 최소 수정 |
| 로그 | 오류·권한 거부·배포 실패 기록 | Blocker/Critical 우선 처리 |

### 운영 첫 변경 원칙

- 오류가 없는 경우에도 바로 대량 수정·자동화·사진 기능을 추가하지 않는다.
- 반복적으로 불편한 지점만 기록한 뒤 P0/P1/P3 기준으로 우선순위를 정한다.
- 운영 흐름이 안정될 때까지 새 기능 배포는 작은 단위로 한다.
