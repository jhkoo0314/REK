# 부동산 매물관리 웹서비스 — 기술 아키텍처 v1.0

## 1. 문서 목적

이 문서는 매물관리 웹서비스를 실제로 만들고 운영하기 위한 기술 구조를 확정한다. 목표는 최신 기술을 많이 쓰는 것이 아니라, **2인 사무실이 매일 안정적으로 매물·상담·계약 업무를 처리할 수 있는 최소 구조**를 만드는 것이다.

이 구조는 다음 문서와 함께 사용한다.

- 제품 범위: `web_service_prd_v1.md`
- 개발 환경: `development_environment_plan.md`
- 권한 기준: `user_access_policy_v1.md`
- 데이터 구조: `supabase_data_model_v1.md`
- 보안 전환: `supabase_security_transition_plan.md`
- 업무·화면 기준: `web_workflow_spec_v1.md`, `web_screen_spec_wireframe_v1.md`

## 2. 확정 기술 스택

| 영역 | 확정 선택 | 역할 | 선택 이유 |
| --- | --- | --- | --- |
| 웹 프레임워크 | Next.js 16 App Router | 화면, 서버 처리, 배포 단위 | React 기반 화면과 서버 작업을 한 프로젝트에서 관리 |
| UI | React + TypeScript 5.x 이상 | 화면 구성과 오류 예방 | 업무 화면을 컴포넌트 단위로 재사용하고 입력 오류를 줄임 |
| 스타일 | Tailwind CSS | 여백·색상·반응형 디자인 | 화면 디자인을 일관되게 유지 |
| UI 부품 | shadcn/ui | 표, 폼, Dialog, Drawer, Toast 등 | 기본 HTML 느낌 없이 실무형 UI를 빠르게 구성 |
| 폼 검증 | React Hook Form + Zod | 입력·검증·오류 표시 | 금액·날짜·필수값 오류를 입력 단계에서 차단 |
| 표/목록 | TanStack Table | 매물·상담·계약 목록 | 정렬·필터·열 제어를 안정적으로 구현 |
| 날짜 | date-fns | 날짜 계산·표시 | 오늘 할 일과 계약·상담 일정 처리 |
| 인증 | Clerk | 로그인, 초대, 사용자 역할 | 인증 화면과 사용자 관리를 직접 만들지 않음 |
| 데이터베이스 | Supabase Postgres | 매물·상담·계약·광고 데이터 | 관계형 업무 데이터를 한 곳에서 관리 |
| 파일 | Supabase Storage (후순위) | 매물 사진 | 비공개 사진 접근 제어 가능 |
| 배포 | Vercel | Local/Preview/Production 배포 | Git 연결 후 검토용 배포와 운영 배포를 분리 |

### 2.1 TypeScript 버전 결정

초기 논의의 “TypeScript 4”가 아니라 **TypeScript 5.x 이상**을 사용한다. Next.js 16은 TypeScript 중심 개발 경험을 제공하므로, 새 프로젝트에서 과거 메이저 버전을 고정할 이유가 없다. 정확한 마이너 버전은 프로젝트 생성 시 Next.js가 제안하는 호환 버전으로 고정하고, 임의로 먼저 올리지 않는다.

### 2.2 사용하지 않는 기술

| 기술/구조 | 1차에서 사용하지 않는 이유 |
| --- | --- |
| 별도 Python API 서버(FastAPI 등) | 일상 CRUD·계산에 필요하지 않고 배포·인증·장애 지점만 늘어남 |
| 별도 Node/Express 서버 | Next.js 서버 기능으로 충분 |
| Prisma·Drizzle 등 별도 ORM | Supabase의 타입 생성과 `supabase-js`로 시작 가능. DB 로직이 복잡해질 때 검토 |
| Redux·Zustand 전역 상태 관리 | 목록·폼 중심 업무 도구에는 서버 데이터와 로컬 폼 상태로 충분 |
| tRPC·GraphQL | API 계층을 과하게 늘리지 않기 위해 제외 |
| Redis·메시지 큐·실시간 동기화 | 2인, 동시 수정이 드문 초기 업무에는 불필요 |
| 마이크로서비스 | 한 개의 웹 프로젝트로 운영 가능한 규모 |

## 4. Next.js 애플리케이션 설계

### 4.1 App Router 사용 기준

Next.js App Router를 사용한다. 목록·상세처럼 데이터를 읽는 화면은 기본적으로 서버에서 렌더링하고, 검색 입력·테이블 필터·폼·Dialog처럼 사용자 반응이 필요한 부분만 Client Component로 만든다.

| 구분 | 기본 선택 | 예시 |
| --- | --- | --- |
| Server Component | 기본 | 대시보드, 매물 상세, 초기 목록 데이터 |
| Client Component | 필요한 곳만 | 필터바, 빠른 수정 팝오버, 신규 매물 폼, 광고 문구 Drawer |
| Server Action | 폼 저장 중심 | 매물·상담·계약 등록과 수정 |
| Route Handler | 외부 호출 또는 파일 처리 필요 시 | 향후 파일 signed URL, 웹훅, 엑셀 내보내기 |

서버/클라이언트 구분은 성능 최적화보다 **비밀값과 권한 확인을 브라우저 밖에서 처리하기 위한 기준**이다.

### 4.2 화면 데이터 갱신 기준

| 상황 | 처리 방식 |
| --- | --- |
| 신규 등록·수정 성공 | 현재 화면의 데이터를 갱신하고 성공 메시지 표시 |
| 대시보드에 영향 | 저장 후 관련 화면을 재검증하여 오늘 할 일·상태 건수 반영 |
| 목록 빠른 수정 | 해당 행의 값만 즉시 반영하고, 실패하면 이전 값 유지와 오류 안내 |
| 여러 사람이 같은 매물 수정 | 1차에는 마지막 정상 저장값을 기준으로 처리. 저장 직전 최근 수정 시각이 달라졌으면 경고하는 기능은 후속 검토 |

### 4.3 기능 모듈 기준

코드는 “기술 종류”가 아니라 업무 단위로 읽히게 구성한다.

| 모듈 | 책임 |
| --- | --- |
| `listings` | 건물·호실 검색, 매물 등록·목록·상세·수정, 상태 변경 |
| `consultations` | 고객 문의, 상담 이력, 다음 연락일 |
| `contracts` | 계약 조건, 일정, 입금 확인, 매물 상태 제안 |
| `advertisements` | 채널 상태와 광고 문구 생성 |
| `tasks` | 오늘 할 일 계산과 완료 체크 |
| `members` | 사용자 초대·역할·활성 상태(admin) |

## 5. Python 사용 결정

### 결론

**웹서비스의 매일 쓰는 기능에는 Python 서버를 두지 않는다.** 기존 Streamlit에서 Python이 하던 가격 표기, 날짜 계산, 할 일 계산, 광고 템플릿 조합은 TypeScript로 옮긴다.

| 작업 | 1차 구현 위치 | 이유 |
| --- | --- | --- |
| 보증금·월세·관리비 표시 | TypeScript | 화면과 가장 가까운 단순 계산 |
| 오늘 할 일 계산 | TypeScript + Supabase 조회 | 날짜·상태 기준의 단순 업무 규칙 |
| 매물 상태·계약 상태 검증 | Zod + Server Action | 저장 전에 한 곳에서 검증 |
| 광고 문구 템플릿 조합 | TypeScript 함수 | 입력과 출력이 명확하고 즉시 결과 필요 |
| 엑셀 내보내기 | Next.js Route Handler | 웹에서 바로 파일 생성 가능 |
| 기존 SQLite 데이터 이관 | 일회성 Python 스크립트 가능 | 이미 있는 Python·SQLite 자료 활용 가능 |
| 사진 일괄 보정·OCR·대량 분석 | 필요 시 별도 Python 작업 | 웹 요청과 분리하는 편이 안전 |

### Python을 다시 검토할 조건

- 사진 수백 장을 한 번에 정리·OCR해야 한다.
- 정해진 시간에 대량 보고서를 만들거나 외부 파일을 일괄 변환해야 한다.
- 복잡한 통계·추천 모델을 반복 실행해야 한다.

이 경우에도 먼저 “웹 요청이 끝날 때까지 기다려야 하는 작업인지”를 판단한다. 시간이 오래 걸리는 작업이라면 웹 본체에 Python API를 바로 붙이기보다, 독립적인 일괄 실행 도구로 시작한다.

## 6. 인증·권한·데이터 접근 구조

### 6.1 인증 흐름

| 순서 | 처리 |
| --- | --- |
| 1 | 사용자가 Clerk로 로그인한다. |
| 2 | Next.js는 현재 Clerk 사용자와 세션을 확인한다. |
| 3 | 서버는 `organization_members`에서 활성 멤버십·역할을 확인한다. |
| 4 | 업무 요청은 사용자의 Clerk 인증 문맥으로 Supabase에 전달한다. |
| 5 | Production에서는 Supabase RLS가 같은 조직의 활성 멤버 접근만 최종 허용한다. |

Clerk와 Supabase는 공식 Native Integration으로 연결한다. 이 방식은 Clerk가 서명한 세션 토큰을 Supabase가 신뢰할 수 있도록 하며, 기존 수동 JWT Template 구성에 새로 의존하지 않는다.

### 6.2 접근 위치별 규칙

| 위치 | 허용하는 접근 | 금지하는 접근 |
| --- | --- | --- |
| 브라우저 | 공개 키를 사용한 UI 동작, 필요 시 사용자의 인증 토큰으로 제한된 요청 | Clerk Secret·Supabase secret/service-role 키 사용 |
| Server Component/Action | 사용자 인증 확인 후 일반 업무 CRUD | 조직 ID를 요청값만으로 신뢰 |
| 제한된 운영 서버 작업 | DB 마이그레이션, 제한된 관리자 작업, 긴급 복구 | 일반 매물 목록·수정에 비밀 키로 RLS 우회 |
| Supabase | RLS와 Storage 정책으로 최종 행/파일 권한 판단 | 조직 경계를 넘는 조회 허용 |

### 6.3 개발에서 운영으로의 전환

| 환경 | Clerk | Supabase RLS | 데이터 |
| --- | --- | --- | --- |
| Local | Development | 개발 중 비활성화 가능 | 가공 테스트 데이터만 |
| Preview | Development | 개발 검증 단계에 따라 적용 | 가공 테스트 데이터만 |
| Production | Production | 활성화 필수 | 보안 테스트 후 실제 업무 데이터 |

정확한 RLS 정책과 전환 절차는 `supabase_security_transition_plan.md`를 따른다.

## 7. Supabase 사용 방식

### 7.1 데이터베이스

`organizations`, `organization_members`, `buildings`, `units`, `listings`, `consultations`, `consultation_followups`, `contracts`, `listing_advertisements`, `task_completions`를 중심으로 사용한다. 자세한 열과 관계는 데이터 모델 문서를 기준으로 한다.

| 구분 | 구현 기준 |
| --- | --- |
| DB 변경 | Supabase SQL migration 파일로 남긴다. 대시보드에서만 수동 수정하지 않는다. |
| 타입 | DB 스키마에서 TypeScript 타입을 생성해 사용한다. |
| 쿼리 | 한 번에 필요한 열만 명시적으로 선택한다. 목록에서 `select('*')`를 쓰지 않는다. |
| 조직 경계 | 모든 업무 쿼리에 조직 맥락이 있어야 하고, Production RLS로 재확인한다. |
| 삭제 | 연결된 기록이 있으면 물리 삭제보다 상태 변경·비활성화를 우선한다. |

### 7.2 사진 Storage(후순위)

| 항목 | 기준 |
| --- | --- |
| 버킷 | private `listing-photos` |
| 파일 경로 | `{organization_id}/{listing_id}/{file_id}.{ext}` |
| 조회 | 짧은 유효시간의 signed URL |
| 제한 | 허용 파일 형식·용량 검증, 조직·매물 소속 검증 |
| 운영 전제 | DB RLS와 별도로 Storage 정책도 완료 |

### 7.3 Realtime 사용 여부

1차에는 사용하지 않는다. 저장 후 화면을 갱신하는 방식으로 충분하다. 같은 매물을 동시에 자주 수정하거나 즉시 알림이 꼭 필요해질 때만 검토한다.

## 8. 코드와 폴더 구조

프로젝트 규모에 맞게 한 저장소, 한 Next.js 앱으로 관리한다.

| 경로 | 역할 |
| --- | --- |
| `app/` | URL별 페이지, 레이아웃, Server Action, Route Handler |
| `app/(app)/` | 로그인 후 공통 레이아웃을 쓰는 업무 화면 |
| `components/ui/` | shadcn/ui 기반의 재사용 기본 부품 |
| `components/shared/` | 헤더, 사이드바, 상태 배지, 공통 표·폼 부품 |
| `features/listings/` | 매물 업무 화면·폼·검증·서버 처리 |
| `features/consultations/` | 상담 업무 관련 코드 |
| `features/contracts/` | 계약 업무 관련 코드 |
| `features/advertisements/` | 광고 현황·문구 템플릿 코드 |
| `features/tasks/` | 오늘 할 일 계산·완료 처리 |
| `lib/` | Clerk, Supabase, 날짜·금액·권한 공통 함수 |
| `types/` | 생성된 DB 타입과 화면용 타입 |
| `supabase/migrations/` | DB 구조·정책 변경 기록 |
| `scripts/` | 일회성 데이터 이관·점검 스크립트 |
| `docs/` | 프로젝트 문서의 사본 또는 연결 정보 |

처음부터 모든 화면을 지나치게 작게 쪼개지 않는다. 한 기능 안에서 반복되는 UI나 로직이 보일 때만 `components` 또는 `lib`로 분리한다.

## 9. 환경 변수와 비밀값 관리

### 9.1 환경별 분리

| 환경 | 용도 | 연결 대상 |
| --- | --- | --- |
| Local | 개인 개발 | Clerk Development + Supabase Dev |
| Preview | 변경 검토 | Clerk Development + Supabase Dev/Preview 테스트 데이터 |
| Production | 실제 업무 | Clerk Production + Supabase Production |

Vercel은 Local, Preview, Production 환경을 구분해 배포·환경 변수를 관리할 수 있다. 같은 이름의 변수라도 환경마다 다른 값을 넣어, 테스트 DB가 운영 배포에 연결되지 않도록 한다.

### 9.2 변수 분류

| 분류 | 예시 이름 | 사용 위치 | 규칙 |
| --- | --- | --- | --- |
| 공개 설정 | `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | 브라우저/서버 | 공개 전제 값만 사용 |
| 공개 설정 | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 브라우저/서버 | RLS가 실제 접근을 제한 |
| 서버 비밀값 | `CLERK_SECRET_KEY` | Next.js 서버만 | `NEXT_PUBLIC_` 접두사 금지 |
| 제한된 서버 비밀값 | `SUPABASE_SECRET_KEY` 또는 legacy service role | 제한된 서버 작업만 | 일반 CRUD·브라우저 사용 금지 |
| 운영 설정 | 앱 URL, 허용 리다이렉트 URL | 환경별 | Local/Preview/Production을 섞지 않음 |

`.env.local`은 Git에 올리지 않는다. 비밀값을 코드·문서·스크린샷·오류 메시지에 기록하지 않는다.

## 10. 배포와 변경 운영

### 10.1 Git·Vercel 흐름

| 단계 | 브랜치/환경 | 하는 일 | 배포 결과 |
| --- | --- | --- | --- |
| 개발 | 기능 브랜치 | 기능 구현과 로컬 확인 | 필요 시 Preview |
| 검토 | Pull Request + Preview | 실제 화면·업무 흐름 확인 | 테스트 URL |
| 운영 반영 | `main` 병합 | 검토 통과 기능만 반영 | Production 배포 |

Preview는 운영과 분리된 테스트 공간이다. 실제 고객·계약·출입·사진 데이터는 Preview에 넣지 않는다.

### 10.2 DB 변경 흐름

1. 스키마·RLS 변경을 SQL migration 파일로 작성한다.
2. Dev Supabase에 먼저 적용하고 가공 데이터로 확인한다.
3. 기능 브랜치 Preview에서 화면 흐름을 확인한다.
4. 운영 적용 전 백업·테스트·변경 내용을 확인한다.
5. Production Supabase에 순서대로 적용한다.
6. 배포 후 로그인·조회·저장·조직 분리 테스트를 다시 수행한다.

운영 DB를 화면 수정 검증용으로 직접 사용하지 않는다.

## 11. 백업·로그·장애 대응의 최소 기준

| 대상 | 1차 기준 | 비고 |
| --- | --- | --- |
| DB 구조 | Git의 migration 파일 | 같은 구조를 재현할 수 있어야 함 |
| 업무 데이터 | Supabase 백업 정책 확인 + 정기 내보내기 계획 | 별도 운영·백업 문서에서 주기 확정 |
| 배포 이력 | Vercel 배포 기록 | 문제가 생기면 직전 배포로 되돌릴 근거 |
| 오류 확인 | Vercel 로그와 Supabase 로그 | 개인정보·비밀값이 로그에 남지 않게 함 |
| 사용자 행동 | 생성·수정 시각과 사용자 ID | 초기에는 핵심 변경 정보만 기록 |

외부 모니터링 서비스(Sentry 등)는 실제 사용 중 오류를 놓치기 시작할 때 추가한다. 시작부터 여러 운영 도구를 붙이지 않는다.

## 13. 아키텍처 완료 기준

- [ ] Next.js 16 App Router 단일 프로젝트에서 업무 화면과 서버 처리가 실행된다.
- [ ] TypeScript, Tailwind, shadcn/ui, Zod, React Hook Form, TanStack Table의 역할이 겹치지 않는다.
- [ ] Clerk가 로그인·초대를 담당하고, Supabase는 업무 데이터와 RLS를 담당한다.
- [ ] 일반 업무 CRUD에 별도 Python 또는 별도 API 서버가 필요하지 않다.
- [ ] 개발·Preview·운영의 Clerk·Supabase·Vercel 환경 변수가 분리되어 있다.
- [ ] Production 일반 CRUD는 사용자 인증 문맥과 RLS를 통과한다.
- [ ] 비밀 키는 브라우저·Git·일반 로그에 노출되지 않는다.
- [ ] DB 변경은 migration 파일로 남고, 운영 적용 전에 Dev에서 검증한다.
- [ ] 사진 업로드·대량 처리·AI 기능은 핵심 매물 관리가 안정된 뒤 별도 단계로 추가한다.
