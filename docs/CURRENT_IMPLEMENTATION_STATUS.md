## 현재 단계

- 1단계 완료 — P0 데이터 항목 확정, migration 작성 및 사용자의 Dev DB 수동 적용 완료
- 2-1 구현 완료 — 조직별 매물 목록·검색 화면 구현. Dev 가공 seed·실조회 검증 대기
- 2-2 구현 완료 — 신규 매물 등록·저장 흐름을 브라우저에서 정상 확인
- 2-3 구현 완료 — 상세·수정·목록 반영을 브라우저에서 정상 확인
- 2-4 구현 진행 — 목록의 빠른 수정 구현 완료, 건물·호실 관리와 이력 대기
- 다음 작업: 2-4 건물·호실 관리 화면

## 현재 구현된 기능

- Next.js 16·TypeScript·Tailwind 프로젝트를 루트 폴더에 만들었다.
- Clerk Development를 연결하고, 로그인·회원가입 주소와 사용자 메뉴를 추가했다.
- 로그인된 사용자만 업무 화면 그룹에 접근하도록 했다. 기본 시작 주소는 `/consultations`다.
- 공통 `AppShell`, `PageHeader`, 빈 화면 부품과 상담·인박스·매물·건물·계약·광고의 빈 주소를 기능별 파일로 만들었다.
- 가공 목업 데이터로 상담 목록·상세·상담 조건 매물 검색·제안 화면 이동, 오늘 예정 업무, 건물·호실 탐색기, 계약 목록, 광고비·문구 화면을 구현했다.
- 상담 목록 상단에 `＋ 새 상담 등록`을 추가하고, Streamlit의 일반 상담/매물 상담 구분, 고객·상담·희망 조건·다음 연락일 입력 순서를 반영한 저장 전 등록 화면을 구현했다. 저장 버튼은 안내만 표시한다.
- 실제 DB 조회·저장, Supabase 연결은 아직 구현하지 않았다.
- P0 조직·건물·호실·매물 및 제한 연락처·호실 출입 정보의 열 이름, 필수 여부, 상태값, 중복·금액·날짜 규칙과 기본 노출 제외 원칙을 `P0_DATA_FIELD_SPEC.md`로 확정했다.
- `supabase/migrations/20260826000100_create_p0_core_schema.sql`을 작성했다. 이 migration은 Dev에서 RLS를 명시적으로 비활성화하도록 작성했으며, 사용자가 Supabase Dev DB에 직접 적용했다. Production DB에는 적용하지 않았다.
- `DEV_DB_APPLY_PRECHECK.md`에 가공 seed, Dev 초기화 영향, 적용 순서와 제외 대상을 기록했다. 원격 Dev DB 대상명은 아직 조회하지 않았다.
- `DEV_DB_RESET_AND_APPLY.md`에 Dev `public` 스키마만 초기화하고 P0 migration을 수동 적용하는 순서를 기록했고, 사용자가 초기 P0 migration 적용을 완료했다.
- 2-1 매물 목록은 서버에서 Clerk의 활성 조직과 Dev DB의 active 멤버십을 다시 확인한 뒤 현재 조직의 매물만 읽도록 구현했다. 검색·필터 조건은 URL에 남기며, 목록에는 연락처·출입 정보·내부 메모를 조회하지 않는다.
- Clerk Development의 `REK_test` 조직 생성을 확인하고, 웹 상단에 조직 선택 메뉴를 추가했다.
- `REK_test` 조직과 현재 로그인한 사용자 1명을 Dev DB의 `organizations`, `organization_members`에 active admin으로 연결했다. 연결 상태를 읽기 전용으로 다시 확인했다.
- `20260826000200_add_listing_reference_number.sql`을 작성했다. 이는 목록의 `M-000001` 표시번호를 위한 추가 migration이며, 사용자가 Dev에 적용했다고 알려왔다.
- 신규 매물 저장 DB 함수(`20260826000300`)와 Dev 웹 접근 권한(`20260826000400`)을 통한 등록 흐름은 브라우저에서 정상 동작을 확인했다. migration별 수동 적용 시각은 별도로 기록하지 않았다.
- 2-2 신규 매물 등록 화면과 서버 저장 처리를 구현했다. 기존/새 건물·호실 선택, 금액·거래 방식 검증, 저장 중 중복 클릭 방지, 저장 결과 안내를 포함하며 사용자가 브라우저에서 정상 동작을 확인했다.
- 2-3 매물 상세·수정의 기본 흐름을 구현했다. 목록에서 같은 조직의 현재 매물만 상세로 열고, 일반 조건을 수정하면 같은 매물 행을 갱신한다. 연락처·출입 정보·상담·계약 연결은 표시하지 않는다.
- 매물 등록·수정 화면에 세대 비밀번호 제한 입력칸을 추가했다. 이 값은 목록과 일반 상세에 표시하지 않으며, 신규 등록 저장을 위한 `20260826000600` migration은 Dev 수동 적용 대기다.
- 매물 목록의 각 행에는 비밀번호 값을 미리 싣지 않고, `비밀번호 보기`를 눌렀을 때만 서버가 같은 조직·현재 매물을 다시 확인해 작은 확인창에 표시하도록 했다.
- 매물 등록·수정에 임대인·세입자 연락처 제한 입력칸을 추가했다. 임대인은 건물 공통 연락처, 세입자는 새 `unit_contacts` 호실 연락처 테이블에 분리 저장한다. `20260826000700` migration은 Dev 수동 적용 대기다.
- 새 매물 등록에서 기존 건물은 건물명·주소 검색 선택창으로 고른다. 선택 결과는 최대 8건으로 좁혀 표시하며, 기존 건물·호실의 제한 연락처는 새 등록 화면에서 비워 둔다고 자동 삭제하지 않는다.
- 현재 매물 조건에서 현장 상태 입력을 제거하고, 입주 조건을 즉시 가능·날짜 지정·확인 필요로 분리했다. 이 값을 저장·검색하기 위한 `20260826000800` migration은 Dev 수동 적용 대기다.
- 원룸·투룸 P0 등록·수정·상세 화면에서 전용면적 입력·표시를 제거했다. `listings.exclusive_area_m2` DB 칼럼은 아파트 등 후속 확장을 위해 남기며, 기존 값은 수정 저장으로 지우지 않는다.
- 2-4의 첫 범위로 목록 행의 `빠른 수정`을 구현했다. 상태·사진 상태·마지막 재확인일·보유처만 수정하며, 서버가 같은 조직의 현재 매물을 다시 확인한 뒤 저장한다.
- 신규 호실에 `302호` 같은 숫자 호실을 입력하면 층을 자동 제안하고 직접 수정할 수 있게 했다. 호실 단계의 방 구조 입력은 제거했으며, 현재 매물 조건의 방 구조로 표시·조회한다. 현재 선택 가능한 방 구조는 원룸·투룸·투베이·쓰리룸·주인세대다.
- 위 추가 방 구조를 Dev DB에도 저장할 수 있도록 `20260826000500_expand_residential_property_types.sql`을 작성했다. 이 파일은 아직 Dev에 적용하지 않았다.
