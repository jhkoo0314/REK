# Supabase 보안 전환 계획

## 개발 중

- Dev에는 가공 데이터만 사용한다.
- UI와 서버는 항상 로그인 사용자 조직 기준으로 설계한다.
- P0 Dev DB는 RLS를 **명시적으로 비활성화**한다. 이 설정은 migration에 남기며, 가공 연락처·가공 출입 비밀번호를 포함한 화면 저장·재조회 검증에 사용한다.
- RLS가 꺼진 Dev DB에는 실제 고객 연락처·실제 출입 비밀번호·실제 계약 정보를 절대 넣지 않는다.
- service-role/secret 키로 일반 CRUD를 우회하지 않는다.
- 매물의 제한 연락처와 출입 비밀번호는 일반 화면 목업에는 넣지 않는다. Dev seed에는 저장·수정·재조회 검증용으로 명백한 가공 값만 넣을 수 있으며, 매물 기본 목록·검색·광고 조회문에서는 제한 테이블을 제외한다. P1 상담의 고객 연락처는 같은 조직 직원의 상담 목록·상세 조회에만 포함할 수 있다.

## Production 전환

1. Clerk Production, Supabase Production, Vercel Production을 분리한다.
2. Clerk–Supabase Native Integration을 연결한다.
3. 모든 업무 테이블에 RLS를 활성화한다.
4. 조직 멤버십 기준 SELECT·INSERT·UPDATE·DELETE 정책과 `WITH CHECK`을 작성한다.
5. `building_contacts`, `unit_access_details`와 상담 연락처에도 별도 RLS를 적용한다. `organization_member_sensitive_permissions`에서 admin이 staff별 민감정보 열람 권한을 허용한 경우에만 상세 화면의 명시적 조회·수정 요청으로 접근하게 한다.
6. admin/staff/inactive/다른 조직/미로그인 계정과, 민감정보 권한이 있는 staff·없는 staff를 나누어 검증한다.
7. 실제 데이터는 위 검증과 수용 테스트가 모두 끝난 뒤 입력한다.

## Dev DB와 Production DB의 차이

| 구분 | Dev | Production |
| --- | --- | --- |
| RLS | 비활성화. 가공 데이터의 기능 검증용 | 활성화. 조직·활성 멤버 기준 정책 필수 |
| 연락처·출입 비밀번호 | 가공 값만 저장·상세 조회 가능 | 실제 값 저장 전 RLS·조직 분리·멤버별 권한 테스트 필수 |
| 목적 | 화면 저장·수정·재조회 확인 | 실제 업무 운영 |

## 금지

- 브라우저에 비밀 키 넣기
- Production RLS를 끈 채 운영하기
- 운영 문제를 이유로 전체 RLS 해제하기
- 실제 데이터가 든 Streamlit SQLite를 Dev에 복사하기
