# 웹 재빌드 기준서

> 기준일: 2026-08-25
>
> 상태: 코드 재빌드 시작 전
>
> 이 문서는 현재 `C:\realestate-main`의 Streamlit 업무 시스템을 웹으로 다시 구현하기 위한 단일 기준이다.

## 1. 목표와 판단 기준

이 프로젝트는 고객 공개용 매물 사이트가 아니다. 초대된 사무실 직원이 매물·상담·계약·광고비·오늘 할 일을 안전하게 처리하는 내부 업무 웹서비스다.

기능·입력 항목·업무 순서는 Streamlit의 `README.md`, `AGENT.md`, 데이터 정의서와 업무 흐름서를 기준으로 한다. 구현 기술만 Next.js, Clerk, Supabase로 바꾼다.

우선순위는 데이터 손실과 잘못된 상태 변경 방지, 건물 → 호실 → 현재 매물 업무, 오늘 업무 확인, 민감 정보 보호, 반복 업무 단축 순서다.

## 2. 재빌드 범위

| 단계 | 구현 대상 | 이번 단계에서 하지 않는 일 |
| --- | --- | --- |
| 기반 | Next.js, Clerk 로그인, App Shell, 공통 UI, Supabase 연결 | Production 배포, 실제 데이터 입력 |
| P0-A | 조직·멤버, 건물·호실·매물의 등록·검색·상세·수정 | 자동 회차 생성, 사진 파일 업로드 |
| P0-B | 사진 보유 여부·재확인·현장 상태·보유처, 목록 빠른 수정, 건물·호실 관리, 매물 이력 | 대량 수정 |
| P1-A | 상담 등록·수정·후속 전화/문자/방문 이력·다음 연락일 | 자동 문자 발송, 고객용 CRM |
| P1-B | 계약 일정·금액·중개 방식·단계 이력·출처 상담 연결 | 다건 입금·수수료 자동 계산 |

## 3. 반드시 지킬 업무 규칙

- 모든 업무 데이터는 `건물 → 호실 → 매물` 관계를 따른다.
- 가격·관리비·상태·입주 가능일 같은 일반 변경은 같은 현재 매물을 수정한다. 새 매물은 자동으로 만들지 않는다.
- 매물 수정은 연결된 상담·계약·이력을 삭제하거나 새로 만들지 않는다.
- 계약의 실제 계약 매물과 출처 상담의 최초 문의 매물은 달라도 된다.
- 계약 완료·해지 등으로 매물 또는 상담 상태를 바꾸기 전에는 웹에서 영향과 선택지를 보여 주고 사용자의 확인을 받는다.
- 광고 문구의 입력값과 결과는 저장하지 않으며, 생성만으로 다른 상태를 바꾸지 않는다.
- 기본 목록과 오늘 할 일에는 연락처·출입 비밀번호·내부 메모를 표시하지 않는다. 상세에서도 민감 정보는 접어서 표시한다.
- 금액은 만원 단위 정수, 업무 날짜는 시간 없는 날짜로 저장한다.

## 4. 데이터와 보안 기준

- 모든 업무 테이블은 `organization_id`를 포함한다. 브라우저에서 받은 조직 ID를 신뢰하지 않는다.
- 서버는 Clerk 로그인과 활성 멤버십을 확인한다. Production에서는 Supabase RLS도 함께 통과해야 한다.
- secret/service-role 키는 브라우저 또는 일반 CRUD에 사용하지 않는다.
- Local·Dev·Preview에는 가공 데이터만 사용한다.
- 기존 Streamlit SQLite 원본은 읽기 전용 보관 자료다. 자동 이관하지 않는다. 실제 이관은 별도의 범위·백업·검증·사용자 승인이 있어야만 검토한다.

## 5. 새 코드 구조

```text
app/                         라우트 조립과 서버 페이지
components/ui/               기본 UI
components/shared/           앱 셸·상태 배지·표 틀·민감정보 표시
features/listings/           매물·건물·호실 업무
features/consultations/      상담과 후속 이력
features/contracts/          계약과 단계 이력
features/tasks/              오늘 할 일
features/advertisements/     광고비·문구 생성
features/exports/            Excel 내보내기
lib/                         Clerk·Supabase·권한·날짜·금액 공통 함수
supabase/migrations/         순서가 있는 DB 변경 파일
```

각 `app/**/page.tsx`는 화면 조립만 한다. 큰 카드·표·폼은 해당 `features` 폴더에 둔다. 승인된 `docs/Design_guide/`의 색상·글꼴·정보 위계·문구를 사용한다.

## 6. DB 재시작 원칙

코드 재빌드와 Dev DB 초기화는 별도 작업이다.

1. 새 P0 데이터 모델과 migration 순서를 문서로 확정한다.
2. migration 파일을 작성한다. 이 단계에서는 Dev DB를 바꾸지 않는다.
3. 사용자가 명시적으로 승인한 경우에만 Dev DB를 초기화하고 새 migration을 적용한다.
4. 가공 조직·가공 계정·가공 매물 seed를 넣고 브라우저 흐름을 확인한다.
5. Production DB·Clerk Production·기존 SQLite는 이 과정에서 절대 바꾸지 않는다.

기존 재빌드 전 migration과 seed는 삭제했다. 새 P0 데이터 모델 검토 뒤, 새 migration과 가공 seed를 처음부터 작성한다.

## 7. 완료 기준

- P0: 가공 계정으로 새/기존 건물·호실 매물 등록, 검색, 상세, 수정, 빠른 수정과 민감 정보 숨김을 확인한다.
- P1: 상담 후속 이력, 계약·출처 상담·일정, 오늘/지연 업무·완료 체크, 광고비·문구·내보내기를 각각 가공 데이터로 확인한다.
- P2: admin/staff/inactive/다른 조직 계정, PC·모바일, 저장 오류·빈 화면·권한 없음, RLS와 Production 전환 조건을 확인한다.

모든 단계는 lint·typecheck·build·관련 테스트와 실제 브라우저 확인을 구분해 기록한다.
