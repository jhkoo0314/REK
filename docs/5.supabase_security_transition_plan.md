# 부동산 매물관리 웹서비스 — Supabase 보안 전환 계획서 v1.0

## 1. 문서 목적

이 문서는 개발 초기의 **Supabase RLS 비활성화 + Clerk Development** 환경에서 작업한 뒤, 실제 업무용 웹서비스로 전환할 때 필요한 보안 기준과 전환 순서를 정의한다.

목표는 두 가지다.

1. 개발 속도를 위해 초기 구현을 단순하게 시작한다.
2. 실제 매물·고객·계약 정보를 넣기 전에, 로그인 사용자와 소속 사무실에 따라 데이터가 분리되도록 전환한다.

본 문서는 `web_service_prd_v1.md`, `development_environment_plan.md`, `user_access_policy_v1.md`, `supabase_data_model_v1.md`의 후속 문서다.

## 2. 반드시 지킬 원칙

| 구분 | 개발 단계 | 실제 운영 단계 |
| --- | --- | --- |
| Clerk | Development 인스턴스 | Production 인스턴스 |
| Supabase | 별도 Dev 프로젝트, RLS 일시 비활성화 가능 | 별도 Production 프로젝트, RLS 활성화 필수 |
| 데이터 | 가공한 테스트 데이터만 사용 | 실제 업무 데이터 사용 가능 |
| 배포 | Local / Preview | Production |
| 접근 제어 | 화면과 서버의 기본 로그인 확인 | Clerk 로그인 + Next.js 서버 검증 + Supabase RLS |

### 2.1 개발 모드에서 허용하는 범위

- Dev Supabase 프로젝트에서만 RLS를 비활성화한다.
- 가공한 건물명·호실·연락처·계약금·사진만 사용한다.
- Preview 배포에도 실제 고객 정보, 실제 출입 비밀번호, 실제 매물 사진을 넣지 않는다.
- 개발 편의를 위해 RLS를 끈 상태라도, 모든 API와 화면은 `organization_id`를 기준으로 설계한다.

### 2.2 운영에서 절대 허용하지 않는 범위

- 운영 Supabase에서 RLS를 끈 채 실제 데이터를 저장하지 않는다.
- 브라우저 코드에 Supabase `secret`/`service_role` 키를 넣지 않는다.
- 일반 매물 CRUD에 RLS를 우회하는 서버 비밀 키를 사용하지 않는다.
- 요청 본문으로 받은 `organization_id`를 그대로 신뢰하지 않는다.
- 문제가 생겼다고 운영 RLS를 임시로 전체 해제하지 않는다.

## 3. 목표 보안 구조

실제 운영에서는 한 가지 장치에만 의존하지 않는다.

| 계층 | 책임 | 핵심 기준 |
| --- | --- | --- |
| Clerk | 사용자가 누구인지 확인 | 초대된 사용자만 로그인, 비활성 사용자는 차단 |
| Next.js 서버 | 사용자가 어떤 업무를 하려는지 확인 | 서버에서 로그인·역할·소속을 확인하고 입력값 검증 |
| Supabase RLS | 사용자가 어떤 행을 읽고 바꿀 수 있는지 최종 제한 | 같은 `organization_id`의 활성 멤버만 접근 |
| Supabase Storage | 사진 파일 접근 제한 | 비공개 버킷과 조직별 경로 정책 적용 |

Clerk와 Supabase는 **공식 Native Integration 방식**으로 연결한다. 과거 Clerk JWT Template 방식은 신규 구현 기준으로 사용하지 않는다. 연결 후에는 Supabase가 요청 JWT에서 Clerk 사용자 식별자(`sub`)를 읽을 수 있는지 실제 테스트로 확인한다.

## 4. 기준 식별자와 소속 판정

### 4.1 기준 식별자

| 항목 | 기준 값 | 사용처 |
| --- | --- | --- |
| 사용자 | Clerk 사용자 ID | `organization_members.clerk_user_id` |
| 조직 | `organizations.id` (UUID) | 모든 업무 테이블의 `organization_id` |
| 역할 | `admin`, `staff` | 화면·서버의 업무 권한 판단 |
| 멤버 상태 | `active`, `inactive` | RLS 접근 허용 여부 |

### 4.2 소속 판정 규칙

1. 로그인한 Clerk 사용자의 `sub` 값을 가져온다.
2. `organization_members`에서 동일한 `clerk_user_id`이면서 `status = 'active'`인 멤버를 찾는다.
3. 그 멤버의 `organization_id`와 같은 행만 업무 데이터에 접근할 수 있다.
4. 멤버가 없거나 `inactive`이면 어떠한 업무 데이터도 읽거나 수정할 수 없다.

초기에는 한 사람이 한 조직에만 속한다. 향후 여러 사무실을 지원할 때는 활성 조직 선택 기능을 추가하되, 그 전까지 조직을 요청값으로 임의 변경할 수 없게 한다.

## 5. RLS 정책 설계 기준

### 5.1 공통 정책 원칙

`buildings`, `units`, `listings`, `consultations`, `consultation_followups`, `contracts`, `listing_advertisements`, `task_completions` 및 이후 추가되는 업무 테이블은 아래 원칙을 따른다.

| 작업 | 허용 조건 |
| --- | --- |
| 조회 (`SELECT`) | 로그인한 사용자가 해당 조직의 활성 멤버 |
| 추가 (`INSERT`) | 새 행의 `organization_id`가 로그인한 사용자의 조직과 동일 |
| 수정 (`UPDATE`) | 기존 행과 수정 후 행 모두 로그인한 사용자의 조직과 동일 |
| 삭제 (`DELETE`) | 로그인한 사용자가 해당 조직의 활성 멤버 |

업무상 `admin`과 `staff` 모두 매물·상담·계약을 관리할 수 있도록 1차 운영 정책에서는 두 역할에 동일한 데이터 CRUD 권한을 둔다. 사용자 초대, 멤버 비활성화, 조직 설정 변경은 `admin`만 가능하다.

### 5.2 테이블별 정책 범위

| 테이블 | 조회 | 추가/수정/삭제 | 비고 |
| --- | --- | --- | --- |
| `organizations` | 본인 조직만 | 조직 설정은 admin만 | 초기에는 설정 화면 최소화 |
| `organization_members` | 본인 행 조회, admin은 조직 멤버 관리 | admin만 멤버 관리 | 권한 판정의 기준 테이블 |
| `buildings` | 조직 멤버 | 조직 멤버 | 건물주 등 민감 정보는 목록에서 제외 |
| `units` | 조직 멤버 | 조직 멤버 | 건물에 종속 |
| `listings` | 조직 멤버 | 조직 멤버 | 현재 매물/가격/상태 |
| `consultations` | 조직 멤버 | 조직 멤버 | 고객 연락처는 상세 화면에서만 |
| `consultation_followups` | 조직 멤버 | 조직 멤버 | 상담에 종속 |
| `contracts` | 조직 멤버 | 조직 멤버 | 계약 및 입금 정보 |
| `listing_advertisements` | 조직 멤버 | 조직 멤버 | 채널별 광고 상태 |
| `task_completions` | 조직 멤버 | 조직 멤버 | 업무 완료 체크 상태 |

### 5.3 구현 시 주의점

- 각 정책은 `organization_id`를 직접 비교하는 방식으로 작성한다.
- 조직 멤버 여부는 별도의 안전한 헬퍼 함수로 판정한다. 이 함수는 현재 JWT의 Clerk 사용자 ID와 `organization_members`의 활성 멤버십을 비교한다.
- RLS 내부에서 멤버십 테이블을 다시 조회할 때 생길 수 있는 정책 순환을 피하도록, 헬퍼 함수·권한·검색 경로를 명시적으로 설정하고 검토한다.
- `WITH CHECK` 정책을 반드시 둬서, 수정 또는 추가 시 다른 조직 ID로 바꿔 넣는 우회를 막는다.
- 조인으로 연결된 하위 테이블도 부모 ID만 믿지 않고 자체 `organization_id` 정책을 적용한다.

## 6. 민감 정보 처리

RLS는 **행 단위** 접근 제어다. 같은 조직의 멤버에게 특정 열만 자동으로 가려 주지는 않는다. 따라서 민감 정보는 다음처럼 별도로 제한한다.

| 정보 | 저장 위치 | 목록 화면 | 상세 화면 | 서버/API 원칙 |
| --- | --- | --- | --- | --- |
| 건물주 연락처·입금계좌 | `buildings` | 표시하지 않음 | 필요한 업무자만 표시 | 필요한 열만 명시적으로 조회 |
| 임차인 연락처·상담 메모 | `consultations` | 연락처 마스킹 또는 미표시 | 상담 상세에서 표시 | `select('*')` 금지 |
| 계약금·잔금·정산 정보 | `contracts` | 요약값만 | 계약 상세에서 표시 | 로그에 원문 값 기록 금지 |
| 출입·보안 관련 정보 | 별도 필드 또는 별도 테이블 | 표시하지 않음 | 업무상 필요한 경우만 | URL·오류 메시지에 포함 금지 |

1차 운영은 동일 사무실의 `admin`과 `staff`가 실무상 공동 관리하는 전제로 설계한다. 이후 역할별로 민감 정보 노출을 더 세분화해야 하면, 민감 정보를 별도 테이블로 분리하고 해당 테이블에 더 엄격한 정책을 추가한다.

## 7. 사진과 파일(Storage) 정책

사진 기능을 추가할 때는 Supabase Storage 버킷을 `public`으로 만들지 않는다.

| 항목 | 기준 |
| --- | --- |
| 버킷 | 비공개(private) `listing-photos` |
| 경로 | `{organization_id}/{listing_id}/{file_id}.{ext}` |
| 파일 조회 | 조직 멤버가 짧은 수명의 signed URL을 요청해 조회 |
| 파일 추가 | 서버가 로그인·조직·매물 소속을 확인한 뒤 허용 |
| 파일 삭제 | 조직 멤버만, 연결된 매물의 조직 일치 확인 |
| 금지 | 공개 URL, 사용자 입력을 그대로 경로로 사용, 다른 조직 경로 접근 |

Storage의 `storage.objects`에도 별도의 RLS 정책이 필요하다. DB 테이블 정책만으로 파일 접근까지 보호되지는 않는다.

## 8. 환경별 키와 서버 접근 원칙

| 값 | 사용 위치 | 규칙 |
| --- | --- | --- |
| Clerk Publishable Key | 브라우저/Next.js | 공개 가능 환경 변수 |
| Clerk Secret Key | Next.js 서버만 | 브라우저 노출 금지 |
| Supabase URL | 브라우저/Next.js | 공개 가능 환경 변수 |
| Supabase Publishable/Anon Key | 브라우저/Next.js | RLS가 최종 제한하도록 사용 |
| Supabase Secret 또는 legacy `service_role` Key | 서버의 제한된 관리 작업만 | 일반 화면 CRUD에 사용 금지, 브라우저 노출 절대 금지 |

서버 액션·Route Handler는 매 요청마다 Clerk 로그인, 멤버 상태, 역할, 입력값을 먼저 확인한다. 일반 업무 쿼리는 사용자의 인증 문맥으로 Supabase RLS를 통과해야 한다. RLS를 우회하는 비밀 키는 마이그레이션, 제한된 운영자 관리 작업, 긴급 복구처럼 명확히 분리된 서버 작업에만 사용한다.

## 9. 전환 절차

### 단계 0 — 개발 규칙 고정

- Dev·Preview에 실제 업무 데이터가 없는지 확인한다.
- 모든 업무 테이블에 `organization_id`, 생성·수정 시각, 생성·수정 사용자 필드가 있는지 확인한다.
- 화면과 API가 조직 ID를 URL 또는 폼 입력에서 임의로 받지 않는지 확인한다.
- 현재 DB 스키마와 테스트 데이터를 백업한다.

### 단계 1 — 운영 환경을 새로 준비

- Clerk Production 인스턴스와 Supabase Production 프로젝트를 Dev와 분리해 만든다.
- Vercel Production 환경 변수에 운영용 키만 등록한다.
- Dev/Preview/Production의 URL, 키, 데이터베이스가 섞이지 않았는지 확인한다.

### 단계 2 — Clerk–Supabase Native Integration 연결

- Clerk와 Supabase 대시보드에서 공식 Native Integration을 연결한다.
- 테스트 사용자가 로그인한 상태에서 Supabase 요청 JWT에 Clerk 사용자 식별자(`sub`)와 인증된 역할 정보가 전달되는지 확인한다.
- 구형 JWT Template 또는 수동 토큰 구성에 의존하는 코드는 새 구현에 넣지 않는다.

### 단계 3 — 조직과 멤버십을 준비

- 운영 조직 레코드를 생성한다.
- 첫 관리자에게 Clerk 사용자 ID를 연결한 `organization_members` 레코드를 만든다.
- 초대된 staff도 활성 멤버로 등록한다.
- 멤버십이 없는 사용자와 `inactive` 사용자는 데이터 접근이 불가한지 먼저 확인한다.

### 단계 4 — RLS와 정책을 테이블별 적용

안전하게 검증할 수 있도록 다음 순서로 적용한다.

1. `organization_members`, `organizations`
2. `buildings`, `units`, `listings`
3. `consultations`, `consultation_followups`
4. `contracts`, `listing_advertisements`, `task_completions`
5. 사진 버킷과 `storage.objects` 정책

각 묶음마다 RLS를 활성화하고 `SELECT`, `INSERT`, `UPDATE`, `DELETE`와 `WITH CHECK`를 모두 테스트한 후 다음 묶음으로 진행한다.

### 단계 5 — 애플리케이션 전환

- Next.js 서버 쿼리를 사용자 인증 문맥 기반으로 바꾼다.
- 목록 API의 `select('*')`를 필요한 열의 명시적 조회로 교체한다.
- 페이지, 서버 액션, Route Handler에서 멤버십·역할·입력 검증을 일관되게 적용한다.
- 개발용 우회 코드, 샘플 계정 자동 로그인, 테스트 키를 제거한다.

### 단계 6 — 실제 데이터 이관 및 운영 시작

- 모든 보안 테스트가 통과한 Production에만 실제 데이터를 이관한다.
- 처음에는 관리자 계정과 소수의 staff 계정으로 제한 운영한다.
- 배포 후 접근 오류, 권한 거부, 서버 오류 로그를 확인한다.
- 운영 데이터가 Preview 또는 Dev에 복제되지 않도록 유지한다.

## 10. 전환 완료 테스트

아래 항목을 모두 통과해야 실제 데이터를 넣을 수 있다.

| 번호 | 검증 | 기대 결과 |
| --- | --- | --- |
| S-01 | 로그인하지 않고 데이터 조회 | 거부되거나 빈 결과 |
| S-02 | 활성 멤버가 자기 조직 매물 조회 | 허용 |
| S-03 | 사용자 A가 사용자 B의 조직 ID로 직접 조회 | 거부되거나 빈 결과 |
| S-04 | 사용자 A가 다른 조직 ID로 INSERT/UPDATE 시도 | 거부 |
| S-05 | inactive 멤버 로그인 후 데이터 조회 | 거부되거나 빈 결과 |
| S-06 | staff가 사용자 관리 기능 접근 | 거부 |
| S-07 | admin이 동일 조직 staff를 초대·비활성화 | 허용 |
| S-08 | 목록 API 응답에 연락처·계좌·보안 정보 포함 여부 | 포함되지 않음 |
| S-09 | 다른 조직의 사진 경로 또는 URL 접근 | 거부 |
| S-10 | 브라우저 빌드 결과에 비밀 키 존재 여부 | 존재하지 않음 |
| S-11 | 서버 요청의 임의 `organization_id` 변경 | 서버가 무시하거나 거부 |
| S-12 | 일반 CRUD가 비밀 키에 의존하는지 | 의존하지 않음 |

---

## 11. 장애 대응과 롤백 원칙

| 상황 | 즉시 조치 | 금지 조치 |
| --- | --- | --- |
| 특정 사용자가 접근하지 못함 | 멤버십 상태, Clerk ID 연결, 해당 RLS 정책을 확인 | Production 전체 RLS 비활성화 |
| 특정 화면이 빈 목록을 표시 | 서버 쿼리의 인증 문맥과 조직 조건을 점검 | 비밀 키로 일반 조회 우회 |
| 잘못된 정책 배포 | 직전 검증된 정책 마이그레이션으로 되돌리고 제한 운영 | 정책을 모두 삭제한 채 운영 |
| 키 노출 의심 | 즉시 키 폐기·재발급, Vercel 환경 변수 교체, 접근 로그 점검 | 노출된 키를 계속 사용 |

운영 전에는 데이터베이스 백업과 정책 마이그레이션 파일을 보관한다. 긴급 상황에서도 ‘RLS 전체 해제’가 아닌, 영향을 받은 기능을 일시 중지하고 검증된 정책으로 복원하는 방식을 사용한다.

## 12. 완료 기준

- [ ] Dev / Preview / Production의 Clerk·Supabase 프로젝트가 분리되어 있다.
- [ ] Production Supabase의 모든 업무 테이블과 Storage 객체에 RLS가 활성화되어 있다.
- [ ] `organization_id` 기준의 조회·추가·수정·삭제 정책이 검증되었다.
- [ ] 활성 멤버가 아닌 사용자는 어떠한 업무 데이터도 접근할 수 없다.
- [ ] 일반 매물관리 요청이 Supabase 비밀 키를 사용하지 않는다.
- [ ] 민감 정보가 목록 API와 브라우저 로그에 노출되지 않는다.
- [ ] 다른 조직 데이터와 사진 파일에 대한 교차 접근 테스트가 실패한다.
- [ ] 실제 데이터는 모든 완료 기준 통과 후 Production에만 이관한다.
