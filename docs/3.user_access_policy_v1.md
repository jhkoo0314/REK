# 부동산 매물관리 웹서비스 — 사용자 접근·권한 정책서 v1.0

> 작성일: 2026-08-14  
> 상태: 웹서비스 1차 기준 확정안  
> 기준 문서: `web_service_prd_v1.md`, `development_environment_plan.md`

---

## 1. 문서 목적

이 문서는 Clerk 로그인 사용자가 웹서비스의 어떤 화면과 데이터를 볼 수 있고, 어떤 행동을 할 수 있는지를 정한다.

현재 서비스에는 매물 조건뿐 아니라 임대인·세입자·상담 고객 연락처, 출입 비밀번호, 내부 메모가 들어갈 수 있다. 따라서 로그인은 편의 기능이 아니라 **사무실 내부정보의 출입문**이다.

이 문서의 목적은 두 가지다.

1. 개발 중에는 로그인 흐름을 단순하게 구현한다.
2. 실제 운영 전에는 사용자·조직·데이터 접근을 명확한 기준으로 잠근다.

## 2. 적용 범위와 기본 원칙

### 2.1 적용 범위

- Clerk 로그인·로그아웃·세션
- 업무 화면 접근 제어
- 관리자와 직원의 최소 역할 구분
- 사무실 조직과 사용자 연결
- Supabase 운영 RLS의 권한 기준
- 사용자 초대·비활성화·담당자 변경

### 2.2 이번 버전에서 하지 않는 것

- 고객 회원가입
- 임대인·세입자 전용 계정
- 외부 중개사 계정
- 공개 매물 열람 계정
- 사용자별 세밀한 메뉴 권한 조합
- 복잡한 승인·결재 절차
- 다수 사무실을 관리하기 위한 조직 선택 화면

### 2.3 기본 원칙

1. 로그인하지 않은 사용자는 업무 화면과 API에 접근할 수 없다.
2. 사용자는 자신이 연결된 사무실 조직의 데이터만 본다.
3. 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않는다. 운영 단계에서는 서버와 Supabase RLS가 함께 막아야 한다.
4. 비밀번호·연락처·내부 메모는 기본 목록보다 더 제한적으로 보여준다.
5. 실제 사용자 계정은 관리자만 추가·초대·비활성화한다.
6. 직원 퇴사·기기 교체 시에는 먼저 접근을 끊고, 업무 데이터는 삭제하지 않는다.

## 3. 사용자와 역할 정의

### 3.1 1차 역할

| 역할 | 의미 | 사용자 수 기준 |
|---|---|---|
| 관리자 (`admin`) | 사무실 운영 책임자. 사용자와 조직 설정을 관리 | 최소 1명, 가능하면 2명 |
| 직원 (`staff`) | 일상 매물·상담·계약·광고 업무를 처리 | 사무실 실제 업무 인원 |

1차에는 `읽기 전용`, `외부 협력자`, `회계`, `지점 관리자` 역할을 만들지 않는다.

### 3.2 역할별 권한

| 기능 | 관리자 | 직원 | 비고 |
|---|:---:|:---:|---|
| 로그인·로그아웃 | 가능 | 가능 | Clerk 제공 기능 사용 |
| 매물 조회·등록·수정·종료 | 가능 | 가능 | 현재 업무의 핵심 |
| 건물·호실 고정정보 수정 | 가능 | 가능 | 저장 전 영향 범위 안내 |
| 상담 등록·수정·종료 | 가능 | 가능 | 고객 연락처는 상담 업무 범위에서만 노출 |
| 계약 등록·수정·삭제 | 가능 | 가능 | 삭제는 명시적 확인 필요 |
| 광고 현황·광고문구 생성 | 가능 | 가능 | 광고문구는 DB 미저장 |
| 내부 업무용 Excel 내려받기 | 가능 | 가능 | 화면별 경고와 열 제외 규칙 적용 |
| 사용자 초대·비활성화 | 가능 | 불가 | 운영 단계에서 구현 |
| 조직 설정·보안 설정 | 가능 | 불가 | 운영 단계에서 구현 |
| 운영 데이터 전체 초기화 | 불가 | 불가 | 일반 서비스 기능으로 만들지 않음 |

관리자와 직원 모두 매물 업무는 처리할 수 있게 한다. 1차의 목적은 통제가 아니라 업무 처리이므로, 직원의 매물·상담·계약 기능을 불필요하게 제한하지 않는다.

## 4. 로그인 정책

### 4.1 1차 로그인 방식

| 항목 | 결정 |
|---|---|
| 인증 서비스 | Clerk |
| 개발 단계 | Clerk Development 인스턴스 |
| 운영 단계 | Clerk Production 인스턴스 |
| 가입 방식 | 공개 가입 없음 |
| 사용자 추가 | 관리자가 초대하거나 계정을 생성 |
| 로그인 수단 | 이메일 + 비밀번호를 기본으로 사용 |
| 비밀번호 재설정 | Clerk 기본 기능 사용 |
| 소셜 로그인 | 1차 제외 |
| 2단계 인증 | 1차 제외, 운영 안정화 후 검토 |

### 4.2 경로 접근 정책

| 경로 유형 | 비로그인 사용자 | 로그인 사용자 |
|---|---|---|
| 로그인 화면 | 접근 가능 | 이미 로그인했으면 서비스 첫 화면으로 이동 |
| 업무 화면 (`/app/*`) | 로그인 화면으로 이동 | 역할과 조직 확인 후 접근 |
| 로그인·오류 안내 화면 | 접근 가능 | 접근 가능 |
| 서버 API·Server Action | 요청 거부 | 사용자·조직 확인 후 실행 |
| 공개 매물 페이지 | 1차에 없음 | 해당 없음 |

로그인 성공 뒤의 기본 진입 화면은 `오늘 할 일`로 한다. 사용자가 그날 처리해야 할 우선 업무를 바로 보게 하기 위함이다.

### 4.3 로그인 실패·세션 종료 처리

| 상황 | 화면 처리 |
|---|---|
| 잘못된 로그인 정보 | Clerk의 오류 문구 표시, 업무 데이터는 보여주지 않음 |
| 세션 만료 | 로그인 화면으로 이동, 작성 중인 입력은 서버에 저장되지 않음 |
| 권한 없는 조직 접근 | `접근 권한이 없습니다` 안내 후 기본 화면 또는 로그인 화면으로 이동 |
| 비활성화된 사용자 | 접근 차단, 관리자에게 문의 안내 |

작성 중인 입력이 있는 상태에서 세션이 끝날 수 있으므로, 장시간 작성 화면에서는 저장 전 이탈 경고와 임시 입력 보존 방식을 이후 화면 명세에서 검토한다.

## 5. 조직과 사용자 연결 정책

### 5.1 조직을 데이터에 두는 이유

현재는 사무실 하나만 운영하지만, 데이터는 처음부터 조직 단위로 구분한다.

- 향후 본인 사무소 개업 또는 직원 추가에 대비
- 개발·운영 데이터뿐 아니라 사무실 간 데이터가 섞이는 위험 방지
- Supabase RLS 정책을 단순하고 명확하게 작성
- 사용자가 어떤 사무실의 데이터를 다루는지 설명 가능

### 5.2 1차 조직 정책

| 항목 | 기준 |
|---|---|
| 운영 조직 수 | 실제 운영은 1개 |
| 조직 생성 | 일반 사용자는 불가 |
| 조직 선택 UI | 1차 제외 |
| 사용자 소속 | 운영 1차에는 한 사용자당 한 조직 |
| 데이터 소속 | 모든 업무 테이블에 `organization_id` 저장 |
| 사용자 식별 | Clerk의 `user_id`를 내부 사용자 기록과 연결 |

### 5.3 필요한 사용자 데이터

운영 Supabase에는 Clerk의 계정 정보를 복제해 관리하지 않고, 업무 권한에 필요한 최소 정보만 둔다.

| 항목 | 예시 | 목적 |
|---|---|---|
| 내부 사용자 ID | UUID | 내부 관계 연결 |
| Clerk 사용자 ID | `user_...` | 로그인 사용자 확인 |
| 조직 ID | UUID | 데이터 범위 제한 |
| 역할 | `admin` / `staff` | 관리자 기능 구분 |
| 상태 | 활성 / 비활성 | 퇴사·권한 중지 처리 |
| 표시 이름 | 재현 | 화면의 작성자 표시 |
| 생성·수정 일시 | 자동 | 운영 확인 |

이 사용자 데이터의 상세 테이블 구조는 `supabase_data_model_v1.md`에서 확정한다.

## 6. 개발 단계의 접근 기준

개발 단계에서는 기능 검증을 우선하되, 실제 운영 수준의 보안처럼 보이도록 착각해서는 안 된다.

### 6.1 개발 중 구현할 것

- Clerk 로그인·로그아웃
- 업무 경로의 비로그인 접근 차단
- 현재 로그인 사용자 표시
- 테스트 계정 2개 이상으로 로그인 확인
- Server Action 또는 API에서 Clerk 사용자 존재 확인

### 6.2 개발 중 임시로 보류할 것

- 역할별 화면·버튼 차단
- 사용자 초대·비활성화 관리 화면
- 조직별 Supabase RLS
- 사용자별 생성·수정 이력의 상세 조회
- 운영 이메일·비밀번호 정책

### 6.3 개발 단계의 주의사항

개발 Supabase에서 RLS가 꺼져 있다면 Clerk 로그인은 “화면 입구”만 막는 수준이다. Supabase 데이터 자체의 접근 보안은 운영 전 RLS를 적용해야 완성된다.

따라서 개발 중에는 실제 연락처, 비밀번호, 계약 정보, 내부 메모를 절대 입력하지 않는다.

## 7. 운영 단계의 권한 적용 방식

운영에서는 아래 세 겹이 함께 작동해야 한다.

| 보호 단계 | 담당 | 역할 |
|---|---|---|
| 1. 로그인 확인 | Clerk | 로그인하지 않은 사용자의 서비스 진입 차단 |
| 2. 서버 권한 확인 | Next.js 서버 로직 | 사용자 상태·조직·역할을 확인한 뒤 요청 처리 |
| 3. 데이터 접근 제한 | Supabase RLS | 조직 밖 데이터와 권한 없는 행의 조회·수정·삭제 차단 |

### 7.1 운영 데이터 접근 기본 규칙

| 동작 | 운영 기준 |
|---|---|
| 조회 | 활성 사용자는 자기 조직 데이터만 조회 |
| 등록 | 서버가 현재 사용자의 조직 ID를 함께 기록 |
| 수정 | 자기 조직 데이터만 수정 |
| 삭제 | 자기 조직 데이터만, 명시적 확인을 거쳐 삭제 |
| Excel | 현재 사용자의 조직 데이터만 내보내기 |
| 파일 업로드 | 자기 조직의 매물 사진 경로만 사용 |

브라우저에서 들어온 `organization_id`를 그대로 신뢰하지 않는다. 서버는 로그인한 Clerk 사용자와 내부 사용자 기록을 기준으로 조직 ID를 결정한다.

### 7.2 역할별 운영 규칙

1차 운영에서는 관리자와 직원 모두 일상 업무 데이터를 처리할 수 있다. 관리자 전용은 사용자·조직·보안 설정으로 한정한다.

| 운영 기능 | 권한 기준 |
|---|---|
| 업무 데이터 조회·등록·수정 | 활성 관리자 또는 활성 직원 |
| 업무 데이터 삭제 | 활성 관리자 또는 활성 직원 + 확인 절차 |
| 사용자 초대 | 활성 관리자 |
| 사용자 비활성화 | 활성 관리자 |
| 조직 설정 변경 | 활성 관리자 |
| RLS·키·배포 설정 | 서비스 관리자만, 일반 앱 화면에서 제공하지 않음 |

## 8. 내부정보 접근 기준

### 8.1 정보 등급

| 등급 | 예시 | 기본 노출 원칙 |
|---|---|---|
| 일반 업무 정보 | 건물명, 호수, 가격, 입주 가능일, 상태 | 로그인 직원에게 표시 가능 |
| 제한 업무 정보 | 사진, 옵션, 관리비 메모, 계약 일정 | 필요한 업무 화면에 표시 |
| 민감 내부정보 | 비밀번호, 열쇠 위치, 연락처, 내부 메모 | 기본 목록에서 숨기고 필요한 상세 흐름에서만 표시 |

### 8.2 화면별 노출 기준

| 화면 | 비밀번호 | 연락처 | 내부 메모 |
|---|---:|---:|---:|
| 오늘 할 일 기본 표 | 숨김 | 숨김 | 숨김 |
| 매물 현황 기본 표 | 숨김 | 숨김 | 숨김 |
| 매물 등록·수정 | 필요한 경우 표시 | 매물 관계자만 표시 | 표시 가능 |
| 건물·호실 상세 | 필요한 경우 표시 | 기본 숨김 | 표시 가능 |
| 상담 조회·상세 | 숨김 | 팔로업 목적에 한해 표시 | 상담 내용 표시 가능 |
| 계약 조회·상세 | 숨김 | 상세에서만 표시 | 상세에서만 표시 |
| 광고문구 생성 | 입력·출력 금지 | 입력·출력 금지 | 입력·출력 금지 |

모든 사용자가 같은 사무실 직원이라는 이유만으로 기본 표에 민감정보를 계속 표시하지 않는다. 화면 목적에 맞게 최소 노출한다.

## 9. 사용자 생명주기 정책

### 9.1 사용자 추가

운영 시작 후 새 직원이 들어오면 아래 순서를 따른다.

1. 관리자가 Clerk에서 사용자 초대 또는 계정 생성
2. 사용자가 로그인과 비밀번호 설정 완료
3. 내부 사용자 기록에 Clerk 사용자 ID·조직·역할을 연결
4. 활성 상태인지 확인
5. 매물 조회와 테스트 등록을 함께 확인

초대만 하고 조직 연결을 하지 않은 사용자는 업무 데이터에 접근할 수 없어야 한다.

### 9.2 사용자 비활성화

퇴사·휴직·업무 제외 시에는 데이터를 삭제하지 않고 접근만 끊는다.

1. Clerk에서 계정 접근을 제한하거나 사용자 비활성화
2. 내부 사용자 기록을 `비활성`으로 변경
3. 해당 사용자의 활성 세션이 유지되지 않는지 확인
4. 작성한 매물·상담·계약 기록은 그대로 보존
5. 업무 인수인계 대상과 남은 일정 확인

### 9.3 담당자 변경

- 관리자 역할은 최소 2명이 확인 가능한 구조를 권장한다.
- 기존 관리자가 떠나기 전 새 관리자 계정을 먼저 활성화한다.
- Clerk, Supabase, Vercel, GitHub의 서비스 관리자 권한도 함께 이전한다.
- 기존 담당자의 개인 계정 하나에 서비스 소유권이 남지 않게 점검한다.

## 10. 감사·기록의 최소 기준

1차에는 복잡한 관리자 대시보드를 만들지 않는다. 다만 업무 데이터에는 다음 자동 기록을 남긴다.

| 기록 | 목적 |
|---|---|
| `created_at` | 언제 처음 등록됐는지 확인 |
| `updated_at` | 언제 마지막으로 바뀌었는지 확인 |
| `created_by_user_id` | 최초 등록자 확인 |
| `updated_by_user_id` | 마지막 수정자 확인 |
| 삭제·종료 일시와 사유 | 이력과 오류 대응 |

이 정보는 운영 문제가 생겼을 때 확인하기 위한 것이며, 직원 감시용 대시보드로 확장하지 않는다.

## 11. 테스트·수용 기준

### 개발 단계

- [ ] 비로그인 사용자가 `/app`과 하위 업무 화면을 열 수 없다.
- [ ] 개발 Clerk 계정 2개로 각각 로그인·로그아웃된다.
- [ ] 로그인 후 오늘 할 일 화면으로 이동한다.
- [ ] Clerk 사용자가 없는 요청은 서버 저장 기능이 실행되지 않는다.
- [ ] 개발 DB에는 가상 테스트 데이터만 있다.

### 운영 전환 단계

- [ ] 운영 Clerk 계정으로 로그인·로그아웃된다.
- [ ] 초대되지 않은 사용자는 가입하거나 데이터에 접근할 수 없다.
- [ ] 비활성화된 사용자는 다시 접속할 수 없다.
- [ ] 직원은 자기 조직의 매물·상담·계약만 조회·수정한다.
- [ ] 다른 조직 ID를 URL·요청값에 넣어도 데이터가 보이지 않는다.
- [ ] RLS가 직접 Supabase 요청에서도 조직 밖 데이터를 막는다.
- [ ] 사용자 추가·비활성화 뒤 기존 업무 기록은 유지된다.
- [ ] 기본 목록과 일반 Excel에 비밀번호·연락처·내부 메모가 노출되지 않는다.

## 12. 결정 기록과 다음 문서

### 이 문서에서 확정한 결정

1. 인증은 Clerk를 사용한다.
2. 1차는 관리자와 직원 두 역할만 사용한다.
3. 공개 가입은 만들지 않고 관리자 초대 방식으로 운영한다.
4. 현재는 사무실 하나만 운영하되, 모든 업무 데이터에는 조직 소속을 둔다.
5. 개발 단계에서는 로그인 보호를 먼저 구현하고, 역할·RLS는 운영 전환 게이트에서 완성한다.
6. 운영에서는 Clerk 로그인, Next.js 서버 확인, Supabase RLS를 함께 적용한다.

### 다음 문서로 넘길 사항

`supabase_data_model_v1.md`에서는 다음을 구체적으로 설계한다.

- `organizations`, `users` 또는 `organization_members` 테이블 구조
- Clerk 사용자 ID와 내부 사용자 ID 연결
- 모든 업무 테이블의 `organization_id` 관계
- 생성자·수정자 자동 기록
- 개발 seed 데이터의 사용자·조직 예시

## 13. 확정 결론

> 1차는 사무실 직원이 쉽게 쓰는 업무 서비스여야 한다. 그래서 역할은 관리자·직원 두 개로 최소화한다. 그러나 실제 데이터는 조직 단위로 분리하고, 운영 전에는 로그인·서버·RLS 세 단계로 접근을 제한한다.
