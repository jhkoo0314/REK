# 부동산 매물관리 웹서비스 — 프로젝트 빌드 작업표

> 작성일: 2026-08-14  
> 상태: 구현 시작 전 기준 작업표  
> 대상: 배방우리부동산 원룸·투룸 중심 내부 임대 중개 업무 웹서비스  
> 사용 방법: 위에서 아래 순서대로 진행한다. 각 작업의 완료 기준을 통과하기 전에는 다음 큰 단계로 넘어가지 않는다.

---

## 1. 이 프로젝트가 만드는 것

이 프로젝트는 고객에게 공개하는 부동산 포털이 아니다. 사무실의 `admin`(관리자)과 `staff`(직원)가 로그인해 매물, 상담, 계약, 광고 현황, 오늘 할 일을 한 흐름으로 처리하는 내부 업무 웹서비스다.

완성 후의 기본 흐름은 아래와 같다.

```text
로그인
→ 대시보드에서 오늘·지연 업무 확인
→ 신규 매물 등록 또는 기존 매물 수정
→ 필요 시 상담·계약·광고 업무 연결
→ 저장된 일정과 상태를 기준으로 오늘 할 일 다시 계산
→ 대시보드에서 다음 처리 대상 확인
```

### 반드시 유지할 업무 규칙

- 매물 구조는 `건물 → 호실 → 매물`이다.
- 가격·상태·입주 가능일의 일반 변경은 기존 현재 매물을 수정한다. 새 매물을 자동으로 만들지 않는다.
- 상담·계약·광고는 매물에 연결되지만, 매물 수정으로 자동 삭제하거나 새로 만들지 않는다.
- 계약 완료·취소 시 매물 상태 변경은 사용자에게 확인받은 후에만 적용한다.
- 광고 문구 생성은 복사할 문구만 만들며, 매물·광고 상태를 자동으로 바꾸지 않는다.
- 연결 기록이 있는 매물은 삭제보다 상태 변경 또는 비활성화를 먼저 안내한다.
- 연락처·계좌·출입 정보·내부 메모는 기본 목록에 표시하지 않는다.
- 기존 Streamlit SQLite 데이터는 웹 DB로 이관하지 않는다. 웹서비스 운영 시작일부터 새로 등록한다.

## 2. 작업 전 공통 원칙

### 데이터와 보안

- Local과 Preview에는 완전히 가공한 테스트 데이터만 사용한다.
- 실제 고객명, 연락처, 계약금, 계좌, 출입 비밀번호, 열쇠 위치, 매물 사진을 개발 환경에 넣지 않는다.
- Production은 Clerk Production, Supabase Production, Vercel Production을 Dev/Preview와 분리한 뒤에만 연다.
- Production에서 실제 데이터를 다루기 전에는 Supabase RLS(조직별 데이터 잠금)를 활성화하고 조직 분리 테스트를 통과한다.
- 브라우저나 Git 저장소에 Clerk Secret Key, Supabase Secret/service-role Key를 넣지 않는다.
- 일반 매물·상담·계약 저장에는 RLS를 우회하는 비밀 키를 사용하지 않는다.

### 구현과 디자인

- 실제 코드, 데이터베이스, 로그인, 보안, 배포는 Codex가 구현한다.
- Gemini 디자인 시안은 사용자 승인 후에만 실제 화면에 반영한다.
- 화면은 표·검색·폼 중심의 정돈된 업무용 서비스로 만든다.
- 데스크톱을 우선하되, 휴대폰에서 대시보드·검색·상세 확인·간단 수정은 가능해야 한다.
- 로딩, 빈 화면, 오류, 저장 중, 접근 불가, 삭제 확인도 기능의 일부로 구현한다.

### 완료 판단 공통 기준

각 기능은 코드 작성만으로 완료가 아니다. 아래를 모두 확인한다.

- 정상 입력과 잘못된 입력에서 결과가 이해하기 쉽게 표시되는가
- admin과 staff의 권한이 맞는가
- 다른 조직 데이터가 보이거나 수정되지 않는가
- 목록·상세·대시보드 등 연결된 화면이 함께 갱신되는가
- 데스크톱과 필요한 모바일 흐름에서 사용 가능한가
- 린트, 타입 검사, 빌드, 관련 테스트가 통과하는가

## 4. 단계 0 — 프로젝트 기반과 개발 환경

### 목적

안전하게 개발할 빈 웹서비스와 테스트 환경을 만든다. 이 단계에서는 실제 부동산 업무 데이터를 입력하지 않는다.

### 작업 목록

- [ ] Next.js 16 App Router + TypeScript 5.x 프로젝트를 만든다.
- [ ] Tailwind CSS와 shadcn/ui를 설정한다.
- [ ] 기본 폴더를 만든다.
  - `app/`: URL별 화면
  - `app/(app)/`: 로그인 후 업무 화면
  - `components/ui/`: 기본 UI 부품
  - `components/shared/`: 사이드바·헤더·상태 배지 등
  - `features/listings/`, `features/consultations/`, `features/contracts/`, `features/advertisements/`, `features/tasks/`, `features/members/`
  - `lib/`: 로그인·DB·권한·날짜·금액 공통 함수
  - `types/`: DB와 화면 타입
  - `supabase/migrations/`: DB 구조 변경 파일
- [ ] ESLint, 타입 검사, 테스트, 빌드 명령을 준비한다.
- [ ] `.env.local`을 Git 추적에서 제외한다.
- [ ] Clerk Development 인스턴스와 Supabase Dev 프로젝트를 만든다.
- [ ] Vercel 프로젝트와 Git 저장소를 연결하고 Preview 배포를 확인한다.
- [ ] Local/Preview/Production 환경변수 이름과 값을 분리한다.
- [ ] README에 테스트 데이터 원칙과 실행 방법이 맞게 적혀 있는지 확인한다.

### 필요한 환경변수

| 이름 | 쓰는 곳 | 주의사항 |
|---|---|---|
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | 브라우저·서버 | 공개 가능 값만 |
| `CLERK_SECRET_KEY` | 서버 | 브라우저·Git 노출 금지 |
| `NEXT_PUBLIC_SUPABASE_URL` | 브라우저·서버 | 환경별 프로젝트 주소 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 브라우저·서버 | RLS가 최종 접근 제한 |
| `SUPABASE_SECRET_KEY` | 제한된 운영 서버 작업 | 일반 CRUD에 사용 금지 |
| `APP_ENV` | 화면·로그 구분 | local / preview / production |

### 완료 기준

- [ ] 로컬에서 기본 웹 화면이 열린다.
- [ ] Preview 주소가 생성되고 휴대폰과 PC에서 열 수 있다.
- [ ] Preview가 운영 Clerk 또는 운영 Supabase를 가리키지 않는다.
- [ ] 비밀 환경변수 파일이 Git에 포함되지 않는다.
- [ ] 실제 데이터가 어떤 개발 DB나 Preview에도 없다.

### 이번 단계에서 하지 않는 일

- 실제 로그인 계정 운영
- 운영 DB·운영 RLS 설정
- 실제 매물 등록
- 사진 업로드, Excel 내보내기, 자동화

## 5. 단계 1 — 로그인과 공통 앱 화면

### 목적

로그인한 사용자만 업무 화면으로 들어오게 하고, 모든 업무가 같은 화면 구조에서 열리도록 만든다.

### 화면 작업

- [ ] Clerk 로그인·로그아웃을 연결한다.
- [ ] 미로그인 사용자가 업무 주소에 직접 들어오면 로그인 화면으로 보낸다.
- [ ] 로그인 성공 후 기본 화면을 `/dashboard`로 정한다.
- [ ] 데스크톱 좌측 메뉴를 만든다.
  - 대시보드
  - 매물 관리
  - 상담 관리
  - 계약 관리
  - 광고 현황
  - 사용자 관리(admin만)
- [ ] 상단 헤더에 화면 제목, 설명, 로그인 사용자 메뉴를 표시한다.
- [ ] 모바일 메뉴와 기본 반응형 구조를 만든다.
- [ ] 상태 배지, 빈 화면, 오류 안내, 로딩 Skeleton, Toast, 확인 Dialog를 공통 부품으로 만든다.
- [ ] 대시보드에는 우선 빈 구조를 만들고, 실제 업무 데이터는 단계 4에서 연결한다.

### 권한 작업

- [ ] 로그인한 Clerk 사용자를 서버에서 확인한다.
- [ ] `organization_members`의 활성 멤버인지 확인하는 공통 함수를 준비한다.
- [ ] admin은 사용자 관리 메뉴를 볼 수 있고 staff는 볼 수 없게 한다.
- [ ] 멤버십이 없거나 비활성 상태면 “관리자에게 계정 확인을 요청해 주세요” 안내를 보인다.

### 완료 기준

- [ ] 미로그인 사용자는 `/dashboard`, `/listings` 등 업무 화면을 볼 수 없다.
- [ ] 활성 admin 테스트 계정은 대시보드와 사용자 관리 메뉴를 볼 수 있다.
- [ ] 활성 staff 테스트 계정은 일반 업무 메뉴만 볼 수 있다.
- [ ] 멤버십이 없는 테스트 계정과 inactive 계정은 업무 데이터에 접근할 수 없다.
- [ ] PC와 휴대폰에서 메뉴·헤더·기본 화면이 깨지지 않는다.

## 6. 단계 2 — Dev 데이터베이스와 매물 기본 구조

### 목적

매물 업무의 기준인 `건물 → 호실 → 매물` 구조와 조직·사용자 연결을 Supabase Dev에 만든다.

### Migration 작업

- [ ] `organizations` 테이블 생성
- [ ] `organization_members` 테이블 생성
- [ ] `buildings` 테이블 생성
- [ ] `units` 테이블 생성
- [ ] `listings` 테이블 생성
- [ ] 생성·수정 시각과 작성·수정 사용자 필드를 주요 테이블에 넣는다.
- [ ] 모든 업무 테이블에 `organization_id`를 넣는다.
- [ ] 조직별 건물 중복 방지 규칙을 만든다.
- [ ] 같은 건물에서 `302`와 `302호`를 같은 호실로 판단하도록 호실 번호 정규화 규칙을 만든다.
- [ ] 한 호실에 현재 매물(`is_current = true`)이 최대 한 건만 생기도록 DB 제약을 만든다.
- [ ] 금액 음수 금지, 날짜 규칙, 상태값 기본 검증을 DB와 서버 검증에 나눠 적용한다.

### 개발용 가상 데이터

- [ ] 테스트 조직 A와 조직 B를 만든다.
- [ ] admin-A, staff-A, inactive-A, staff-B, no-member 테스트 계정을 준비한다.
- [ ] 가상 건물 3개 이상, 호실, 매물 15개 이상을 만든다.
- [ ] 공실·입주 가능 예정·계약 진행·계약 완료·보류 상태를 섞는다.
- [ ] 가상 연락처는 `010-0000-0000` 같은 값만 사용한다.

### 완료 기준

- [ ] 빈 Supabase Dev 프로젝트에 migration을 순서대로 적용해 같은 구조를 다시 만들 수 있다.
- [ ] 조직 A 사용자가 조직 B의 건물·호실·매물을 후보나 목록에서 보지 않는다.
- [ ] 기존 매물의 가격·상태·입주일을 바꿔도 새 매물 행이 생기지 않는다.
- [ ] 같은 호실에 현재 매물을 중복 저장할 수 없다.
- [ ] DB 타입과 화면에서 쓰는 TypeScript 타입이 일치한다.

## 7. 단계 3 — 매물 관리 P0 완성

### 목적

사무실에서 가장 자주 하는 매물 등록·검색·수정 업무를 웹에서 빠르고 안전하게 처리한다.

### 3-1. 매물 목록

- [ ] `/listings` 화면을 만든다.
- [ ] 기본 표에 상태, 건물·호실, 유형, 보증금/월세, 관리비, 입주 가능일, 광고 요약, 최근 수정 정보를 표시한다.
- [ ] 연락처, 계좌, 출입 정보, 내부 메모는 목록에서 제외한다.
- [ ] 건물명·주소·호실·매물 번호로 검색한다.
- [ ] 상태, 방 유형, 거래 유형, 가격대, 입주 가능일, 광고 상태 필터를 제공한다.
- [ ] 적용한 필터를 칩으로 보여 주고 개별 해제·전체 초기화를 지원한다.
- [ ] 결과가 없을 때 신규 매물 등록 또는 필터 초기화를 안내한다.
- [ ] 목록에서 상세로 갔다가 돌아와도 검색·필터·스크롤 위치를 유지한다.
- [ ] 모바일에서는 상태·가격·입주 가능일 중심의 카드 목록으로 바꾼다.

### 3-2. 신규 매물 등록

- [ ] `/listings/new`에 한 화면 3단계 등록 폼을 만든다.
  1. 건물 검색 또는 새 건물 등록
  2. 호실 선택 또는 새 호실 등록
  3. 매물 조건 입력
- [ ] 기존 건물 후보에는 주소와 호실 수를 함께 보여 준다.
- [ ] 기존 호실 후보에는 현재 매물 상태·가격·최근 수정일을 함께 보여 준다.
- [ ] 같은 호실에 현재 매물이 있으면 저장 대신 기존 매물 열기를 우선 제안한다.
- [ ] 금액은 숫자 입력과 만원 단위 보조 표시를 제공한다.
- [ ] 입주 가능일이 날짜 지정이면 날짜 입력을 필수로 한다.
- [ ] 취소·이탈 시 입력 내용이 사라질 수 있음을 확인받는다.
- [ ] 성공하면 새 매물 상세로 이동한다.

### 3-3. 매물 상세와 수정

- [ ] `/listings/[listingId]` 상세 화면을 만든다.
- [ ] 기본 정보, 상담, 계약, 광고, 활동 탭을 만든다. 아직 구현하지 않은 탭은 준비 중 안내를 표시한다.
- [ ] 기본 정보에 임대 조건, 입주·상태, 공간 정보, 건물·호실, 관리 정보, 민감 정보를 구분해 표시한다.
- [ ] 민감 정보는 기본 접힘 상태로 둔다.
- [ ] 전체 수정 화면에서 가격·관리비·상태·입주일·옵션·메모를 수정한다.
- [ ] 목록의 빠른 수정은 보증금·월세·관리비·상태·입주 가능일로만 제한한다.
- [ ] 상태를 계약 완료 또는 보류로 바꾸면 광고 확인 안내를 표시한다.
- [ ] 연결된 상담·계약이 있는 매물을 삭제하려 하면 삭제 영향과 상태 변경 대안을 먼저 안내한다.

### P0 테스트와 완료 기준

- [ ] 기존 건물에 새 호실과 매물을 등록해도 건물이 중복 생성되지 않는다.
- [ ] 새 건물→새 호실→새 매물이 올바르게 연결된다.
- [ ] 건물명 일부, 주소 일부, 호실, 매물 번호 검색이 동작한다.
- [ ] 상태·유형·가격대 필터를 함께 적용해 정확한 결과만 표시한다.
- [ ] 목록 빠른 수정과 상세 값이 즉시 일치한다.
- [ ] 가격·상태·입주일 수정은 기존 매물 행을 수정한다.
- [ ] 잘못된 금액·날짜·필수값은 저장되지 않고 입력칸 가까이에 한글로 안내된다.
- [ ] 저장 실패 시 기존 값과 사용자의 입력을 임의로 지우지 않는다.
- [ ] 가공 매물 10건 이상으로 PC와 휴대폰에서 전체 흐름을 확인한다.

P0가 모두 통과될 때까지 단계 4 이후 기능을 앞당겨 만들지 않는다.

## 8. 단계 4 — 대시보드와 오늘 할 일 P1

### 목적

매물·상담·계약의 날짜와 상태를 “오늘 해야 할 행동”으로 바꿔 업무 누락을 줄인다.

### 작업 목록

- [ ] 대시보드 상단에 날짜와 `+ 신규 매물 등록` 버튼을 둔다.
- [ ] 지연 업무를 오늘 업무보다 먼저 보여 준다.
- [ ] 오늘 업무를 입주, 퇴실·공실 확인, 상담 연락, 계약 일정으로 나눈다.
- [ ] 공실, 입주 가능 예정, 계약 진행, 광고 수정 필요 현황을 카드로 표시한다.
- [ ] 각 숫자나 업무 항목을 누르면 해당 매물·상담·계약 상세 또는 필터된 목록으로 이동한다.
- [ ] `task_completions` 테이블과 완료 체크 동작을 만든다.
- [ ] 업무 완료 체크는 원본 매물·상담·계약의 상태를 자동으로 바꾸지 않게 한다.
- [ ] 원본 날짜가 바뀌면 새 날짜의 업무는 다시 미완료로 보이게 한다.

### 완료 기준

- [ ] 오늘 입주·퇴실·상담 연락·계약 일정이 유형별로 표시된다.
- [ ] 지연된 업무가 먼저 보인다.
- [ ] 완료 체크 후 원본 데이터가 바뀌지 않는다.
- [ ] 상담의 다음 연락일을 바꾸면 이전 업무가 정리되고 새 날짜에 반영된다.
- [ ] 현황 카드를 누르면 올바른 필터 목록으로 이동한다.

## 9. 단계 5 — 상담 관리 P1

### 목적

문의 고객의 조건과 후속 연락을 기록해 방문·계약 연결을 놓치지 않는다.

### DB와 기능 작업

- [ ] `consultations`, `consultation_followups` migration을 만든다.
- [ ] 일반 상담(매물 없이 시작)과 매물 상담(특정 매물 연결)을 모두 지원한다.
- [ ] `/consultations` 목록을 만든다.
- [ ] 고객 이름 또는 내부 식별명, 상태, 희망 조건 요약, 연결 매물, 다음 연락일, 최근 활동을 표시한다.
- [ ] 목록에서 연락처는 마스킹하거나 표시하지 않는다.
- [ ] 상담 등록 폼에 고객 식별명, 문의 채널, 희망 조건, 문의일, 메모, 선택 매물을 둔다.
- [ ] 상담 상세에서 전화·문자·방문·매물 제안 이력을 누적한다.
- [ ] 이력 저장 시 결과 상태와 다음 연락일을 함께 지정할 수 있게 한다.
- [ ] 종료 또는 계약 완료 상담은 다음 연락일을 비우고 일반 후속 목록에서 제외한다.
- [ ] 매물 상세의 상담 탭에서 새 상담을 시작하면 해당 매물을 자동 연결한다.

### 완료 기준

- [ ] 일반 상담을 매물 없이 만들고 나중에 매물을 연결할 수 있다.
- [ ] 통화·문자·방문 이력이 최초 상담 내용을 덮어쓰지 않고 쌓인다.
- [ ] 다음 연락일이 오늘이면 대시보드에 표시된다.
- [ ] 종료 사유를 남기고 상담을 종료할 수 있다.
- [ ] 민감한 고객 연락처와 긴 상담 메모가 기본 목록에 노출되지 않는다.

## 10. 단계 6 — 계약 관리 P1

### 목적

계약 조건과 일정, 금액 확인을 매물·상담과 연결하고 광고 종료 같은 후속 행동을 놓치지 않는다.

### DB와 기능 작업

- [ ] `contracts` migration을 만든다.
- [ ] 계약은 반드시 매물 회차에 연결되도록 검증한다.
- [ ] 상담 연결은 선택 사항으로 둔다.
- [ ] `/contracts` 목록에 연결 매물, 고객 식별명, 계약 상태, 계약일·입주일·잔금일, 입금 확인 상태를 표시한다.
- [ ] 계약 등록·수정 폼에 계약 종류, 중개 방식, 상태, 일정, 보증금·가계약금·잔금, 내부 메모를 둔다.
- [ ] 계약일, 추가 계약금일, 잔금일이 계약 진행 시작일보다 빠르지 않게 검증한다.
- [ ] 가계약금 수령액이 계약금 전체보다 크지 않게 검증한다.
- [ ] 계약 완료·취소 Dialog에서 매물 상태 변경 여부를 사용자가 선택한다.
- [ ] 기본 선택값은 `매물 상태는 변경하지 않음`으로 둔다.
- [ ] 계약 완료 매물에 게시 중 광고가 있으면 광고 종료 확인 업무를 보인다.

### 완료 기준

- [ ] 매물에서 계약을 시작하면 매물이 자동 연결된다.
- [ ] 계약 완료 후 매물 상태를 바꾸지 않음을 선택하면 계약만 완료된다.
- [ ] 계약 취소 때 사유를 남길 수 있다.
- [ ] 잔금일이나 계약 일정이 오늘이면 대시보드에 표시된다.
- [ ] 계약 목록의 상태·일정·입금 미확인 필터가 정확히 동작한다.

## 11. 단계 7 — 광고 현황과 문구 생성 P1

### 목적

외부 광고 사이트에 자동 등록하지 않으면서도, 채널별 광고 상태와 반복 문구 작성을 쉽게 관리한다.

- [ ] 채널은 당근·네이버·직방과 직접 입력을 지원한다.
- [ ] 광고 상태를 등록 예정, 게시 중, 수정 필요, 중지, 종료로 관리한다.

- [ ] 제목 후보와 본문을 만들어 수정·복사할 수 있게 한다.
- [ ] 사용자가 외부 채널에 직접 붙여넣어 등록하고, 필요할 때 광고 상태를 직접 변경하게 한다.

### 완료 기준

- [ ] 게시 중인 광고를 매물별·채널별로 확인할 수 있다.
- [ ] 계약 완료·보류 매물의 게시 중 광고를 찾을 수 있다.
- [ ] 공실 매물에서 문구를 생성하고 클립보드로 복사할 수 있다.
- [ ] 문구 생성만으로 매물 가격·상태·광고 상태가 바뀌지 않는다.
- [ ] 계약 완료·보류 매물에서 새 문구 생성을 시도하면 상태 확인을 안내하거나 막는다.

## 12. 단계 8 — 통합 테스트와 사용성 보완 P2

### 목적

각 화면이 아닌 실제 하루 업무 전체가 자연스럽게 이어지는지 가공 데이터로 검증한다.

### 반드시 수행할 흐름

- [ ] 신규 매물: 건물 검색 → 호실 등록 → 매물 저장 → 광고 문구 복사
- [ ] 기존 매물 변동: 호실 검색 → 가격·입주일·상태 수정 → 연결 상담·계약·광고 유지 확인
- [ ] 신규 문의: 상담 등록 → 매물 제안 → 다음 연락일 설정 → 대시보드 업무 확인
- [ ] 계약: 매물/상담에서 계약 등록 → 일정 확인 → 완료 처리 → 광고 종료 확인
- [ ] 업무 시작: 대시보드 → 지연/오늘 업무 처리 → 완료 체크 → 원본 상태 분리 확인
- [ ] 권한: admin, staff, inactive, 다른 조직, 멤버 없음 계정으로 접근 확인

### 품질 점검

- [ ] 매물 목록만 보고 전화·확인할 매물을 빠르게 판단할 수 있는지 확인한다.

- [ ] 모든 저장 버튼은 처리 중 중복 클릭을 막고 결과를 알려 주는지 확인한다.
- [ ] 폼 오류는 기술 용어 대신 수정할 내용을 한글로 안내하는지 확인한다.
- [ ] 화면 너비가 좁아도 핵심 업무 정보가 읽히는지 확인한다.
- [ ] Blocker와 Critical 오류를 모두 0건으로 만든다.

## 13. 단계 9 — Production 보안 전환과 신규 운영 시작 P2

### 시작 전제

- [ ] Blocker와 Critical 오류가 0건이다.
- [ ] Production Clerk, Supabase, Vercel이 Dev/Preview와 분리되어 있다.

- [ ] Clerk–Supabase 공식 Native Integration을 Production 인스턴스끼리 연결한다.
- [ ] 로그인 요청의 Clerk 사용자 ID(`sub`)를 Supabase에서 확인한다.
- [ ] 운영 조직과 첫 admin 멤버십을 만든다.

- [ ] 사진 기능을 추가한 경우에만 private Storage 버킷, 조직별 경로, Storage RLS를 적용한다.

### Production 필수 테스트

- [ ] 미로그인 요청은 데이터 조회·저장이 거부된다.
- [ ] active admin/staff는 자기 조직 데이터만 조회·등록·수정·삭제할 수 있다.

- [ ] staff는 사용자 관리 기능을 사용할 수 없다.
- [ ] 브라우저 배포 결과에 Clerk Secret·Supabase Secret/service-role Key가 없다.
- [ ] 기본 목록 API에 연락처·계좌·출입 정보가 없다.
- [ ] 일반 CRUD가 비밀 키로 RLS를 우회하지 않는다.

### 실제 운영 시작

- [ ] 기존 Streamlit SQLite 파일을 읽기 전용 백업으로 보관한다.
- [ ] “새로 들어오는 매물부터 웹서비스에 등록한다”는 운영 기준을 사용자에게 공유한다.
- [ ] 첫 실제 건물·호실·매물을 웹에서 새로 등록한다.
- [ ] 첫 상담의 다음 연락일이 대시보드에 나오는지 확인한다.
- [ ] 첫 계약의 일정·상태·광고 확인 흐름을 점검한다.
- [ ] 문제 발생 시 웹과 Streamlit에 같은 업무를 중복 입력하지 않고, 임시 기록 후 한 번만 반영한다.

## 14. 단계 10 — 후속 기능 P3

아래 기능은 핵심 업무가 안정되고 반복적인 필요성이 확인된 경우에만 별도 작업으로 시작한다.

| 후보 기능 | 시작 조건 |
|---|---|
| 사진 업로드·정렬 | 매물 등록·수정이 안정되고 Storage 보안 정책을 검증함 |
| Excel 내보내기 | 화면 조회만으로 부족한 반복 업무가 확인됨 |
| 대량 상태·가격 수정 | 같은 수정 작업이 반복되어 실제 시간이 많이 듦 |
| 변경 이력 고도화 | 현재 생성·수정 기록만으로 원인 확인이 어려움 |
| 광고 성과 분석 | 채널별 데이터가 충분히 축적됨 |
| 문자 템플릿·발송 | 동의, 비용, 발송 책임 기준이 정리됨 |
| AI 문구 보조 | 일반 템플릿만으로 업무상 부족함이 확인됨 |
| Python 일괄 도구 | OCR·사진 보정 같은 장시간 작업이 실제 발생함 |
