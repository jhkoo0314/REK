# 부동산 매물관리 웹서비스 — 하이브리드 개발 협업 규칙 v1.0

## 1. 문서 목적

이 문서는 부동산 매물관리 웹서비스를 다음의 역할 분리 방식으로 개발하기 위한 작업 규칙이다.

- **Codex**: 프로젝트의 실제 빌드와 기능·데이터·보안·배포를 전담한다.
- **Gemini Flash 3.6**: 웹서비스의 전체 UI 디자인 뼈대와 시각적 방향만 만든다.

목표는 디자인 품질을 높이면서도, 인증·DB·권한·업무 로직이 디자인 작업으로 인해 흔들리지 않게 하는 것이다.

---

## 2. 핵심 운영 원칙

1. 실제 프로젝트 코드와 운영 환경은 Codex만 변경한다.
2. Gemini는 디자인 기준물(화면 구성, 디자인 시스템, 시각적 프로토타입)을 만든다.
3. Gemini 결과는 바로 운영 코드에 넣지 않고, 사용자 승인 후 Codex가 Next.js·shadcn/ui 구조에 맞게 다시 구현한다.
4. 전체 디자인 뼈대를 먼저 확정하고, 그 안에 매물→상담→계약→광고 기능을 하나씩 넣는다.
5. 기능을 추가할 때 디자인을 매번 새로 갈아엎지 않는다. 기존 디자인 시스템과 화면 구조 안에서 확장한다.
6. 실제 고객·계약·출입·계정·비밀값은 Gemini 디자인 작업에 제공하지 않는다.

### 3.1 Gemini가 할 수 있는 일

- 서비스 전체 UI 콘셉트와 디자인 톤 제안
- 데스크톱·모바일 공통 레이아웃 제안
- 사이드바, 헤더, 대시보드, 매물 목록, 상세, 등록 폼의 시각적 뼈대 제작
- 색상, 글자 크기, 여백, 카드, 표, 버튼, 상태 배지의 디자인 기준 제안
- 가공 예시 데이터가 들어간 정적 화면·클릭 가능한 디자인 프로토타입 제작
- 화면별 디자인 개선안과 스타일 가이드 작성

### 3.2 Gemini가 하면 안 되는 일

- Git 저장소·Next.js 프로젝트 파일을 직접 수정하거나 삭제
- 패키지 설치·제거, `package.json` 변경, 빌드 설정 변경
- Clerk, Supabase, Vercel 대시보드 설정 변경
- SQL migration, RLS, Storage 정책, API, Server Action 작성·변경
- 실제 데이터, 사용자 계정, API 키, 환경 변수 열람 또는 사용
- 업무 규칙을 임의로 바꾸기(예: 매물 수정 시 새 매물 생성, 계약 완료 시 자동 광고 종료)
- 화면 버튼에 실제 DB 저장·삭제·로그인 기능을 연결

## 4. 작업 공간 분리

| 공간 | 책임자 | 용도 | 실제 데이터/비밀값 |
| --- | --- | --- | --- |
| 디자인 기준물 | Gemini | 화면 시안, 정적 프로토타입, 디자인 토큰, 화면 캡처 | 사용 금지 |
| 디자인 인수 문서 | Codex + 사용자 | 승인된 화면과 변경 요청 기록 | 가공 예시만 사용 |
| 프로젝트 저장소 | Codex | Next.js 코드, 테스트, migration, 문서 연결 | 환경별 규칙에 따라 사용 |
| Dev/Preview 환경 | Codex | 기능·화면 검토 | 가공 테스트 데이터만 |
| Production 환경 | Codex + 운영 책임자 | 실제 운영 | 실제 데이터 허용, RLS 필수 |

Gemini의 시안·프로토타입은 “참조물”이다. 실제 서비스 소스와 같은 저장소에 직접 덮어쓰지 않는다. Codex가 승인된 디자인을 기준으로 프로젝트 코드에 반영한다.

## 5. 개발 진행 방식

### 5.1 1단계 — Codex가 프로젝트 기반을 만든다

| Codex 작업 | 결과 |
| --- | --- |
| Next.js 16, TypeScript, Tailwind, shadcn/ui 프로젝트 생성 | 실제 웹서비스 코드 기반 |
| 기본 라우트와 빈 업무 화면 생성 | 대시보드·매물 관리 등 화면 진입점 |
| Clerk Development와 Supabase Dev 기본 연결 | 로그인·가공 데이터 개발 준비 |
| 공통 UI 제약 설정 | 상태 배지, 폼, Dialog, Toast를 구현할 기준 |

이 단계의 UI는 기능 확인용 최소 구조여도 된다. 전체적인 시각 디자인을 임의로 완성하려 하지 않는다.

### 5.2 2단계 — Gemini가 전체 디자인 뼈대를 만든다

Gemini 디자인 범위는 기능 구현이 아닌 다음의 “빈 업무 도구”다.

| 화면 | 반드시 정할 것 | 기능 연결 여부 |
| --- | --- | --- |
| 공통 앱 셸 | 사이드바, 헤더, 페이지 폭, 모바일 메뉴 | 연결하지 않음 |
| 대시보드 | 오늘 할 일, 현황 카드, 최근 활동의 정보 위계 | 가공 데이터만 |
| 매물 목록 | 검색·필터·표·상태 배지·빠른 수정의 배치 | 저장 기능 없음 |
| 신규 매물 등록 | 단계형 폼, 입력 그룹, 오류 표시 위치 | 저장 기능 없음 |
| 매물 상세 | 헤더, 탭, 정보 카드, 상담/계약/광고 영역 | 가공 데이터만 |
| 상담·계약·광고 | 목록과 상세의 공통 시각 체계 | 저장 기능 없음 |
| 모바일 | 목록 카드, 필터 Drawer, 상세 세로 배치 | 가공 데이터만 |

Gemini 시안에는 버튼과 표가 있어도 된다. 다만 버튼은 화면 전환이나 시각 확인 목적의 동작만 허용하며, 실제 저장·삭제·로그인·외부 전송은 수행하지 않는다.

### 5.3 3단계 — 사용자 디자인 승인

사용자는 다음 네 가지를 기준으로 시안을 승인한다.

| 판단 항목 | 확인 질문 |
| --- | --- |
| 업무성 | 매물 목록만 보고 전화·확인할 대상을 판단할 수 있는가? |
| 속도 | 신규 매물 등록과 상태 수정의 흐름이 복잡하지 않은가? |
| 일관성 | 대시보드·목록·상세·모바일에서 같은 서비스처럼 보이는가? |
| 완성도 | 간격·글자·색상·표·카드가 내부툴이 아닌 안정적인 웹서비스 품질인가? |

승인 전에는 실제 기능 구현을 시작하지 않는다. 승인 후 시각 변경은 “디자인 변경 요청”으로 관리한다.

### 5.4 4단계 — Codex가 디자인을 실제 프로젝트에 반영한다

| 순서 | Codex 작업 | 확인 결과 |
| --- | --- | --- |
| 1 | Gemini 시안을 화면 명세와 대조 | 업무 흐름·필수 정보가 빠지지 않음 |
| 2 | 디자인 토큰을 Tailwind/shadcn/ui 구조로 변환 | 색상·여백·글자·상태 체계 통일 |
| 3 | 공통 앱 셸부터 구현 | 모든 화면의 구조 일관성 확보 |
| 4 | 매물 목록·상세·등록의 정적 UI 구현 | 가공 데이터로 디자인 일치 확인 |
| 5 | 반응형·접근성·로딩·오류 상태 구현 | 실제 브라우저 사용 가능 |
| 6 | 사용자 확인 후 기능을 순서대로 연결 | 디자인 뼈대 안에 안전하게 기능 추가 |

Codex는 시안을 그대로 복사하는 것이 아니라, 반응형·접근성·shadcn/ui 호환성·실제 데이터 길이를 고려해 구현한다. 디자인 의도가 바뀌는 경우에는 이유와 대안을 먼저 제시하고 승인받는다.

### 5.5 5단계 — 기능을 한 개씩 넣는다

기능 추가는 아래 순서를 지킨다.

1. 매물 목록·검색·필터
2. 신규 매물 등록
3. 매물 상세·수정·상태 변경
4. 대시보드와 오늘 할 일
5. 상담 관리
6. 계약 관리
7. 광고 현황과 문구 생성
8. 사용자 관리, Production 보안 전환

각 기능은 기존 디자인 뼈대의 어느 화면·컴포넌트에 들어가는지 먼저 확인한 뒤 구현한다.

| 글자 | 화면 제목, 섹션 제목, 본문, 표, 보조 정보의 크기·굵기 |
| 간격 | 화면 외곽, 카드 안쪽, 폼 항목, 표 행의 기본 여백 |
| 컴포넌트 | 버튼, 입력, Select, 표, 탭, Drawer, Dialog, Toast의 상태별 모습 |
| 상태 | 로딩, 빈 화면, 오류, 저장 중, 권한 없음, 삭제 확인 |
| 예시 데이터 | 가공한 건물·호실·금액·상태만 사용 |
| 사용 자산 | 아이콘, 폰트, 이미지 사용 여부와 라이선스/출처 |

### 디자인 인수 시 확인할 금지 사항

- [ ] 실제 고객명·전화번호·계좌·출입 정보가 없다.
- [ ] 실제 API 키·환경 변수·DB 연결 정보가 없다.
- [ ] 실제 프로젝트 파일을 수정하라는 지시가 없다.
- [ ] 데이터 저장·삭제·로그인 같은 기능 구현 지시가 포함되지 않는다.
- [ ] 기존 화면 명세의 매물→상담→계약→광고 연결을 깨지 않는다.

## 7. Codex 구현 규칙

### 7.1 디자인을 코드로 옮길 때 지킬 것

- shadcn/ui를 기본 부품으로 쓰고, 시안에 맞게 스타일을 조정한다.
- 기능별 데이터와 화면 상태를 디자인 코드 안에 하드코딩하지 않는다.
- 목록·상세·폼에서 실제 데이터 길이가 길어져도 레이아웃이 깨지지 않게 한다.
- 화면마다 새 색상·새 버튼 모양을 만들지 않고 승인된 토큰을 재사용한다.
- 로딩·빈 화면·오류·권한 없음 상태도 승인된 디자인 체계 안에서 구현한다.
- 모바일은 데스크톱을 축소하는 방식이 아니라, 목록·필터·상세의 업무 우선순위를 유지하는 방식으로 구현한다.

### 7.2 기능 구현 시 바꾸면 안 되는 업무 규칙

| 규칙 | 구현 기준 |
| --- | --- |
| 매물 일반 수정 | 기존 현재 매물을 수정한다. 새 매물을 자동 생성하지 않는다. |
| 조직 데이터 | 로그인 사용자의 조직 데이터만 보여 주고 변경한다. |
| 계약 연동 | 계약 완료·취소 시 매물 상태 변경은 사용자가 확인한다. |
| 광고 문구 | 문구 생성만으로 매물·광고 상태를 자동 변경하지 않는다. |
| 삭제 | 연결 기록이 있으면 삭제보다 상태 변경을 우선 안내한다. |
| 민감 정보 | 목록에서는 최소 노출, 상세에서도 필요한 경우에만 표시한다. |

| 정보 위계 | 대시보드에서 지연 업무를 더 강하게 보이게 함 |

### 8.2 Codex와 먼저 판단해야 하는 변경

| 변경 유형 | 이유 |

| 외부 채널·문자·AI 연동 | 보안·비용·운영 규칙에 영향 |

### 8.3 변경 기록 형식

| 항목 | 작성 예시 |
| --- | --- |

## 9. Gemini 디자인 요청 기본 템플릿

Gemini에 디자인을 요청할 때 아래 정보를 함께 제공한다.

```text
프로젝트: 원룸·투룸 중심 부동산 매물관리 웹서비스
사용자: 소규모 사무실의 admin/staff
목적: 매물 등록·검색·수정, 상담·계약·광고 현황을 빠르게 처리

이번 요청 범위:
- [예: 데스크톱 공통 앱 셸 + 매물 목록 + 매물 상세]

반드시 보여 줄 정보:
- [예: 상태, 건물·호실, 보증금/월세, 관리비, 입주 가능일, 광고 상태]

디자인 방향:
- 정돈된 업무용 SaaS 수준
- 표와 폼의 가독성 우선
- 과한 애니메이션 제외
- 밝은 중립 배경, 명확한 상태 배지, 충분한 여백
- 데스크톱 우선 + 모바일 핵심 업무 대응

제약:
- 실제 데이터·연락처·계약금·사진·계정 정보 사용 금지
- 가공 예시 데이터만 사용
- DB, 로그인, API, 기능 로직, 프로젝트 코드 수정 금지
- 정적 디자인/프로토타입과 디자인 토큰만 제안

결과물 요청:
- 화면 시안
- 데스크톱/모바일 기준
- 색상·타이포그래피·spacing·컴포넌트 상태 가이드
- 빈 화면·오류·로딩 상태 제안
```

## 10. 최종 체크리스트

- [ ] Codex가 실제 프로젝트 코드·DB·인증·배포를 단독으로 관리한다.
- [ ] Gemini는 디자인 기준물과 정적 프로토타입만 만든다.
- [ ] Gemini 결과가 사용자 승인 없이 프로젝트에 반영되지 않는다.
- [ ] 전체 UI 뼈대를 먼저 확정한 뒤 기능을 순서대로 넣는다.
- [ ] 기능 구현이 디자인 시안의 업무 흐름과 데이터 규칙을 바꾸지 않는다.
- [ ] 실제 데이터·비밀값·운영 계정이 Gemini 작업에 제공되지 않는다.
- [ ] 디자인 변경과 기능 변경을 서로 다른 요청으로 관리한다.
- [ ] 기능 완료 시 디자인 품질·업무 흐름·권한·테스트를 함께 확인한다.
