## 0. 이번 범위 정렬의 기준

웹 프로젝트의 목적은 별도의 축소 도구를 만드는 것이 아니라, 현재 운영 중인 `C:\realestate-main` Streamlit 시스템의 업무를 로그인 기반 웹으로 안전하게 구현하는 것이다.

- 업무 기능·입력 항목·처리 순서는 Streamlit의 `README.md`, `AGENT.md`, `docs/real_estate_data_dictionary_v1.md`, `docs/real_estate_listing_workflow_spec_v1.md`를 기준으로 한다.
- 웹 프로젝트는 Next.js·Clerk·Supabase·Vercel로 구현 방식을 바꾸되, 사무실 내부용 도구라는 목적과 업무 규칙은 유지한다.
- 이 문서의 이번 갱신은 기존의 “광고·Excel·상담 후속 이력·계약 상세 일정을 MVP에서 제외”한다는 축소 해석을 대체한다.
- 기존 SQLite의 실제 데이터를 자동 이관하지 않는다. 이관 여부·범위·검증 방식은 실제 운영 전 별도 승인 작업으로 결정한다. 현재 웹 Dev·Preview에는 가공 데이터만 사용한다.
- Streamlit에서 계약 상태를 바꿨을 때 연결 상태를 반영하는 업무 결과는 웹에서도 지원한다. 다만 웹에서는 저장 전 확인 창으로 사용자의 명시적 확인을 받아 잘못된 자동 변경을 막는다.

## 1. 이 계획의 결론

웹서비스 개발은 유지한다. 다만 공개 서비스나 대규모 SaaS가 아니라, **한 사무실의 최대 5명이 매물과 기본 업무 일정을 함께 확인하는 도구**로 범위를 줄인다.

이번 계획은 현재 코드를 모두 지우고 다시 만드는 계획이 아니다. 이미 만든 로그인, 공통 화면, 그리고 `건물 → 호실 → 매물` 데이터 뼈대는 유지한다. 아직 실제 운영 데이터가 없으므로, 승인 후 필요한 화면과 DB 구조만 차분히 정리한다.

## 2. 목표와 제외 범위

### 목표

1. 초대된 사용자만 로그인해 자기 사무실 매물을 안전하게 본다.
2. 매물을 등록·검색·수정할 때 중복과 누락을 줄인다.
3. 상담의 다음 연락일과 계약의 주요 일정을 놓치지 않는다.
4. PC에서 빠르게 사용하고, 휴대폰에서는 확인·검색·간단 수정이 가능하게 한다.

### 이번 웹 전환에서 하지 않는 일

- 공개 회원가입, 고객용 공개 매물 페이지, 여러 조직을 고르는 화면
- 사진 파일 업로드, OCR, 외부 광고 사이트 자동 등록, 광고 성과 분석
- 자동 추천, 자동 고객 매칭, 자동 문자 발송
- 복잡한 수수료·일할 계산, 다건 결제 관리, 대량 수정
- 별도 Python 서버, 별도 API 서버, Redis, 실시간 채팅, 모바일 앱

사진 **보유 여부**, 재확인·현장 상태, 월별 광고비 기록, 직접입력형 광고 문구 생성, 내부 업무용 Excel 내보내기는 Streamlit에 이미 있는 업무이므로 웹 전환 범위에 포함한다.

이 기능들은 실제 사용 중 반복 필요성이 확인된 뒤 별도 계획으로 검토한다.

## 3. 단순한 기술 구성

| 역할 | 사용할 것 | 이유 |
| --- | --- | --- |
| 화면과 서버 처리 | Next.js + TypeScript | 화면과 저장 규칙을 한 프로젝트에서 관리 |
| 로그인 | Clerk | 초대된 사용자만 접속 |
| 업무 데이터 | Supabase PostgreSQL | 여러 사용자의 동시 사용·백업·권한 분리 |
| 배포 | Vercel | 웹사이트 실행과 검토 배포 |

Next.js 안의 서버 기능이 저장·권한 확인을 담당한다. 별도의 Python 백엔드는 추가하지 않는다. Python은 나중에 사진·OCR처럼 오래 걸리는 일괄 작업이 생길 때만 별도 도구로 검토한다.

## 4. 반드시 유지할 업무·보안 규칙

- 모든 매물은 `건물 → 호실 → 매물` 순서로 연결한다.
- 가격·관리비·상태·입주 가능일 변경은 기존 현재 매물을 수정한다. 자동으로 새 매물을 만들지 않는다.
- 상담과 계약은 매물에 연결하되, 매물 수정으로 지우지 않는다.
- 상담에서 처음 문의한 매물과 실제 계약한 매물은 다를 수 있다. 계약에는 연결된 상담을 별도로 기록해 유입 경로와 계약 성사 결과를 함께 확인한다.
- 계약 완료·취소, 광고 문구 생성만으로 매물 상태를 자동 변경하지 않는다. 사용자가 확인한 뒤 바꾼다.
- 목록에는 연락처·출입 정보·내부 메모를 기본 표시하지 않는다. 상세에서는 접은 뒤 필요할 때만 본다.
- 실제 운영에서는 한 조직만 쓰더라도 모든 업무 데이터에 조직 소속을 둔다.
- 개발·검토 화면에는 가공 데이터만 사용한다. 기존 SQLite 자료는 이관하지 않고 읽기 전용 백업으로 보관한다.

## 5. 날짜·금액 처리 기준

| 대상 | 저장·계산 기준 |
| --- | --- |
| 보증금·월세·관리비 | `만원` 단위 정수 저장. 예: 80만 원은 `80` |
| 면적처럼 소수가 필요한 값 | DB의 정확한 소수 형식(`numeric`) 사용 |
| 입주일·퇴실 예정일·다음 연락일·계약일 | 시간 없이 날짜만 저장 |
| 생성·수정 시각 | 시간대가 포함된 시각으로 저장 |
| 중요한 계산 | 화면에서 보여줘도 저장 직전 서버가 다시 검증 |

계약 수수료나 일할 계산이 실제로 필요해질 때, 계산식·반올림·표시 단위를 먼저 문서로 확정한 뒤 한 곳의 공통 함수로 구현한다.

## 8. 상담 유입과 계약 성사 연결 규칙

상담과 계약은 아래처럼 별도 매물을 가리킬 수 있어야 한다.

```text
상담: 유입 경로 = 네이버, 최초 문의 매물 = 1번 매물
                     ↓
계약: 실제 계약 매물 = 2번 매물, 성사 상담 = 위 상담
```

- 상담에는 유입 경로와 최초 문의 매물을 선택해 기록한다. 최초 문의 매물이 없는 일반 상담도 허용한다.
- 계약에는 실제로 계약한 매물을 반드시 선택한다.
- 계약 등록 시 기존 상담을 선택할 수 있고, 선택한 상담의 최초 문의 매물과 달라도 저장을 막지 않는다.
- 상담 상세에는 `계약으로 연결됨` 결과와 실제 계약 매물을 보여 준다.
- 계약 상세에는 성사된 상담의 유입 경로와 최초 문의 매물을 보여 준다.
- 이 연결은 성과 확인을 위한 기록이다. 계약을 저장해도 상담·매물 상태를 자동으로 바꾸지 않는다.

### 승인 후 정리·완성할 부분

1. 현재 가공 시안인 매물 상세를 실제 Dev DB 조회 화면으로 교체한다.
2. 매물 수정 기능을 먼저 완성한다.
3. 대시보드·상담·계약의 가공 예시는 P1 순서가 되기 전까지 실제 기능 완료로 표시하지 않는다.
4. 광고 관련 메뉴·예시 화면은 혼동을 막기 위해 P1 이후까지 숨기거나 `준비 중`으로 분명히 표시하는 방안을 결정한다.

### 하지 않을 일

- 이미 Dev에 적용된 migration을 삭제하거나 운영 데이터처럼 다루지 않는다.
- 사용자 승인 없이 DB 구조를 초기화하거나 새 migration을 적용하지 않는다.
- 현재 코드 전체를 삭제한 뒤 처음부터 작성하지 않는다.

## 10. 작업 순서와 승인 지점

1. **계획 승인**: 이 문서의 P0/P1 범위와 제외 기능을 확정한다.
2. **P0 상세·수정 구현**: 매물 핵심 흐름을 완성하고 가공 데이터로 확인한다.
3. **P0 사용성 점검**: 실제 업무와 비슷한 가공 매물로 등록·검색·수정 흐름을 확인한다.
4. **P1 상담·계약 DB 설계 승인**: 상담의 유입 경로·최초 문의 매물, 계약의 실제 계약 매물·성사 상담 연결 규칙을 확정한 뒤 migration 파일만 작성한다.
5. **P1 구현과 오늘 할 일**: 상담·계약·일정 화면을 차례로 연결한다.
6. **운영 전환 승인**: 테스트와 권한 확인 뒤에만 Production RLS·배포를 진행한다.

DB migration은 언제나 파일을 먼저 작성하고, 별도 사용자 승인 후 Dev에 적용한다. Production 적용은 또 별도의 승인과 점검이 필요하다.

## 11. 다음 안전한 작업

이 계획이 승인되면 첫 구현 작업은 **P0 매물 상세의 실제 DB 조회와 기존 매물 수정**이다. 이 작업으로 매물 등록 → 상세 확인 → 수정 → 목록 반영의 기본 업무 흐름을 완성한다.
