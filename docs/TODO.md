## 0. 재빌드 기반 — 로그인과 공통 화면

**목적:** 새 기능을 만들기 전에, 직원이 로그인하고 동일한 화면 틀에서 업무를 시작할 수 있게 한다.

**이번 단계의 입력·처리:** Clerk Development 계정 로그인 여부를 확인하고, 로그인하지 않은 사람은 업무 화면을 볼 수 없게 한다. DB 데이터는 아직 만들거나 변경하지 않는다.

### 0-1. 프로젝트 뼈대

- [x] Next.js + TypeScript + Tailwind 프로젝트를 새로 만든다.
- [x] 패키지 설치 명령과 lint, typecheck, build 명령을 준비한다.
- [x] `.env.local`이 Git에 올라가지 않도록 확인한다. 값 자체는 화면이나 로그에 표시하지 않는다.
- [x] `app`, `components/ui`, `components/shared`, `features`, `lib` 기본 폴더를 만든다.
- [x] `app/**/page.tsx`에는 화면 조립만 두고, 큰 화면 요소는 기능별 컴포넌트로 나눌 기준을 정한다.
- [x] 각 기능을 `features/<기능>/components`, `server`, `schemas`로 나누고, 한 파일에 화면·검증·DB 처리·다이얼로그를 함께 넣지 않는 구조를 적용한다.
- [x] `REBUILD_MASTER_SPEC.md`의 확정 폴더 트리를 만든 뒤, 페이지·공통 UI·업무 기능·공통 함수의 위치가 기준과 맞는지 확인한다.

### 0-2. 로그인과 접근 제한

- [x] Clerk Development 로그인·로그아웃 화면을 연결한다.
- [x] 로그인하지 않은 사용자가 `/consultations`, `/dashboard`, `/listings` 같은 업무 주소를 직접 열어도 로그인 화면으로 이동하게 한다. 실제 브라우저 확인은 남아 있다.
- [x] 로그인 후 기본 시작 주소를 상담 관리 `/consultations`로 정한다.
- [ ] 활성 멤버십이 없는 계정, 비활성 계정의 안내 화면을 준비한다.
- [x] 이 단계에서는 사용자 초대·조직 선택 화면을 만들지 않는다.

### 0-3. 공통 앱 화면과 확정 디자인 구현 가이드 적용

- [x] `docs/DESIGN_BUILD_PREP.md`를 먼저 읽고, 목록 중심 부동산 업무 CRM의 화면 역할·메뉴 순서·공통 부품 분리 기준을 확인한다.

- [x] 연락처·출입 비밀번호는 P0 제한 테이블에 저장하되, 기본 목록·검색·목업·내보내기에는 표시하지 않는 공통 규칙을 적용한다. 계좌와 일반 내부 메모는 이번 범위에서 제외한다.

**완료 확인**

**이번 단계 제외:** 실제 매물 조회·저장, DB migration 적용, 실제 업무 데이터 입력.

**시작 조건:** 0단계 로그인·App Shell·공통 UI가 완성된 상태.

- [x] 상담 상세의 `매물 찾기 → 조건이 적용된 매물 목록 → 이 상담에 제안 → 상담 상세` 화면 이동을 구현한다.

## 1. P0 데이터 모델 — DB 파일 작성과 Dev 적용 준비

**목적:** 건물 → 호실 → 매물의 기본 관계와 조직 분리를 DB에서 안전하게 지킬 수 있게 한다.

**중요:** 여기서는 migration 파일을 작성하는 것까지다. Dev DB 초기화나 migration 적용은 사용자의 별도 승인 뒤에만 한다.

### 1-1. P0 데이터 항목 확정

- [x] `organizations`, `organization_members`의 최소 항목과 admin/staff, active/inactive 기준을 확정한다.
- [x] `buildings`에 주소·공동 정보·공통 민감 정보의 저장 위치를 확정한다.
- [x] `units`에 호수·구조·방향·옵션·방문 관련 정보의 저장 위치를 확정한다.
- [x] `listings`에 현재 상태·가격·관리비·입주 조건·사진 보유 여부·재확인일·보유처의 저장 기준을 확정한다. 입주 조건은 즉시 가능·날짜 지정·확인 필요로 구분한다.
- [x] `listings.property_type`에 주거형 방 구조와 아파트·오피스텔·상가·사무실을 구분할 기준을 확정한다. P0 입력 화면은 원룸·투룸·투베이·쓰리룸·주인세대를 대상으로 한다.
- [x] 주거형 방 구조와 모든 매물에 공통인 면적·층·가격·관리비 항목을 구분한다. 전용면적은 아파트 등 후속 확장용 DB 예약 항목으로만 유지하고, 원룸·투룸 P0 화면에서는 입력·표시하지 않는다.
- [x] 모든 업무 테이블의 `organization_id`, 생성·수정 시각, 생성·수정 사용자 기록 원칙을 확정한다.
- [x] 금액은 만원 단위 정수, 날짜는 시간 없는 날짜로 저장하는지 확인한다.

### 1-2. P0 migration 파일 작성

- [x] 조직과 멤버십 migration을 작성한다.
- [x] 건물·호실·매물 migration을 작성한다.
- [x] 같은 조직 안에서 건물 중복을 막는 규칙을 작성한다.
- [x] `302`와 `302호`를 같은 호실로 처리하는 중복 방지 규칙을 작성한다.
- [x] 호실당 현재 매물은 한 건만 허용하는 규칙을 작성한다.
- [x] 금액·상태·날짜의 잘못된 값을 막는 규칙을 작성한다.
- [x] 일반 매물 수정은 같은 현재 매물 행을 수정한다는 저장 규칙을 작성한다.
- [x] migration 파일별 목적과 **작성만 완료 / Dev 적용 완료** 상태를 문서에 기록한다.

### 1-3. Dev DB 적용 승인 전 확인

- [x] 현재 로그인한 개발자 1명 admin, 가공 조직 1개, 건물·호실·매물 가공 seed 계획을 작성한다. `DEV_DB_APPLY_PRECHECK.md`를 따른다. 다른 조직·staff·inactive 검증은 P2로 보류한다.

- [x] Production Supabase, Clerk Production, 기존 Streamlit SQLite가 대상에서 제외됐는지 적용 계획에서 확인했다.
- [x] 사용자가 Dev DB 초기화·migration 적용을 직접 완료했다.

**완료 확인**

- [x] migration 파일만으로 빈 Dev DB에 적용할 순서가 명확하다. `DEV_DB_RESET_AND_APPLY.md`에 수동 절차를 기록했다.
- [x] 다른 조직의 건물·호실·매물을 연결할 수 없게 설계됐다.
- [x] 일반 수정으로 새 매물이 만들어지지 않게 설계됐다.

**이번 단계 제외:** Dev DB 실제 초기화·적용, 매물 화면 구현, 상담·계약·광고 테이블.

**향후 확장 메모:** 아파트 단지·동·공급면적, 상가 권리금·부가세·용도, 오피스텔 전용 항목은 실제 도입 승인 뒤 별도 migration·화면·테스트 작업으로 추가한다.

## 2. P0 매물 업무 — 등록·검색·수정·건물 관리

**목적:** 매일 쓰는 매물 업무를 먼저 완성한다. 직원이 매물을 새로 등록하고, 찾고, 확인하고, 현재 정보를 안전하게 고칠 수 있어야 한다.

**시작 조건:** 단계 1 migration이 Dev DB에 적용됐고, 가공 seed가 준비된 상태.

### 2-1. 매물 목록과 검색 — 구현 완료 / Dev 실제 조회 검증 대기

- 진행 상태: 코드 구현과 lint·typecheck·build 확인 완료. Dev seed 및 `20260826000200` migration 적용 뒤 실제 목록·검색 결과를 브라우저에서 확인한다.
- [x] 로그인 사용자의 활성 조직 매물만 서버에서 조회한다.
- [x] 목록에 상태, 건물명, 주소, 호실, 구조, 보증금, 월세, 관리비, 입주 조건, 매물번호를 표시한다. 기본 목록은 계약 완료를 제외한 관리 중 매물이며, 상태 필터에서 전체·계약 완료를 다시 조회할 수 있다.
- [x] 연락처·출입 정보·내부 메모는 목록 조회와 표시에서 제외한다.
- [x] 건물명·주소·호실·매물번호 검색을 구현하고 검색 조건을 URL에 남긴다.
- [x] 상태, 거래 유형, 입주 조건, 가격 범위, 보유처, 사진 보유 여부, 재확인일 필터를 구현한다.
- [x] 빈 결과, 필터 초기화, DB 오류 시 다시 시도 안내를 구현한다.
- [x] 휴대폰에서는 같은 데이터를 카드 형태로 표시한다.

### 2-2. 신규 매물 등록 — 구현·브라우저 정상 동작 확인 완료

- 진행 상태: 등록·저장 흐름을 브라우저에서 정상 동작 확인했다. 저장 뒤 상세 화면으로 여는 기능은 2-3에서 구현한다.
- [x] 기존 건물 선택과 새 건물 입력을 제공한다.
- [x] 선택 건물의 기존 호실 선택과 새 호실 입력을 제공한다.
- [x] 새 호실에 일반적인 숫자 호실을 입력하면 층을 자동으로 제안하고, 필요하면 직접 바꿀 수 있게 한다. 호실 단계의 방 구조 입력은 제거하고 현재 매물 조건의 방 구조 선택으로 관리한다.
- [x] 현재 매물 조건의 방 구조 선택에 원룸·투룸·투베이·쓰리룸·주인세대를 제공한다. DB enum 확장 migration 적용은 별도 확인한다.
- [x] 새 건물 → 새 호실 → 현재 매물을 한 번에 저장하는 DB 함수를 작성한다.
- [x] 같은 호실에 현재 매물이 있으면 저장 단계에서 막는다.
- [x] 가격·관리비·거래 유형·입주 조건·보유처·사진 보유 여부·재확인일·현장 상태를 검증한다.
- [x] 저장 중 중복 클릭을 막고, 입력 오류를 해당 칸 근처에 표시한다.
- [x] 저장 성공 뒤 매물번호를 안내하고 목록으로 이동할 수 있게 한다. 상세 이동은 2-3에서 구현한다.

- [x] 로그인 조직의 현재 매물만 상세에서 열리게 한다.
- [x] 건물·호실·주소·가격·관리비·입주 조건·구조·보유처·사진·재확인·현장 상태를 표시한다.
- [x] 세대 비밀번호는 일반 목록·상세에서 제외하고, 매물 등록·수정 화면의 제한 입력칸에서만 저장·수정한다. 연락처 입력은 후속 건물 관리 단계에서 추가한다.
- [x] 임대인 연락처는 건물 기준, 세입자 연락처는 호실 기준의 제한 정보로 분리하고 매물 등록·수정 화면에서만 입력·수정한다.
- [x] 매물 등록에서는 임대인 연락처를 1번 건물 선택에, 세입자 연락처·세대 비밀번호를 2번 호실 선택에 배치한다.
- [x] 기존 건물 선택은 일반 드롭다운 대신 건물명·주소 검색 선택창을 사용한다.
- [x] 매물 목록 행에서 `비밀번호 보기`를 누르면, 같은 조직의 해당 호실 비밀번호만 작은 확인창에 표시하고 복사할 수 있게 한다.

- [x] 서버가 로그인·활성 멤버십·같은 조직·현재 매물 한 건을 다시 확인한 뒤 저장한다.
- [x] 저장 뒤 목록과 상세에 바뀐 값이 반영되는지 브라우저에서 확인한다.

### 2-4. 빠른 수정·건물/호실 관리·이력

- [x] 기능 구현 완료: 빠른 수정, 실제 Dev DB 연결 건물·호실 관리, 과거 이력 전용 상세, 계약 완료→과거 이력 전환, 관리 종료 사유 선택·확인 흐름을 구현했다.
- 진행 상태: 빠른 수정·건물/호실 관리·과거 이력·계약 완료 전환·관리 종료 사유 선택을 브라우저에서 정상 확인했다. 2-4 기능과 범위 검증을 완료했다.

- [ ] **P1 계약관리 선행 수정:** 현재 매물 화면에 남아 있는 임시 `계약 완료` 동작을 제거한다. 계약 진행·계약 완료는 계약관리에서만 처리하고, 계약관리의 확정 결과가 매물을 계약 완료 과거 이력으로 전환하게 한다.

**완료 확인**

- [ ] 다른 조직 매물과 민감 정보가 기본 목록에서 보이지 않는다.

## 3. P1 상담 관리 — 문의와 후속 연락

**목적:** 이 서비스의 대표 업무 화면으로 일반 문의와 매물 문의를 리드부터 계약 결과까지 관리하고, 다음 연락과 후속 통화·문자·방문 내용을 놓치지 않는다.

### 3-1. 데이터와 저장 규칙

- [x] 상담과 후속 상담 이력 migration을 작성한다.
- [x] 최초 문의 매물은 선택 사항이며, 일반 상담은 매물 없이 저장할 수 있게 한다.
- [x] 고객 식별명·연락처·상담일·유입 경로·상담 방식·상담 메모를 저장한다.
- [x] 희망 지역·방 구조는 복수 선택과 기타 직접 입력을 허용하고, 예산·희망 입주일·필수 조건 메모를 저장한다.
- [x] 상담 상태는 `진행 중`·`보류`·`종료`·`확인 필요`, 진행 단계는 `신규 문의`·`조건 확인`·`방문 예정`·`방문 완료`·`검토 중`·`종료`로 분리한다. 계약 진행·완료는 상담에서 선택하거나 변경하지 않는다.
- [x] 전화·문자·방문·기타 후속 이력의 일자·진행 단계·방문 결과·내용·종료 사유·다음 연락일을 저장한다.
- [x] 후속 이력 추가·수정·삭제 때 최신 상담일·마지막 이력·다음 연락일·진행 단계 요약을 다시 계산한다.
- [x] 상담 종료 시 다음 연락일을 해제하는 규칙을 구현한다.
- [x] 고객 연락처는 같은 조직 직원의 상담 기본 목록과 상세에 표시한다. 매물 목록·오늘 예정 업무·광고·일반 매물 Excel에는 표시하지 않는다.

### 3-2. 화면과 업무 흐름

- [ ] 상담 목록의 검색·전체 구분·전체 상태·상담일 필터를 구현한다. 세부 진행 단계·종료 사유·집중 대응 필터는 MVP에서 제외한다.
- [ ] 상담 목록을 기본 업무 화면으로 만들고 상담일 최신순으로 정렬한다. 다음 연락일은 목록에서만 표시한다.
- [ ] 목록에 상담번호, 고객 식별명·연락처, 최초 문의 매물번호·건물·호실, 희망 조건 요약, 마지막 이력, 다음 연락일, 상담 상태·진행 단계를 표시한다. 상세 상담 메모·매물의 제한 연락처·출입 정보는 표시하지 않는다.
- [ ] 일반 상담과 매물 연결 상담의 등록·수정을 구현한다.
- [ ] 상담 상세에서 고객 연락처, 최초 문의 매물, 후속 이력 타임라인, 다음 연락일, 계약 연결 결과를 보여 준다. 추가로 안내한 매물은 후속 이력 메모로 기록한다.
- [ ] 후속 통화·문자·방문 이력을 누적하고, 수정·삭제 때 최신 요약을 다시 계산한다.
- [ ] 일반 상담을 나중에 최초 문의 매물과 연결할 수 있게 한다.
- [ ] 계약 등록은 현재 상담을 출처 상담으로 선택해 이동시킨다. 계약 진행·완료는 계약관리에서만 바꾸고, 연결 계약의 결과를 상담 상세에 읽기 전용으로 표시한다.
- [ ] 상담 삭제 전 후속 이력 건수를 안내하고, 상담·후속 이력만 삭제한다. 연결 매물·계약 원본은 삭제하지 않는다.

**완료 확인**

- [ ] 매물 없는 일반 상담과 매물 연결 상담이 모두 저장된다.
- [ ] 후속 이력이 최초 상담 내용을 덮어쓰지 않는다.
- [ ] 후속 이력 추가·수정·삭제 뒤 최신 요약과 다음 연락일이 정확히 다시 계산된다.
- [ ] 다음 연락일이 있는 진행 상담만 다음 단계의 오늘 할 일에 나타난다.
- [ ] 같은 조직 직원은 상담 목록에서 고객 연락처를 확인하고, 다른 조직·매물 목록·오늘 예정 업무에서는 보지 못한다.
- [ ] 상담에서는 계약 진행·계약 완료를 처리할 수 없고, 계약관리에서 처리한 결과만 확인한다.

**이번 단계 제외:** 자동 문자 발송, 고객 공개 페이지, AI 고객 추천.

## 4. P1 계약 관리 — 일정·상태·출처 상담

**목적:** 실제 계약 매물, 계약 일정, 금액, 중개 방식, 출처 상담을 한 기록으로 관리하고 잘못된 상태 변경을 막는다.

### 4-1. 데이터와 저장 규칙

- [ ] 계약과 계약 단계 이력 migration을 작성한다.
- [ ] 실제 계약 매물은 필수, 출처 상담은 선택으로 한다.
- [ ] 계약 유형·중개 방식·계약 진행일·정식 계약일·입주일·만료일·계약 상태 저장 기준을 확정한다.
- [ ] 계약금 전체·가계약금·추가 수령 예정일·잔금·잔금 예정일의 금액·날짜 검증을 구현한다.
- [ ] 가계약·정식계약·잔금 예정·계약 완료·해지 단계 이력을 누적한다.
- [ ] 계약 상태·계약 단계 이력 저장 시 실제 계약 매물을 자동 반영한다: 계약 진행·잔금 예정 → 계약 진행, 계약 완료 → 계약 완료 과거 이력, 해지·만료 → 아직 계약 진행인 매물만 공실.
- [ ] 계약과 출처 상담의 최초 문의 매물이 달라도 저장을 막지 않는다.

### 4-2. 화면과 상태 변경 확인

- [ ] 계약 목록·검색·상태·일정 필터를 구현한다.
- [ ] 매물 또는 상담 상세에서 계약 등록으로 이동할 수 있게 한다.
- [ ] 계약 상세에서 연결 매물·출처 상담·일정·금액·단계 이력을 보여 준다.
- [ ] 계약 상태·계약 단계 이력 저장 때 자동 전환될 실제 계약 매물과 결과를 확인 창에 명확히 설명한다. 해지·만료 때 영향을 받는 매물·상담 상태도 확인 창에 설명한다.
- [ ] 계약 진행·잔금 예정·계약 완료·해지·만료의 매물 자동 반영과, 종료된 과거 이력을 다시 열지 않는 규칙을 확인한다. 계약 일정 날짜만으로 상태가 바뀌지 않는지도 확인한다.
- [ ] 계약 기록을 삭제하는 경우 매물·상담 원본은 삭제하지 않는다.

**완료 확인**

- [ ] 계약이 실제 계약 매물과 선택한 출처 상담에 정상 연결된다.
- [ ] 계약 진행·완료·해지·만료는 계약관리에서만 처리한다.
- [ ] 사용자가 계약관리의 상태 반영을 확인하면 정해진 매물·출처 상담 결과만 저장된다.
- [ ] 날짜·금액 오류가 저장되지 않고, 계약 이력이 보존된다.

**이번 단계 제외:** 다건 입금 내역, 수수료 자동 계산, 계약서·신분증 파일 저장.

## 5. P1 오늘 할 일 — 오늘·지연 업무와 완료 체크

**목적:** 매물 재확인, 사진·현장 확인, 퇴실, 계약 일정, 상담 다음 연락을 날짜 기준으로 짧게 확인하고 원래 기록으로 이동한다. 별도 대시보드나 업무 원본 관리 화면으로 만들지 않는다.

### 5-1. 업무 계산

- [ ] 매물 재확인일이 오늘이면 오늘, 과거면 지연 업무가 되게 한다.
- [ ] 사진 보유 여부와 현장 상태에 따른 확인 필요 업무를 계산한다.
- [ ] 퇴실 예정 D-7·당일, 계약금·잔금·계약 종료일 같은 계약 일정을 계산한다.
- [ ] 진행 중 상담의 다음 연락일을 오늘·지연 업무로 계산한다.
- [ ] 광고비와 광고 문구 생성은 오늘 할 일에 자동으로 넣지 않는다.

### 5-2. 완료 체크와 화면

- [ ] 계산된 업무의 완료 여부만 저장하는 `task_completions` migration을 작성한다.
- [ ] 완료 체크가 원본 매물·상담·계약의 날짜나 상태를 바꾸지 않게 한다.
- [ ] 완료 업무는 기본으로 숨기고 필요할 때 다시 볼 수 있게 한다.
- [ ] 각 업무에서 원래 매물·상담·계약 상세로 이동하게 한다.
- [ ] 기본 표에 연락처·비밀번호·내부 메모가 나오지 않게 한다.

**완료 확인**

- [ ] 기준 날짜를 바꾸면 오늘과 지연 업무가 정확히 나뉜다.
- [ ] 완료 체크·해제 뒤 원본 기록이 바뀌지 않는다.
- [ ] 상담·계약·매물 업무가 원래 상세 화면으로 연결된다.

**이번 단계 제외:** SMS·카카오 알림, 개인별 푸시 알림, 별도 할 일 직접 입력.

## 6. P1 광고비·광고 문구·Excel 내보내기

**목적:** Streamlit에서 쓰던 월별 광고비 기록, 직접입력 문구 생성, 업무용 자료 내보내기를 웹에서도 제공한다.

### 6-1. 월별 광고비

- [ ] `monthly_advertising_costs` migration을 작성한다.
- [ ] 기준연월·채널·월 광고비·메모를 저장한다.
- [ ] 같은 기준연월과 채널은 한 건만 저장하고, 다시 입력하면 수정한다.
- [ ] 광고비는 매물·상담·계약과 자동 연결하거나 성과를 계산하지 않는다.

### 6-2. 직접입력형 광고 문구

- [ ] 지역·방 형태·가격·입주 조건·옵션·강조점 입력 화면을 구현한다.
- [ ] 사실 확인되지 않은 거리·도보 시간·옵션을 자동으로 넣지 않게 한다.
- [ ] 제목과 본문을 생성 뒤 사용자가 직접 수정하고 복사할 수 있게 한다.
- [ ] 입력값과 생성 결과를 DB에 저장하지 않는다.
- [ ] 비밀번호·연락처·내부 메모를 문구에 넣지 않도록 안내한다.

### 6-3. Excel 내보내기

- [ ] 매물·계약·상담·오늘 할 일 화면에서 현재 검색 결과만 내보내게 한다.
- [ ] 각 파일에 포함·제외할 민감 정보 기준을 문서로 확정한다.
- [ ] 파일 생성 전 외부 공유 금지 또는 내부 업무 전용 경고를 표시한다.
- [ ] 내보낸 파일에 비밀번호·내부 메모·불필요한 연락처가 섞이지 않는지 확인한다.

**완료 확인**

- [ ] 같은 월·채널 광고비 중복이 저장되지 않는다.
- [ ] 광고 문구를 만들거나 복사해도 DB 상태가 바뀌지 않는다.
- [ ] 각 Excel 파일에 허용되지 않은 민감 정보가 포함되지 않는다.

**이번 단계 제외:** 매물별 광고 채널 상태, 외부 광고 등록, 광고 클릭·전환 성과 분석.

## 7. P2 통합 검증·Preview·Production 전환

**목적:** 실제 업무를 시작하기 전에 권한·조직 분리·화면 사용성·Production 보안을 확인한다.

### 7-1. 가공 계정과 업무 흐름 검증

- [ ] admin, staff, inactive, 멤버 없음, 다른 조직 가공 계정을 준비한다.
- [ ] 각 계정이 허용된 화면과 데이터만 접근하는지 확인한다.
- [ ] PC에서 매물 등록 → 검색 → 수정 → 상담 → 계약 → 오늘 할 일을 확인한다.
- [ ] 휴대폰에서 로그인 → 검색 → 상세 확인 → 간단 수정을 확인한다.
- [ ] 저장 중 중복 클릭, 빈 화면, 오류, 권한 없음, 확인 창을 점검한다.

### 7-2. Preview·Production 준비

- [ ] Preview가 Dev·Production과 다른 Clerk·Supabase 환경을 쓰는지 확인한다.
- [ ] Preview와 Dev에 실제 데이터가 없는지 확인한다.
- [ ] Clerk Production, Supabase Production, Vercel Production을 분리 준비한다.
- [ ] Clerk–Supabase Native Integration과 Production RLS를 준비한다.
- [ ] 조직별 SELECT·INSERT·UPDATE·DELETE와 INSERT/UPDATE `WITH CHECK` 정책을 검증한다.
- [ ] 일반 CRUD가 secret/service-role 키를 사용하지 않는지 확인한다.

### 7-3. 운영 시작 승인

- [ ] lint, typecheck, build, 관련 테스트 결과를 기록한다.
- [ ] 수용 테스트의 Blocker·Critical 오류가 0건인지 확인한다.
- [ ] Production 릴리스 체크리스트를 완료한다.
- [ ] 운영 조직과 첫 admin·staff의 접근 방식을 승인한다.
- [ ] 실제 데이터는 웹에서 새로 등록하는 방식이 준비됐는지 확인한다.

**완료 확인**

- [ ] 다른 조직·비활성·미로그인 사용자가 업무 데이터를 볼 수 없다.
- [ ] Production RLS와 조직 분리 테스트를 통과한다.
- [ ] 실제 데이터 입력 전 모든 필수 테스트가 통과한다.
