- 사용자가 Dev DB에서 seed를 실행했다. 실제 고객·계약·출입 데이터는 넣지 않았다.

### Dev DB 제약 검증 — Dev 실행 완료

- `supabase/seeds/0002_verify_dev_listing_constraints.sql`를 작성했다.
- `302`/`302호` 중복, 다른 조직 건물 연결, 호실당 현재 매물 2건 생성을 각각 막는지 확인한다.
- 사용자가 Dev DB에서 실행해 세 검증을 통과했다. 검증 과정에서 남는 잘못된 데이터는 없다.

### P0 정적 화면·DB 항목 정합성 보완

- 신규 매물 3단계 화면에 매물 보유처, 매물 상태, 거래 유형, 금액, 입주 가능 유형과 날짜 지정 입력 자리를 DB 값에 맞춰 반영했다.
- 전세는 전세금을 보증금 칸에 저장하고 월세는 비우는 표시 기준을 반영했다.
- 구조·방향·기본 옵션이 호실 고정 정보임을 2단계 안내로 분리했다.
- 공통 상태 배지가 Dev DB의 매물 상태 전체를 표시할 수 있게 확장했다.
- 매물 상세의 내부 메모를 공통 `SensitiveInfo`로 감싸 기본 접힘으로 바꿨다.
- 이번 변경은 디자인·입력 구조 정리만이며, 실제 DB 조회·저장과 입력 오류 검증은 아직 연결하지 않았다.

### P0 매물 목록 — Dev DB 초기 조회 연결

- `/listings`가 로그인한 사용자의 활성 멤버십에서 조직 ID를 서버로 확인한 뒤, 그 조직의 `is_current = true` 매물만 읽도록 연결했다.
- 목록에는 건물명·호실·주소·구조·조건·관리비·입주일·상태만 가져온다. 연락처·내부 메모·출입 관련 정보는 조회 항목 자체에서 제외했다.
- 실제 매물이 없을 때의 빈 화면과 DB 연결 실패 시의 다시 시도 안내를 추가했다.
- 검색·추천 필터·상태·거래 유형 필터를 실제 목록 조회에 연결했다. 가격·관리비·광고 등 상세 필터는 아직 구현하지 않았다.
- 이번 단계에서는 DB 구조 변경이나 migration 적용이 없다.

### P0 매물 목록 — 검색·핵심 필터 연결

- 건물명·주소·호실·매물번호의 부분 검색을 연결했다. 검색어는 Enter로 적용되며 URL에 남는다.
- 매물 상태와 거래 유형 필터는 선택 즉시 적용되며, 추천 필터에는 전체·즉시 입주·공실·광고 가능·계약 진행 중을 연결했다.
- 상태·거래 유형·입주 가능 조건은 Dev DB 조회 조건으로 적용한다. 검색은 목록에 이미 제한된 안전한 표시 정보만 대상으로 처리한다.
- 검색 결과가 없을 때는 현재 조건에 맞는 매물이 없음을 알리고, 필터 초기화 버튼을 제공한다.
- 이번 단계에서는 DB 구조 변경이나 migration 적용이 없다.

### P0 신규 매물 등록 — 일괄 저장 migration 작성

- `supabase/migrations/0004_create_listing_registration_function.sql`을 작성했다.
- 기존/신규 건물 → 기존/신규 호실 → 현재 매물 생성을 하나의 DB 작업으로 처리한다. 중간 단계만 저장되는 문제를 막는다.
- 선택한 건물·호실이 로그인 조직에 속하는지, 활성 멤버인지, 같은 호실에 현재 매물이 이미 있는지를 DB에서도 확인한다.
- 사용자가 Dev DB에 직접 적용했다. Production용 RLS·Clerk Native Integration 전환 시에는 권한 방식도 함께 검토한다.

### P0 신규 매물 등록 — Dev 저장 화면 연결

- `/listings/new`를 실제 3단계 입력 화면으로 교체했다. 기존/신규 건물 선택, 기존/신규 호실 선택, 매물 조건 입력을 지원한다.
- 서버에서 로그인 사용자의 활성 멤버십을 다시 확인하고, 화면에서 받은 조직 ID는 사용하지 않는다.
- React Hook Form과 Zod로 필수값·금액·날짜 지정 입주일을 검사한다. 저장 중에는 중복 클릭을 막고, 오류는 해당 입력칸 근처에 표시한다.
- 현재 매물이 이미 있는 호실은 선택 단계에서 표시·비활성화하며, 동시에 등록하려는 경우에도 DB function이 다시 차단한다.
- 저장 후 새 매물 상세 URL로 이동한다. 상세 화면 자체는 아직 가공 시안이므로, 다음 단계에서 실제 상세 조회를 연결해야 한다.
- 중복 호실 또는 현재 매물 중복을 시도하면, 화면 오류 안내와 함께 "중복된 호실입니다" 자체 팝업을 표시한다.

### Dev 로그인 조직 확인 — 적용 완료

- `.env.local`의 Supabase 프로젝트 주소에서 잘못 포함된 `/rest/v1/` 경로를 제거했다. 개발 서버를 다시 시작해야 반영된다.
- 기존 seed 실행 때 조직 A admin에 이메일이 들어간 것을 확인했다. Clerk 로그인 연결에는 이메일이 아니라 `user_`로 시작하는 Clerk Development User ID가 필요하다.
- 현재 실제 로그인 계정이 하나인 Dev 환경을 위해, 활성 멤버십이 없으면 앱이 가공 조직 A admin 연결을 현재 로그인 계정으로 자동 복구한다. 이 동작은 `NODE_ENV=development`에서만 실행되며 Production에서는 실행되지 않는다.
- `0003_link_dev_admin_clerk_user.sql`은 수동 복구가 필요할 때만 보관한다. 현재는 실행할 필요가 없다.

## 2. 확인 완료 상태

- Clerk 로그인 보호와 Local 업무 화면 접근을 확인했다.
- 실제 데이터는 입력하지 않았다.
- 로그인한 admin 계정에서 조직 A의 현재 가공 매물 6개 조회를 확인했다.
- 새 매물 등록에서 동일 호실 중복 차단을 확인했다. 자체 팝업의 브라우저 표시 재확인은 남아 있다.

아직 완료로 판단하지 않은 항목:

- `lint`와 `typecheck`는 Windows가 `node_modules` 내부 파일 접근을 막는 문제(EPERM)로 재실행 확인이 필요하다. 이 제한 때문에 이번 변경의 자동 검사 통과 여부는 아직 확정하지 않았다.
- 사용자 Supabase CLI 로그인은 완료했지만 자동 작업 환경은 해당 인증 정보를 공유하지 않는다. 실제 Dev DB 기준 타입 생성은 사용자 터미널에서 별도로 진행한다.
- Preview 화면 검토와 Local·Preview·Production 환경 분리는 보류 상태다.
- admin/staff/비활성/다른 조직 권한 검증은 멤버십·RLS 구현 후 진행한다.

## 4. 반드시 지킬 기준

- 일반 매물 수정은 기존 현재 매물을 수정하며 새 매물을 자동 생성하지 않는다.
- 계약 완료·취소는 매물 상태를 자동 변경하지 않고 사용자가 확인한다.
- 광고 문구 템플릿 사용만으로 광고·매물 상태를 자동 변경하지 않는다.
- 민감 정보는 목록에서 숨기고 상세 흐름에서 필요한 경우에만 표시한다.
- DB migration은 먼저 파일로 작성하고, 사용자 승인 뒤 Dev → Preview → Production 순서로 적용한다.
- Production 실제 데이터는 RLS·조직 분리·수용 테스트가 모두 끝난 뒤에만 입력한다.
