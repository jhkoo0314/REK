# 현재 구현 상태

> 최종 갱신: 2026-08-26
>
> 이 문서는 “실제로 구현·확인한 것”만 기록한다. 계획이나 작성 예정 migration은 완료로 적지 않는다.

## 현재 단계

- 1단계 완료 — P0 데이터 항목 확정, migration 작성 및 사용자의 Dev DB 수동 적용 완료
- 2-1 구현 완료 — 조직별 매물 목록·검색 화면 구현. Dev 가공 seed·실조회 검증 대기
- 2-2 구현 완료 — 신규 매물 등록·저장 흐름을 브라우저에서 정상 확인
- 2-3 구현 완료 — 상세·수정·목록 반영을 브라우저에서 정상 확인
- 2-4 완료 — 빠른 수정·건물/호실 관리·과거 이력·관리 종료 사유 선택을 구현하고 브라우저에서 정상 확인. 매물 화면의 임시 계약 완료 동작은 P1 계약관리 구현 때 제거 예정
- 3-2 완료 — 상담 목록·상세·후속 이력·최초 문의 매물 연결·계약 출처 전달을 브라우저에서 정상 확인. 실제 계약 저장·결과 표시는 계약관리 단계에서 구현
- 4-1 완료 — 계약·단계 이력 migration, 실제 계약 매물·선택 출처 상담 저장, 금액·날짜 검증, 단계 저장에 따른 매물·상담 자동 반영을 구현
- 4-2 완료 — 계약 목록 검색·상태·일정 필터, 출처 상담 자동 선택 등록, 상세·수정·삭제, 단계 이력과 매물 상태 자동 반영을 구현하고 브라우저에서 확인
- 5-1 완료 — 중요 업무 알림의 날짜 기준 계산·원본 이동·상담 연락처 표시 구현
- 다음 작업: 5-2 중요 업무의 상태 변경과 완료 처리 구현

## 현재 구현된 기능

- Next.js 16·TypeScript·Tailwind 프로젝트를 루트 폴더에 만들었다.
- Clerk Development를 연결하고, 로그인·회원가입 주소와 사용자 메뉴를 추가했다.
- 로그인된 사용자만 업무 화면 그룹에 접근하도록 했다. 기본 시작 주소는 `/consultations`다.
- 공통 `AppShell`, `PageHeader`, 빈 화면 부품과 상담·인박스·매물·건물·계약·광고의 빈 주소를 기능별 파일로 만들었다.
- 가공 목업 데이터로 상담 목록·상세·상담 조건 매물 검색·제안 화면 이동, 오늘 예정 업무, 건물·호실 탐색기, 계약 목록, 광고비·문구 화면을 구현했다.
- 상담 목록 상단에 `＋ 새 상담 등록`을 추가하고, Streamlit의 일반 상담/매물 상담 구분, 고객·상담·희망 조건·다음 연락일 입력 순서를 반영한 저장 전 등록 화면을 구현했다. 저장 버튼은 안내만 표시한다.
- 실제 DB 조회·저장, Supabase 연결은 아직 구현하지 않았다.
- P0 조직·건물·호실·매물 및 제한 연락처·호실 출입 정보의 열 이름, 필수 여부, 상태값, 중복·금액·날짜 규칙과 기본 노출 제외 원칙을 `P0_DATA_FIELD_SPEC.md`로 확정했다.
- `supabase/migrations/20260826000100_create_p0_core_schema.sql`을 작성했다. 이 migration은 Dev에서 RLS를 명시적으로 비활성화하도록 작성했으며, 사용자가 Supabase Dev DB에 직접 적용했다. Production DB에는 적용하지 않았다.
- `DEV_DB_APPLY_PRECHECK.md`에 가공 seed, Dev 초기화 영향, 적용 순서와 제외 대상을 기록했다. 원격 Dev DB 대상명은 아직 조회하지 않았다.
- `DEV_DB_RESET_AND_APPLY.md`에 Dev `public` 스키마만 초기화하고 P0 migration을 수동 적용하는 순서를 기록했고, 사용자가 초기 P0 migration 적용을 완료했다.
- 2-1 매물 목록은 서버에서 Clerk의 활성 조직과 Dev DB의 active 멤버십을 다시 확인한 뒤 현재 조직의 매물만 읽도록 구현했다. 검색·필터 조건은 URL에 남기며, 목록에는 연락처·출입 정보·내부 메모를 조회하지 않는다.
- Clerk Development의 `REK_test` 조직 생성을 확인하고, 웹 상단에 조직 선택 메뉴를 추가했다.
- `REK_test` 조직과 현재 로그인한 사용자 1명을 Dev DB의 `organizations`, `organization_members`에 active admin으로 연결했다. 연결 상태를 읽기 전용으로 다시 확인했다.
- `20260826000200_add_listing_reference_number.sql`을 작성했다. 이는 목록의 `M-000001` 표시번호를 위한 추가 migration이며, 사용자가 Dev에 적용했다고 알려왔다.
- 신규 매물 저장 DB 함수(`20260826000300`)와 Dev 웹 접근 권한(`20260826000400`)을 통한 등록 흐름은 브라우저에서 정상 동작을 확인했다. migration별 수동 적용 시각은 별도로 기록하지 않았다.
- 2-2 신규 매물 등록 화면과 서버 저장 처리를 구현했다. 기존/새 건물·호실 선택, 금액·거래 방식 검증, 저장 중 중복 클릭 방지, 저장 결과 안내를 포함하며 사용자가 브라우저에서 정상 동작을 확인했다.
- 2-3 매물 상세·수정의 기본 흐름을 구현했다. 목록에서 같은 조직의 현재 매물만 상세로 열고, 일반 조건을 수정하면 같은 매물 행을 갱신한다. 연락처·출입 정보·상담·계약 연결은 표시하지 않는다.
- 매물 등록·수정 화면에 세대 비밀번호 제한 입력칸을 추가했다. 이 값은 목록과 일반 상세에 표시하지 않으며, 신규 등록 저장을 위한 `20260826000600` migration은 Dev 수동 적용 대기다.
- 매물 목록의 각 행에는 비밀번호 값을 미리 싣지 않고, `비밀번호 보기`를 눌렀을 때만 서버가 같은 조직·현재 매물을 다시 확인해 작은 확인창에 표시하도록 했다.
- 매물 등록·수정에 임대인·세입자 연락처 제한 입력칸을 추가했다. 임대인은 건물 공통 연락처, 세입자는 새 `unit_contacts` 호실 연락처 테이블에 분리 저장한다. `20260826000700` migration은 Dev 수동 적용 대기다.
- 새 매물 등록에서 기존 건물은 건물명·주소 검색 선택창으로 고른다. 선택 결과는 최대 8건으로 좁혀 표시하며, 기존 건물·호실의 제한 연락처는 새 등록 화면에서 비워 둔다고 자동 삭제하지 않는다.
- 현재 매물 조건에서 현장 상태 입력을 제거하고, 입주 조건을 즉시 가능·날짜 지정·확인 필요로 분리했다. 이 값을 저장·검색하기 위한 `20260826000800` migration은 Dev 수동 적용 대기다.
- 원룸·투룸 P0 등록·수정·상세 화면에서 전용면적 입력·표시를 제거했다. `listings.exclusive_area_m2` DB 칼럼은 아파트 등 후속 확장을 위해 남기며, 기존 값은 수정 저장으로 지우지 않는다.
- 2-4의 첫 범위로 목록 행의 `빠른 수정`을 구현했다. 상태·사진 상태·마지막 재확인일·보유처만 수정하며, 서버가 같은 조직의 현재 매물을 다시 확인한 뒤 저장한다. 사용자가 PC·휴대폰 브라우저에서 이 흐름을 정상 확인했다.
- `/buildings`를 가공 목업 탐색기에서 실제 Dev DB 연결 관리 화면으로 교체했다. 건물명·주소·우편번호·임대인 연락처와 호실·층·방향·고정 옵션·세대 비밀번호·세입자 연락처를 선택한 건물·호실에서만 수정한다. 호실별 현재 매물과 `is_current = false` 과거 매물을 구분해 보여 주며, 사용자가 브라우저에서 저장 흐름을 정상 확인했다.
- 과거 매물은 `/listings/[id]/history` 읽기 전용 상세 화면에서 당시 조건만 확인하도록 구현했다. 이력 행은 이 전용 화면으로, 현재 매물 행은 기존 상세·수정 흐름으로 연다. 사용자가 브라우저에서 정상 확인했다.
- 매물 화면의 임시 `계약 완료` 동작은 브라우저에서 정상 확인했지만, Streamlit 기준과 맞지 않아 P1 계약관리 구현 시 제거한다. 계약 진행·완료는 계약관리에서만 처리하고, 계약관리의 확정 결과가 매물을 `contract_complete`·`is_current = false` 과거 이력으로 전환하도록 이관한다. 기존 계약 완료 Dev 테스트 매물을 같은 기준으로 정리하는 `20260826000900` migration은 수동 적용 대기다.
- Streamlit 기준으로 P1 계약 관리의 자동 반영 규칙을 확정했다. 계약 진행·잔금 예정은 연결 매물을 계약 진행으로, 계약 완료는 과거 이력으로, 해지·만료는 아직 계약 진행인 매물만 공실로 되돌린다. 계약 일정 날짜 자체는 상태를 자동 변경하지 않는다.
- 계약은 매물과 같은 거래 방식(월세·전세·매매·확인 필요)과 별도 계약 구분(신규 계약·재계약)을 저장하도록 정리했다. 새 계약에서 실제 계약 매물을 고르면 거래 방식이 자동 입력되며, 등록·상세·수정 화면 모두 같은 문구를 사용한다. 이를 위한 `20260826001700_split_contract_transaction_and_kind.sql`은 Dev DB 수동 적용 대기다.
- 현재 매물 상세에 `관리 종료` 확인창을 추가했다. 실제 삭제 대신 `타 부동산 계약` 또는 `기타` 사유를 선택해 `ended` 상태·`is_current = false`로 전환하고 과거 이력을 보존하며, 새 매물 등록 가능과 기록 보존 영향을 먼저 설명한다. 사용자가 Dev DB 적용과 브라우저 흐름을 정상 확인했다. P1 상담·계약 연결 구현 전이라 연결 건수 표시는 없다.
- 신규 호실에 `302호` 같은 숫자 호실을 입력하면 층을 자동 제안하고 직접 수정할 수 있게 했다. 호실 단계의 방 구조 입력은 제거했으며, 현재 매물 조건의 방 구조로 표시·조회한다. 현재 선택 가능한 방 구조는 원룸·투룸·투베이·쓰리룸·주인세대다.
- 위 추가 방 구조를 Dev DB에도 저장할 수 있도록 `20260826000500_expand_residential_property_types.sql`을 작성했다. 이 파일은 아직 Dev에 적용하지 않았다.
- P1 상담의 데이터·저장 규칙을 구현했다. `20260826001100_create_p1_consultations.sql`에는 일반/매물 상담, 고객 연락처, 복수 희망 조건, 상담 상태·진행 단계, 후속 이력과 최신 요약 재계산 trigger를 넣었다. Dev에서는 RLS를 명시적으로 비활성화하고 가공 데이터용 접근 권한만 부여한다. 파일만 작성했으며 Dev DB에는 아직 적용하지 않았다.
- 새 상담 등록은 실제 DB 저장 화면으로 교체했다. 같은 조직의 현재 매물만 최초 문의 매물로 연결하며, 고객 연락처는 상담 화면에서만 저장·표시할 준비를 했다. 후속 이력의 추가·수정·삭제 서버 처리도 조직 확인 뒤 동작하도록 준비했으며, 목록·상세 타임라인 UI는 다음 3-2 단계에서 연결한다.
- 상담 저장 뒤 목업 전용 상세 화면으로 이동해 404가 나던 문제를 수정했다. 저장된 UUID 상담도 같은 조직 안에서 실제 DB로 읽어 기본 상세를 표시한다. 고객 이름은 선택 입력으로 바꿨고, 이미 적용한 `20260826001100`의 이름 필수 제약을 풀 `20260826001200_allow_consultation_customer_name_blank.sql`을 추가했다. 상담 등록과 매물 등록의 연락처는 숫자 입력 시 `000-0000-0000` 형식으로 자동 정리한다.
- 상담 목록에서 목업 데이터를 제거하고, 현재 조직의 실제 `consultations` 행만 상담일 최신순으로 표시하도록 바꿨다. 고객 이름·연락처, 일반/매물 구분, 희망 조건, 유입 경로, 상담일, 상태·진행 단계, 다음 연락일을 보이며 검색·기본 상태 필터를 제공한다. 코드 검사만 통과했으며 브라우저 목록 반영 확인은 남았다.
- 상담 상세에 후속 이력 타임라인과 `이력 추가` 화면을 연결했다. 전화·문자·방문·기타의 일자·진행 단계·방문 결과·종료 사유·다음 연락일·내용을 저장하고, 기존 이력 수정·삭제도 지원한다. 종료 단계로 저장하면 상담 종료·다음 연락일 해제를 적용하며, 이력 삭제 뒤 DB trigger가 최신 이력과 다음 연락일 요약을 다시 계산한다. `pnpm typecheck`, `pnpm lint`, `pnpm build`와 사용자 브라우저 저장 확인을 통과했다. 3-1 데이터·저장 규칙은 완료다.
- 3-2의 상담 상세 확장으로 상담 기본 정보 수정, 일반 상담의 최초 문의 매물 사후 연결, 후속 이력 수를 알리는 상담 삭제 확인창을 구현했다. 매물 원본은 상담 삭제로 삭제하지 않는다. 별도 제안·관심 매물 연결은 MVP에서 제거하고, 추가로 안내한 매물은 후속 이력 메모로 기록한다. 코드 검사만 통과했고 브라우저 확인은 남았다.
