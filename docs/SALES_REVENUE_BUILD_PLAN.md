# 중개수수료 수입·담당자별 매출관리 빌드 계획

> 기준일: 2026-08-31  
> 상태: 구현 전 계획 확정 단계  
> 범위: 웹에서 새로 등록하는 계약의 중개수수료 수입과 담당자별 매출 관리

## 1. 목적

현재 계약관리에는 고객의 계약금·가계약금·잔금이 저장되지만, 사무실의 중개수수료 수입과 담당자별 배분 금액은 저장하지 않는다.

이 기능은 계약 대금과 중개수수료를 분리한 뒤, 실제 입금 기준으로 아래를 확인하는 것을 목적으로 한다.

- 사무실이 실제로 받은 중개수수료
- 계약 담당 직원에게 배분되는 매출
- 아직 받지 못한 중개수수료
- 공동중개·환불 이후에도 남는 사무실과 담당자 몫

광고비·상담 유입경로 분석은 현재 기능 범위를 유지하며, 이 계획에 추가하지 않는다.

## 2. 확정된 업무 결정

| 항목 | 확정 기준 |
| --- | --- |
| 공동중개 배분 | 공동중개라도 사무실과 담당 직원이 사전에 정한 비율로 나눈다. |
| 직원 열람 범위 | staff는 본인 담당 계약의 본인 매출만 본다. 다른 직원·사무실 전체 매출은 볼 수 없다. |
| 관리자 열람 범위 | admin은 사무실 전체와 직원별 매출을 확인·수정할 수 있다. |
| 담당자 기준 | 계약을 저장한 로그인 사용자를 계약 담당 직원으로 자동 기록한다. 관리자는 직원별 기본 담당자 수수료 비율을 설정한다. |
| 매출 기준일 | 계약 완료일이 아니라 실제 수수료를 받은 입금일을 월 매출 기준으로 한다. |
| 과거 기록 | 기존 계약은 자동 배정하지 않는다. 담당자·수수료가 없는 계약은 `정산 미입력`으로 따로 표시한다. |

## 3. 용어와 계산 기준

| 용어 | 뜻 | 월 매출에 반영 여부 |
| --- | --- | --- |
| 약정 수수료 | 계약 시 받기로 정한 전체 중개수수료 | 아니오. 예상·미수금 확인용 |
| 실제 수납액 | 실제로 받은 중개수수료 | 예 |
| 외부 공동중개 배분액 | 다른 부동산에 배분한 금액 | 예. 수납액에서 먼저 제외 |
| 사무실 배분액 | 외부 배분 후 사무실에 귀속되는 금액 | admin의 사무실 매출에 표시 |
| 담당자 배분액 | 외부 배분 후 담당 직원에게 귀속되는 금액 | 해당 직원의 본인 매출에 표시 |
| 환불액 | 이미 수납한 수수료를 반환한 금액 | 해당 월 매출에서 차감 |

기본 계산 흐름은 아래와 같다.

```text
실제 수납액
  - 외부 공동중개 배분액
  = 사무실·담당자 배분 대상 금액

사무실·담당자 배분 대상 금액
  × 사무실 배분율 / 담당자 배분율
  = 사무실 배분액 + 담당자 배분액
```

- 사무실 배분율과 담당자 배분율의 합은 반드시 100%여야 한다.
- 관리자가 멤버 권한 화면에서 직원별 기본 담당자 비율을 정한다. 새 계약의 정산을 처음 열면 해당 비율과 사무실 잔여 비율을 자동으로 채운다.
- 이미 저장한 계약 정산과 수납·환불 이력의 비율은 관리자 기본값 변경으로 바뀌지 않는다.
- 금액은 현재 프로젝트 원칙과 같이 **만원 단위 정수**로 저장한다. 비율 계산으로 1만원 단위의 차이가 생기면 저장 전 사무실 또는 담당자 귀속을 사용자가 확인한다.
- 공동중개가 아닌 계약은 외부 공동중개 배분액을 `0`으로 기록한다.

## 4. 저장 구조 계획

계약 원본의 계약금·잔금 칼럼에 수수료를 섞지 않는다. 아래처럼 별도 정산 기록으로 보관한다.

```text
contracts (기존 계약)
 ├─ responsible_clerk_user_id       계약 담당 직원 1명
 └─ contract_revenue_settlements    계약별 약정 수수료·기본 배분 기준 1건
      └─ contract_revenue_entries   실제 수납·환불 기록 여러 건
```

### 4-1. 계약 담당자

기존 `contracts` 테이블에 아래 항목을 추가한다.

| 항목 | 저장 내용 | 규칙 |
| --- | --- | --- |
| `responsible_clerk_user_id` | 실제 계약 담당 직원의 Clerk 사용자 ID | 같은 조직의 활성 멤버만 선택 가능 |

- 신규 계약을 저장하면 로그인한 직원의 Clerk 사용자 ID를 계약 담당자로 자동 기록한다. 계약 등록 화면에서 담당자 선택은 제공하지 않는다.
- 계약을 등록한 사람(`created_by_clerk_user_id`)과 계약 담당자는 최초에는 같은 값으로 저장한다. 담당자 값은 담당자별 매출 계산에 사용하고, 등록자 값은 감사 기록으로 유지한다.
- 실제 담당자가 달라 잘못 기록된 경우에만 admin이 계약 상세에서 담당자를 바로잡을 수 있다. 실제 수납이 하나라도 있으면 이미 저장된 수납 배분은 바꾸지 않는다.

### 4-2. 계약별 정산 기준

새 `contract_revenue_settlements` 테이블은 계약마다 한 건만 둔다.

| 항목 | 저장 내용 |
| --- | --- |
| `contract_id` | 연결 계약 |
| `tenant_commission_amount` | 임차인에게 받는 약정 중개수수료 |
| `landlord_commission_amount` | 임대인에게 받는 약정 중개수수료 |
| `agreed_commission_amount` | 임차인·임대인 수수료 합계(자동 계산) |
| `office_share_rate` | 사무실 배분율 |
| `staff_share_rate` | 담당자 배분율 |
| `settlement_note` | 배분 약정·특이사항 메모 |
| 작성·수정 기록 | 조직, 작성자, 수정자, 시각 |

### 4-3. 실제 수납·환불 기록

새 `contract_revenue_entries` 테이블은 실제 돈의 이동을 누적 기록한다.

| 항목 | 저장 내용 |
| --- | --- |
| `entry_type` | 수납 또는 환불 |
| `entry_date` | 실제 입금일 또는 환불일 |
| `gross_amount` | 실제 받은 금액 또는 환불한 금액 |
| `external_co_broker_share_amount` | 외부 공동중개사에 배분한 금액 |
| `office_share_rate`, `staff_share_rate` | 해당 수납 시점의 확정 배분율 사본 |
| `office_share_amount`, `staff_share_amount` | 계산·확정된 사무실/담당자 배분 금액 |
| `memo` | 입금 방식, 조정 사유 등 |
| 작성·수정 기록 | 조직, 작성자, 수정자, 시각 |

수납 기록마다 배분율·배분금액을 함께 남기는 이유는, 나중에 담당자나 비율이 바뀌어도 과거에 이미 정산한 매출이 바뀌지 않게 하기 위해서다.

## 5. 화면 계획

### 5-1. 계약 등록·수정

- 계약을 저장한 로그인 사용자를 계약 담당자로 자동 기록한다.
- 계약 등록·수정 화면에는 담당자 선택 메뉴를 넣지 않는다. 필요하면 계약 상세에서 admin만 담당자를 바로잡는다.
- 중개수수료 수납은 계약 등록 즉시 강제하지 않는다. 계약 저장 뒤 상세 화면에서 정산한다.

### 5-2. 계약 상세의 중개수수료 정산

계약 상세에 `중개수수료 정산` 영역을 추가한다.

1. 약정 수수료와 사무실/담당자 배분율을 입력한다.
2. 실제 수납이 발생할 때마다 수납일·금액·외부 공동중개 배분액을 추가한다.
3. 시스템이 사무실/담당자 배분액을 제안하고, 1만원 단위 차이를 확인한 뒤 저장한다.
4. 환불은 기존 수납을 삭제하지 않고 별도 환불 기록으로 추가한다.
5. 약정 수수료, 누적 수납, 누적 환불, 미수금, 사무실 귀속액, 담당자 귀속액을 함께 보여 준다.

### 5-3. 매출관리 화면 (`/revenue` 예정)

월 선택과 계약별 목록 중심으로 구현한다. 처음부터 복잡한 차트는 추가하지 않는다.

| 사용자 | 볼 수 있는 내용 |
| --- | --- |
| admin | 월별 사무실 수납·환불·순 귀속액, 직원별 배분액, 계약별 정산 목록, 미입력 목록 |
| staff | 본인이 담당한 계약의 본인 배분 수입·환불·미수금과 계약별 목록만 |

staff 화면에는 다른 직원 이름, 다른 직원 매출, 사무실 전체 합계가 서버 조회 단계부터 포함되지 않게 한다.

## 6. 권한·안전 규칙

- 모든 조회·저장은 기존처럼 로그인 사용자 조직 안에서만 처리한다.
- staff는 본인 `responsible_clerk_user_id` 계약의 정산 기록만 읽는다.
- staff는 본인 담당 계약의 수납을 기록할 수 있으나, 이미 기록된 다른 직원의 배분 기록은 수정할 수 없다.
- admin은 모든 계약·정산을 조회·수정할 수 있다.
- 계약 완료·해지·만료 상태는 기존 계약관리 규칙을 유지한다. 수입 기록은 계약 상태 변경만으로 자동 생성·삭제하지 않는다.
- 해지·환불 시에는 수납 기록을 삭제하지 않고 환불 기록을 남긴다.
- 기존 SQLite 자료는 이 기능으로 이관하지 않는다.

## 7. 구현 순서

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 계획 확정 | 이 문서의 수입 기준·배분·권한 규칙을 승인 |
| 2 | DB migration 작성 | 담당자, 계약별 정산, 수납·환불 테이블과 조직·금액·비율 검증 작성 |
| 3 | 계약 담당자 자동 기록 | 계약 저장 사용자를 담당자로 저장하고, admin만 상세에서 정정할 수 있게 구현 |
| 4 | 정산 입력 | 약정 수수료, 수납, 환불, 공동중개·사무실·담당자 배분 입력 구현 |
| 5 | 매출관리 화면 | admin 전체/직원별, staff 본인 전용 월별 목록 구현 |
| 6 | 검증 | 정상 수납·분할 수납·공동중개·환불·담당자 변경·admin/staff·다른 조직 차단 확인 |
| 7 | Dev DB 적용 | 사용자 승인 후 migration을 Dev DB에 적용하고 실제 흐름 확인 |

## 8. 수용 테스트 기준

| 상황 | 기대 결과 |
| --- | --- |
| 단독중개 수납 | 외부 배분 0, 사무실/담당자 비율 합계 100으로 배분 저장 |
| 공동중개 수납 | 외부 공동중개 배분액을 먼저 제외한 뒤 사무실/담당자 비율로 배분 |
| 분할 수납 | 여러 수납 기록의 담당자 매출이 같은 계약에 누적 |
| 환불 | 기존 수납은 남고, 환불월의 사무실·담당자 매출에서 차감 |
| 담당자 변경 | 수납 전에는 지정 가능, 수납 후 admin만 변경 가능하며 과거 배분은 유지 |
| staff 열람 | 본인 담당 계약·본인 배분액만 조회 가능 |
| admin 열람 | 조직 전체 계약과 직원별 매출을 조회 가능 |
| 다른 조직 | 계약·정산·매출 데이터가 전혀 조회·저장되지 않음 |

## 9. 이번 범위에서 제외

- 급여·인센티브 자동 지급 계산
- 세금계산서·부가세 신고·회계 장부 기능
- 임대료·인건비·일반 경비까지 포함한 손익 계산
- 광고분석의 추가 확장
- Excel·CSV 내보내기
- 기존 Streamlit SQLite 자료 이관

## 10. 구현 전 마지막 확인 항목

구현을 시작하기 전 아래 두 기준만 최종 확인한다.

1. 수납 후 담당자가 바뀌어도 이미 저장된 수납 배분은 바꾸지 않는다.
2. 환불은 환불 시점의 사무실·담당자 배분 비율로 각각 차감한다.

위 기준을 승인하면 migration 작성과 화면 구현 단계로 진행한다.
