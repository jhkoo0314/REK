## 2. P0 매물 업무 — 등록·검색·수정·건물 관리

**목적:** 매일 쓰는 매물 업무를 먼저 완성한다. 직원이 매물을 새로 등록하고, 찾고, 확인하고, 현재 정보를 안전하게 고칠 수 있어야 한다.

**시작 조건:** 단계 1 migration이 Dev DB에 적용됐고, 가공 seed가 준비된 상태.

### 2-1. 매물 목록과 검색 — 구현 완료 / Dev 실제 조회 검증 대기

- [x] 로그인 사용자의 활성 조직 매물만 서버에서 조회한다.
- [x] 목록에 상태, 건물명, 주소, 호실, 구조, 보증금, 월세, 관리비, 입주 조건, 매물번호를 표시한다. 기본 목록은 계약 완료를 제외한 관리 중 매물이며, 상태 필터에서 전체·계약 완료를 다시 조회할 수 있다.

- [x] 원룸·투룸, 아파트, 오피스텔, 상가·사무실 유형별 제목과 본문 읽기 전용 기본 템플릿을 선택하는 화면을 구현했다.
- [x] 기존 Streamlit의 기본형·특징 강조형 흐름을 바탕으로, 원룸·투룸 기본 안내형·특징 강조형과 아파트·오피스텔·상가·사무실 기본 안내형을 화면 기본 템플릿으로 준비했다. 사무실 공용 템플릿 저장·수정은 제공하지 않는다.
- [x] 템플릿은 주소·매물유형·거래조건·관리비·입주 가능일·특징의 확인한 값만 끼워 넣게 구현했다. 확인하지 않은 거리·도보 시간·옵션은 자동으로 넣지 않는다.
- [x] 사용자는 결과를 필요한 만큼 수정하고 제목·본문·전체를 복사할 수 있게 구현했다. 복사·수정만으로 매물·광고 상태는 바뀌지 않는다.
- [x] 비밀번호·연락처·내부 메모와 허용되지 않은 `{{항목}}`은 문구 생성·복사 전에 막는다. 실제 Dev 확인은 남아 있다.

### 6-3. 자료 반출과 민감정보 권한 — 후속 보안 작업

- [x] Excel·CSV 내보내기는 MVP에서 제공하지 않는다. 매물·상담·계약·오늘 할 일은 웹 화면의 검색·필터·상세 보기로 처리한다.
- [x] admin이 staff별 민감정보 열람 권한을 설정하는 `/members` 화면과 `organization_member_sensitive_permissions` migration을 구현했다. 대상은 건물·호실 연락처, 세대 비밀번호·출입 정보, 상담 고객 연락처다. 내부 메모는 현재 별도 민감정보 필드로 분리되어 있지 않아, 실제 도입 시 별도 권한 항목으로 추가한다.
- [x] 기본 목록·검색·오늘 할 일·광고 화면과 유형별 목업에는 민감정보를 표시하지 않는다. 권한이 해제된 staff는 매물 수정·건물·호실 관리에서도 해당 입력값을 받거나 기존 값을 볼 수 없다. 실제 Dev 확인은 남아 있다.
- [ ] 나중에 자료 반출이 꼭 필요해지면 별도 승인 작업으로만 추가한다. 기본값은 다운로드 금지이며, 허용 항목·관리자 권한·기록 방식·민감정보 제외 기준을 먼저 확정한다.

**완료 확인**

- [ ] 같은 월·플랫폼 광고비 중복이 저장되지 않는다. Dev DB 적용과 브라우저 저장 확인이 필요하다.
- [ ] 월별 플랫폼별 광고비와 전체 합계가 정확히 보인다. Dev DB 적용과 브라우저 확인이 필요하다.
- [ ] 템플릿 사용·복사로 매물·광고 상태가 바뀌지 않고, 민감정보가 문구에 포함되지 않는다.
- [x] Excel·CSV 다운로드 기능이 MVP 화면에 없다.

**이번 단계 제외:** 매물별 광고 채널 상태, 외부 광고 등록, 광고 클릭·전환 성과 분석, Excel·CSV 내보내기, 직원별 민감정보 권한의 실제 구현.

## 7. P2 통합 검증·Preview·Production 전환

**목적:** 실제 업무를 시작하기 전에 권한·조직 분리·화면 사용성·Production 보안을 확인한다.

### 7-1. 가공 계정과 업무 흐름 검증

- [ ] admin, staff, inactive, 멤버 없음, 다른 조직 가공 계정을 준비한다.
- [ ] 각 계정이 허용된 화면과 데이터만 접근하는지 확인한다.
- [ ] PC에서 매물 등록 → 검색 → 수정 → 상담 → 계약 → 오늘 할 일을 확인한다.
- [ ] 휴대폰에서 로그인 → 검색 → 상세 확인 → 간단 수정을 확인한다.
- [ ] 저장 중 중복 클릭, 빈 화면, 오류, 권한 없음, 확인 창을 점검한다.

### 7-2. Preview·Production 준비

- [ ] Preview가 Dev·Production과 다른 Clerk·Supabase 환경을 쓰는지 확인한다.
- [ ] Preview와 Dev에 실제 데이터가 없는지 확인한다.
- [ ] Clerk Production, Supabase Production, Vercel Production을 분리 준비한다.
- [ ] Clerk–Supabase Native Integration과 Production RLS를 준비한다.
- [ ] 조직별 SELECT·INSERT·UPDATE·DELETE와 INSERT/UPDATE `WITH CHECK` 정책을 검증한다.
- [ ] 일반 CRUD가 secret/service-role 키를 사용하지 않는지 확인한다.

### 7-3. 운영 시작 승인

- [ ] lint, typecheck, build, 관련 테스트 결과를 기록한다.
- [ ] 수용 테스트의 Blocker·Critical 오류가 0건인지 확인한다.
- [ ] Production 릴리스 체크리스트를 완료한다.
- [ ] 운영 조직과 첫 admin·staff의 접근 방식을 승인한다.
- [ ] 실제 데이터는 웹에서 새로 등록하는 방식이 준비됐는지 확인한다.

**완료 확인**

- [ ] 다른 조직·비활성·미로그인 사용자가 업무 데이터를 볼 수 없다.
- [ ] Production RLS와 조직 분리 테스트를 통과한다.
- [ ] 실제 데이터 입력 전 모든 필수 테스트가 통과한다.
