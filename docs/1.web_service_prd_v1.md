# 부동산 매물관리 웹서비스 PRD v1.0

> **2026-08-25 범위 정렬:** 이 웹서비스는 현재 `C:\realestate-main` Streamlit 시스템의 업무를 웹으로 전환하는 프로젝트다. Streamlit의 현재 광고 업무는 매물별 채널 상태 관리가 아니라 **월별 광고비 기록과 직접입력형 광고 문구 생성**이다. 이 문서에서 그와 다르게 설명한 매물별 광고 채널 기능은 구현 대상이 아니다. 사진 파일 업로드·외부 광고 자동 등록·성과 분석은 계속 후순위다.

> 재빌드를 시작하는 동안에는 `REBUILD_MASTER_SPEC.md`가 이 문서의 기존 구현 범위보다 우선한다.

> 작성일: 2026-08-14  
> 상태: 웹서비스 1차 빌드 기준 확정안  
> 대상: 배방우리부동산의 원룸·투룸 중심 임대 매물 업무  
> 관련 문서: 기존 Streamlit 매물관리 도구의 PRD·데이터 정의서·업무 흐름서·테스트 기준서

---

## 1. 문서 목적

현재 사무실에서 사용하는 Streamlit 기반 매물관리 도구를, 여러 기기에서 안전하게 접속할 수 있는 웹서비스로 전환하기 위한 1차 제품 기준을 정의한다.

이 문서는 다음 판단의 기준이다.

- 무엇을 1차 웹서비스에 만들고, 무엇을 뒤로 미룰지
- 기존 Streamlit의 어떤 업무 흐름과 데이터를 유지할지
- Clerk 로그인, Supabase 데이터, Vercel 배포를 어떤 순서로 적용할지
- 개발 모드와 실제 운영 모드의 보안 경계를 어디에 둘지

이 문서에 없는 기능은 “필요해 보인다”는 이유만으로 추가하지 않는다. 실제 업무에서 반복적으로 필요하다는 근거가 생긴 뒤 별도 문서로 제안·승인한다.

---

## 2. 제품 한 줄 정의

> 사무실 직원이 건물·호실·매물 조건을 빠르게 관리하고, 상담·계약·광고·오늘 할 일을 한 화면 체계 안에서 이어서 처리하는 로그인 기반 업무 웹서비스

고객이 직접 매물을 검색하거나 계약하는 공개 부동산 플랫폼이 아니다. 1차의 핵심은 **사무실 업무의 속도와 기록 정확도**다.

---

## 3. 배경과 해결하려는 문제

### 3.1 현재 방식의 장점

현재 Streamlit 도구는 다음 업무를 이미 구조화했다.

- 건물 → 호실 → 매물 회차의 데이터 구조
- 신규 매물 등록과 기존 호실 최신 정보 수정
- 매물 현황, 상담, 계약, 광고 현황, 오늘 할 일
- Excel 내보내기와 자동 백업

업무 규칙 자체는 검증 단계에 들어섰다. 따라서 웹서비스는 새 업무 방식을 만드는 작업이 아니라, 현재의 검증된 흐름을 더 안정적인 운영 환경으로 옮기는 작업이다.

### 3.2 웹 전환이 필요한 이유

| 현재 제약 | 웹서비스에서 해결할 방향 |
|---|---|
| 메인 PC가 켜져 있어야 접근 가능 | Vercel 배포로 기기와 무관하게 접속 |
| Tailscale·Windows 자동 실행에 운영이 의존 | 로그인 기반의 웹 접근으로 단순화 |
| SQLite 단일 파일과 동시 수정에 제약 | Supabase Postgres 기반 중앙 데이터 관리 |
| 내부 사용자 구분이 없음 | Clerk 로그인으로 사용자 식별 |
| 사진을 실제 데이터로 관리하지 않음 | 필요 시 Supabase Storage로 단계적 확장 가능 |
| 화면 개선과 모바일·브라우저 대응에 제약 | Next.js + shadcn/ui로 서비스 수준 UX 구현 |

### 3.3 반드시 유지할 업무 원칙

1. **업무 판단이 빠른 표 중심 화면**을 유지한다.
2. 건물·호실의 고정 정보와 이번 매물의 변동 정보를 섞지 않는다.
3. 일반적인 조건 변경은 같은 최신 매물 기록을 수정하며, 연결된 상담·계약·광고 기록을 보존한다.
4. 모르는 가격·입주일·상태는 0이나 추측값으로 저장하지 않고 `확인 필요`로 관리한다.
5. 연락처·비밀번호·내부 메모는 기본 목록과 외부 공유 데이터에 노출하지 않는다.
6. 지금 필요한 기능을 먼저 완성하고, 복잡한 CRM·자동화·공개 사이트는 뒤로 미룬다.

## 4. 사용자와 서비스 범위

### 4.1 1차 사용자

| 사용자 | 목적 | 1차 사용 방식 |
|---|---|---|
| 관리자 | 사용자 관리, 전체 업무 운영, 설정 확인 | Clerk 로그인 후 전체 접근 |
| 사무실 직원 | 매물·상담·계약·광고 업무 처리 | Clerk 로그인 후 업무 화면 접근 |

1차에는 고객 계정, 임대인 계정, 외부 중개사 계정을 만들지 않는다.

### 4.2 서비스 접근 범위

- 웹 주소는 인터넷에서 열릴 수 있으나, **로그인하지 않은 사용자는 업무 데이터에 접근할 수 없어야 한다.**
- 가입 버튼을 제공하지 않는다. 실제 사용자는 관리자가 초대·등록한다.
- 1차 운영은 하나의 사무실을 대상으로 한다.
- 다만 향후 개업·직원 추가·사무소 분리를 고려해 데이터에는 처음부터 `organization_id`를 둔다.

### 4.3 1차 성공 기준

다음이 실제로 되면 1차 목적을 달성한 것으로 본다.

1. 등록된 직원만 로그인 후 서비스 화면에 들어갈 수 있다.
2. PC와 모바일 브라우저에서 현재 매물 목록을 조회할 수 있다.
3. 신규 건물·호실·첫 매물을 빠르게 등록할 수 있다.
4. 기존 호실을 선택해 최신 가격·상태·입주일을 수정할 수 있다.
5. 수정 후 연결된 상담·계약 기록이 유지된다.
6. 재확인·사진·퇴실·계약·상담의 오늘 업무를 놓치지 않는다.
7. 상담·계약·광고 상태를 매물과 연결해 확인할 수 있다.
8. 실제 연락처·비밀번호·내부 메모가 권한 없는 화면이나 Excel에 노출되지 않는다.
9. Streamlit 도구 없이도 2주 이상 실제 업무를 지속할 수 있다.

## 5. 1차 기능 범위

### 5.1 반드시 구현한다

#### A. 로그인과 사용자 진입

- Clerk 개발 인스턴스를 이용한 로그인·로그아웃
- 로그인하지 않은 사용자의 업무 화면 접근 차단
- 현재 로그인 사용자 정보 표시
- 개발 단계에서는 관리자/직원 역할 구분을 화면에 강제하지 않음

#### B. 매물 데이터 관리

- 건물 검색과 신규 등록
- 기존 건물의 신규 호실 등록
- 건물 안의 호실 중복 방지 (`302`와 `302호` 동일 처리)
- 건물 → 호실 → 첫 매물의 안전한 일괄 저장
- 기존 호실의 최신 매물 정보 수정
- 매물 상태, 보증금, 월세, 관리비, 입주 가능일, 퇴실 예정일 관리
- 사진 보유 여부, 청소·도배·수리 상태, 재확인 예정일 관리
- 매물 보유처 관리
- 매물 종료 처리와 종료 이력 조회

#### C. 매물 현황과 오늘 할 일

- 매물 현황 리스트: 검색, 상태·룸 형태·보유처·사진·가격 범위 필터
- 표 아래 상세 보기와 현재 매물 빠른 수정
- 오늘·지연·상시 확인 필요 업무의 분리 표시
- 재확인, 퇴실 D-7/당일, 계약 일정, 상담 다음 연락일 계산
- 날짜 업무 완료 체크·해제
- 오늘 할 일의 계약 상태 변경과 매물 상태 연동

#### D. 상담과 계약

- 매물 상담과 일반 상담의 등록·조회·수정
- 고객 조건, 유입 경로, 다음 연락일, 후속 상담 이력
- 계약 진행 시작일, 정식 계약일, 임대차 기간, 계약 상태, 중개 방식
- 계약금 전체, 가계약금 수령액, 추가 수령 예정일, 잔금 예정일
- 계약 일정과 만료 예정 조회

#### E. 광고 업무

- 매물 회차별 광고 채널(당근·직방·네이버·직접 입력)과 현재 상태 관리
- 직접입력형 광고 문구 생성기
- 지역·방 형태·가격·템플릿·강조 포인트 조합
- 생성 결과 수정·복사
- 광고 문구 생성 결과는 DB에 저장하지 않음

#### F. 데이터 활용

- 현재 조회 결과의 Excel 내보내기
- 매물·계약·상담·오늘 할 일별 내보내기 기준 분리
- 매물 사진 업로드를 위한 Supabase Storage 연결 구조 준비

### 5.2 1차에서 제외한다

- 고객용 공개 매물 홈페이지·공개 상세 페이지
- 고객 회원가입·예약·자동 문자·알림톡
- 광고 사이트 자동 등록, 광고비·클릭·성과 자동 수집
- 계약서·신분증·결제 파일 저장
- 계약금·월세·잔금의 입금 내역 및 회계 관리
- AI 자동 문구 생성, 자동 매물 추천, 자동 고객 매칭
- 다수 지점·다수 부동산의 복잡한 관리 화면
- 직원별 상세 권한, 승인 워크플로, 활동 로그 대시보드
- 사진 보정·OCR·파일 일괄 처리

이 기능들은 향후 확장 후보일 뿐, 1차 구현의 완료 조건이 아니다.

## 6. 핵심 데이터와 업무 규칙

### 6.1 데이터의 자리

```text
사무실 조직 1개
└─ 건물 여러 개
   └─ 호실 여러 개
      └─ 매물 회차 여러 개
         ├─ 상담 여러 건
         ├─ 계약 여러 건
         ├─ 광고 채널 여러 건
         └─ 사진 여러 장 (향후 1차 후반 또는 2차)
```

| 데이터 | 저장 내용 | 중요한 원칙 |
|---|---|---|
| 조직 | 사무실 단위 | 모든 업무 데이터의 소유 범위 |
| 건물 | 주소, 주차, 엘리베이터, 공동 정보 | 여러 호실 공통 정보만 저장 |
| 호실 | 호수, 구조, 방향, 고정 옵션 | 대체로 바뀌지 않는 정보 |
| 매물 회차 | 상태, 가격, 입주, 현장·사진 상태 | 이번 매물 조건 |
| 상담 | 고객 조건, 진행 단계, 다음 연락 | 매물 회차에 연결 가능, 일반 상담도 허용 |
| 계약 | 기간, 일정, 상태, 중개 방식 | 반드시 매물 회차에 연결 |
| 광고 | 채널별 현재 상태 | 광고 이력·비용은 1차 제외 |

### 6.2 최신 매물 정보 수정 기준

| 상황 | 처리 |
|---|---|
| 월세·보증금·관리비·입주일 변경 | 최신 매물 기록 수정 |
| 사진 촬영·청소·도배·수리 상태 변경 | 최신 매물 기록 수정 |
| 같은 호실의 연락처·방문 방식·옵션 정정 | 건물 또는 호실 기본 정보 수정 |
| 매물이 사라져 실제 계약 여부를 모름 | `확인 필요` 또는 `보류` |
| 실제 계약 완료 | 계약 완료 처리 후 매물 종료 |
| 잘못 만든 매물 | 정보 오류 종료 또는 명시적 완전 삭제 |

최신 정보 수정으로 인해 계약·상담·광고 연결 기록이 끊기면 안 된다.

## 7. 화면 원칙과 1차 화면 구성

### 7.1 공통 UX 원칙

- SaaS 품질의 정돈된 화면을 사용하되, 업무 화면은 카드보다 표와 검색을 우선한다.
- 필수 입력은 먼저, 드물게 쓰는 정보는 상세 영역에 둔다.
- 저장·수정·종료·삭제 버튼은 결과가 분명하게 구분돼야 한다.
- 저장 실패 시 입력값을 지우지 않는다.
- 중요한 상태는 색만으로 구분하지 않고 텍스트로 함께 표시한다.
- 모바일에서는 등록·조회·오늘 할 일을 우선 지원하되, 복잡한 표 편집은 데스크톱을 기준으로 설계한다.

### 7.2 1차 메뉴

| 메뉴 | 핵심 목적 |
|---|---|
| 오늘 할 일 | 오늘·지연·상시 확인 필요 업무를 우선 처리 |
| 매물 현황 | 검색·필터·현재 매물 빠른 수정·Excel |
| 매물 등록·수정 | 신규 등록, 새 호실, 기존 호실 최신 정보 수정 |
| 건물·호실 관리 | 고정정보·옵션·과거 이력 확인·정정 |
| 상담관리 | 신규 문의와 후속 상담·다음 연락 관리 |
| 계약관리 | 계약 상태·일정·만료 관리 |
| 광고관리 | 광고 채널 현황과 광고문구 생성 |

## 8. 개발 모드와 운영 전환 원칙

### 8.1 개발 모드

개발 속도를 위해 아래 조건으로 시작한다.

| 항목 | 개발 기준 |
|---|---|
| Clerk | 개발 인스턴스 사용 |
| Supabase | 운영용과 분리된 개발 프로젝트 사용 |
| RLS | 초기 CRUD 개발 기간에는 임시 비활성화 가능 |
| 데이터 | 가상의 건물·호실·가격·연락처만 사용 |
| Vercel | Preview 배포 가능, 실제 업무 데이터 입력 금지 |
| 사용자 역할 | 로그인 진입 확인을 우선, 세부 역할은 보류 |

### 8.2 개발 모드의 절대 금지 사항

- 실제 임대인·세입자·상담 고객 연락처 입력
- 실제 공동현관·방문 비밀번호·열쇠 위치 입력
- 실제 계약금·잔금·내부 메모 입력
- 개발 Supabase 프로젝트를 실제 업무 원본으로 사용
- RLS가 꺼진 상태에서 운영 도메인에 실제 서비스를 공개

### 8.3 운영 전환의 필수 조건

실제 데이터를 넣기 전 아래를 모두 완료한다.

1. Clerk 운영 인스턴스와 운영용 환경변수 연결
2. Supabase 운영 프로젝트 분리
3. 모든 업무 테이블에 `organization_id`와 작성·수정 사용자 식별값 적용
4. RLS 활성화 및 조직 범위 정책 적용
5. 로그인하지 않은 사용자의 모든 업무 경로 접근 차단 확인
6. 개인 연락처·비밀번호·내부 메모의 화면·Excel 노출 규칙 확인
7. Vercel Preview와 Production 환경변수 분리
8. 테스트 데이터 제거 또는 운영 데이터와 분리

운영 전환 전에 RLS와 데이터 접근 정책이 완성되지 않으면 실제 업무 데이터는 입력하지 않는다.

## 9. 기술 방향

| 영역 | 1차 결정 | 역할 |
|---|---|---|
| 프레임워크 | Next.js 16 App Router | 화면·서버 기능·라우팅 |
| UI | React + TypeScript 5.x | 컴포넌트와 업무 상태 관리 |
| 디자인 시스템 | Tailwind CSS + shadcn/ui | 정돈된 폼·표·다이얼로그·필터 |
| 로그인 | Clerk | 로그인·세션·사용자 관리 |
| 데이터 | Supabase Postgres | 중앙 업무 데이터 |
| 파일 | Supabase Storage | 향후 매물 사진 |
| 배포 | Vercel | Preview·Production 배포 |
| 입력 검증 | Zod + React Hook Form | 날짜·금액·필수값 오류 방지 |
| 표 | TanStack Table | 매물·상담·계약의 검색·필터·정렬 |

### 9.1 파이썬 사용 원칙

웹서비스의 일상 업무 로직은 TypeScript로 통일한다.

- 오늘 할 일 계산
- 금액·날짜 입력 검사
- 매물·계약·상담 저장 규칙
- 광고 문구 템플릿 조합
- Excel 내보내기

파이썬은 사진 일괄 보정, OCR, 복잡한 성과 분석, 대량 데이터 정리처럼 별도 분석 작업이 실제로 필요해질 때만 독립 기능으로 추가한다. 1차 웹서비스의 상시 서버로 운영하지 않는다.

## 13. 수용 기준

### 개발 단계 수용 기준

- Clerk 개발 계정으로 로그인·로그아웃이 된다.
- 로그인하지 않으면 업무 화면을 볼 수 없다.
- 테스트 데이터로 건물·호실·첫 매물을 저장할 수 있다.
- 같은 건물에 같은 호실을 중복 등록할 수 없다.
- 기존 호실의 최신 조건을 수정해도 연결된 기록이 유지된다.
- 매물 현황에서 검색·필터·종료 처리가 된다.
- 상담·계약 일정이 오늘 할 일에 표시된다.
- 개발 DB와 기존 Streamlit 운영 DB가 섞이지 않는다.

### 운영 전환 수용 기준

- 운영 Clerk와 운영 Supabase 프로젝트가 개발 환경과 분리돼 있다.
- RLS를 활성화한 뒤 로그인 사용자만 자기 조직 데이터를 읽고 수정할 수 있다.
- 실제 연락처·비밀번호·내부 메모가 기본 목록과 권한 없는 내보내기에 표시되지 않는다.
- 데스크톱과 모바일 브라우저에서 핵심 조회·등록 흐름이 정상 동작한다.
- 실제 사용자가 설명 없이 신규 매물 등록과 기존 호실 최신 정보 수정을 끝낼 수 있다.
