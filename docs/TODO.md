## 0. 재빌드 기반 — 로그인과 공통 화면

**목적:** 새 기능을 만들기 전에, 직원이 로그인하고 동일한 화면 틀에서 업무를 시작할 수 있게 한다.

**이번 단계의 입력·처리:** Clerk Development 계정 로그인 여부를 확인하고, 로그인하지 않은 사람은 업무 화면을 볼 수 없게 한다. DB 데이터는 아직 만들거나 변경하지 않는다.

### 0-1. 프로젝트 뼈대

- [ ] Next.js + TypeScript + Tailwind 프로젝트를 새로 만든다.
- [ ] 패키지 설치 명령과 lint, typecheck, build 명령을 준비한다.
- [ ] `.env.local`이 Git에 올라가지 않도록 확인한다. 값 자체는 화면이나 로그에 표시하지 않는다.
- [ ] `app`, `components/ui`, `components/shared`, `features`, `lib` 기본 폴더를 만든다.
- [ ] `app/**/page.tsx`에는 화면 조립만 두고, 큰 화면 요소는 기능별 컴포넌트로 나눌 기준을 정한다.
- [ ] 각 기능을 `features/<기능>/components`, `server`, `schemas`로 나누고, 한 파일에 화면·검증·DB 처리·다이얼로그를 함께 넣지 않는 구조를 적용한다.
- [ ] `REBUILD_MASTER_SPEC.md`의 확정 폴더 트리를 만든 뒤, 페이지·공통 UI·업무 기능·공통 함수의 위치가 기준과 맞는지 확인한다.

### 0-2. 로그인과 접근 제한

- [ ] Clerk Development 로그인·로그아웃 화면을 연결한다.
- [ ] 로그인하지 않은 사용자가 `/dashboard`, `/listings` 같은 업무 주소를 직접 열어도 로그인 화면으로 이동하는지 확인한다.
- [ ] 로그인 후 기본 시작 주소를 `/dashboard`로 정한다.
- [ ] 활성 멤버십이 없는 계정, 비활성 계정의 안내 화면을 준비한다.
- [ ] 이 단계에서는 사용자 초대·조직 선택 화면을 만들지 않는다.

### 0-3. 공통 앱 화면과 디자인 가이드 적용

- [ ] `docs/Design_guide/`의 승인 시안에서 공통 색상·글꼴·여백·상태 표시 기준을 확인한다.
- [ ] 데스크톱 사이드바, 모바일 메뉴, 상단 사용자 메뉴를 공통 `AppShell`로 구현한다.
- [ ] `PageHeader`, `StatusBadge`, 표 바깥틀, 숫자·금액 표시, 민감 정보 접기 부품을 공통으로 만든다.
- [ ] 로딩 중, 데이터 없음, 저장 중, 오류, 권한 없음, 삭제·상태 변경 확인 창을 공통 상태로 준비한다.
- [ ] 기본 목록에는 연락처·출입 비밀번호·내부 메모를 표시하지 않는 공통 규칙을 적용한다.

**완료 확인**

- [ ] 로그인 전 업무 화면 접근이 막힌다.
- [ ] 로그인한 개발용 계정이 빈 대시보드 화면을 연다.
- [ ] 데스크톱과 휴대폰 크기에서 메뉴를 열고 닫을 수 있다.
- [ ] lint, typecheck, build 결과를 기록한다.
- [ ] 실제 생성된 폴더 구조가 확정 폴더 트리와 일치하는지 확인한다.

**이번 단계 제외:** 실제 매물 조회·저장, DB migration 적용, 실제 업무 데이터 입력.

## 1. P0 데이터 모델 — DB 파일 작성과 Dev 적용 준비

**목적:** 건물 → 호실 → 매물의 기본 관계와 조직 분리를 DB에서 안전하게 지킬 수 있게 한다.

**중요:** 여기서는 migration 파일을 작성하는 것까지다. Dev DB 초기화나 migration 적용은 사용자의 별도 승인 뒤에만 한다.

### 1-1. P0 데이터 항목 확정

- [ ] `organizations`, `organization_members`의 최소 항목과 admin/staff, active/inactive 기준을 확정한다.
- [ ] `buildings`에 주소·공동 정보·공통 민감 정보의 저장 위치를 확정한다.
- [ ] `units`에 호수·구조·방향·옵션·방문 관련 정보의 저장 위치를 확정한다.
- [ ] `listings`에 현재 상태·가격·관리비·입주 조건·사진 보유 여부·재확인일·현장 상태·보유처의 저장 기준을 확정한다.
- [ ] `listings.property_type`에 원룸·투룸·아파트·오피스텔·상가·사무실을 구분할 기준을 확정한다. P0 입력 화면은 원룸·투룸만 대상으로 한다.
- [ ] 주거형 방 구조와 모든 매물에 공통인 면적·층·가격·관리비 항목을 구분한다.
- [ ] 모든 업무 테이블의 `organization_id`, 생성·수정 시각, 생성·수정 사용자 기록 원칙을 확정한다.
- [ ] 금액은 만원 단위 정수, 날짜는 시간 없는 날짜로 저장하는지 확인한다.

### 1-2. P0 migration 파일 작성

- [ ] 조직과 멤버십 migration을 작성한다.
- [ ] 건물·호실·매물 migration을 작성한다.
- [ ] 같은 조직 안에서 건물 중복을 막는 규칙을 작성한다.
- [ ] `302`와 `302호`를 같은 호실로 처리하는 중복 방지 규칙을 작성한다.
- [ ] 호실당 현재 매물은 한 건만 허용하는 규칙을 작성한다.
- [ ] 금액·상태·날짜의 잘못된 값을 막는 규칙을 작성한다.
- [ ] 일반 매물 수정은 같은 현재 매물 행을 수정한다는 저장 규칙을 작성한다.
- [ ] migration 파일별 목적과 **작성만 완료 / Dev 적용 완료** 상태를 문서에 기록한다.

### 1-3. Dev DB 적용 승인 전 확인

- [ ] 가공 조직 A/B, admin/staff, 건물·호실·매물 가공 seed 계획을 작성한다.
- [ ] seed에는 실제 고객·계약·출입 정보가 없음을 확인한다.
- [ ] Dev DB를 초기화할 경우 영향받는 대상이 Dev 프로젝트뿐인지 확인한다.
- [ ] Production Supabase, Clerk Production, 기존 Streamlit SQLite가 대상에서 제외됐는지 확인한다.
- [ ] 사용자에게 Dev DB 초기화·migration 적용 승인을 요청한다.

**완료 확인**

- [ ] migration 파일만으로 빈 Dev DB에 적용할 순서가 명확하다.
- [ ] 다른 조직의 건물·호실·매물을 연결할 수 없게 설계됐다.
- [ ] 일반 수정으로 새 매물이 만들어지지 않게 설계됐다.

**이번 단계 제외:** Dev DB 실제 초기화·적용, 매물 화면 구현, 상담·계약·광고 테이블.

**향후 확장 메모:** 아파트 단지·동·공급면적, 상가 권리금·부가세·용도, 오피스텔 전용 항목은 실제 도입 승인 뒤 별도 migration·화면·테스트 작업으로 추가한다.

## 2. P0 매물 업무 — 등록·검색·수정·건물 관리

**목적:** 매일 쓰는 매물 업무를 먼저 완성한다. 직원이 매물을 새로 등록하고, 찾고, 확인하고, 현재 정보를 안전하게 고칠 수 있어야 한다.

**시작 조건:** 단계 1 migration이 Dev DB에 적용됐고, 가공 seed가 준비된 상태.

### 2-1. 매물 목록과 검색

- [ ] 로그인 사용자의 활성 조직 매물만 서버에서 조회한다.
- [ ] 목록에 상태, 건물명, 주소, 호실, 구조, 보증금, 월세, 관리비, 입주 조건, 매물번호를 표시한다.
- [ ] 연락처·출입 정보·내부 메모는 목록 조회와 표시에서 제외한다.
- [ ] 건물명·주소·호실·매물번호 검색을 구현하고 검색 조건을 URL에 남긴다.
- [ ] 상태, 거래 유형, 입주 조건, 가격 범위, 보유처, 사진 보유 여부, 재확인일 필터를 구현한다.
- [ ] 빈 결과, 필터 초기화, DB 오류 시 다시 시도 안내를 구현한다.
- [ ] 휴대폰에서는 같은 데이터를 카드 형태로 표시한다.

### 2-2. 신규 매물 등록

- [ ] 기존 건물 선택과 새 건물 입력을 제공한다.
- [ ] 선택 건물의 기존 호실 선택과 새 호실 입력을 제공한다.
- [ ] 새 건물 → 새 호실 → 현재 매물을 한 번에 저장하는 DB 함수를 작성한다.
- [ ] 같은 호실에 현재 매물이 있으면 선택 단계와 저장 단계 모두에서 막는다.
- [ ] 가격·관리비·거래 유형·입주 조건·보유처·사진 보유 여부·재확인일·현장 상태를 검증한다.
- [ ] 저장 중 중복 클릭을 막고, 입력 오류를 해당 칸 근처에 표시한다.
- [ ] 저장 성공 뒤 새 매물 상세로 이동한다.
- [ ] 취소·이탈 시 입력 손실 안내와 브라우저 확인을 한다.

### 2-3. 상세와 수정

- [ ] 로그인 조직의 현재 매물만 상세에서 열리게 한다.
- [ ] 건물·호실·주소·가격·관리비·입주 조건·구조·보유처·사진·재확인·현장 상태를 표시한다.
- [ ] 내부 메모, 연락처, 출입 정보는 기본 접힘으로 표시한다.
- [ ] 가격·관리비·상태·입주 가능일·내부 메모와 확인 업무 값을 수정한다.
- [ ] 서버가 로그인·활성 멤버십·같은 조직·현재 매물 한 건을 다시 확인한 뒤 저장한다.
- [ ] 저장 뒤 목록과 상세에 바뀐 값이 반영되는지 확인한다.

### 2-4. 빠른 수정·건물/호실 관리·이력

- [ ] 목록에서 상태·사진 보유 여부·재확인일·매물 보유처만 빠르게 수정한다.
- [ ] 건물 공통 정보와 호실 고정 정보를 별도 관리 화면에서 수정한다.
- [ ] 호실의 현재 매물과 종료된 과거 매물 이력을 확인한다.
- [ ] 연결된 상담·계약이 있는 매물 삭제 시, 삭제 영향과 상태 변경 대안을 먼저 보여 준다.

**완료 확인**

- [ ] 새/기존 건물과 새/기존 호실 조합 모두로 가공 매물을 등록한다.
- [ ] 중복 호실·현재 매물·잘못된 금액·잘못된 날짜가 저장되지 않는다.
- [ ] 검색 → 상세 → 수정 → 목록 반영이 PC와 휴대폰에서 된다.
- [ ] 일반 수정으로 새 매물·상담·계약 기록이 만들어지거나 삭제되지 않는다.
- [ ] 다른 조직 매물과 민감 정보가 기본 목록에서 보이지 않는다.

**이번 단계 제외:** 상담·계약 저장, 오늘 할 일, 광고비, Excel, 사진 파일 업로드.

## 3. P1 상담 관리 — 문의와 후속 연락

**목적:** 일반 문의와 매물 문의를 기록하고, 다음 연락과 후속 통화·문자·방문 내용을 놓치지 않는다.

### 3-1. 데이터와 저장 규칙

- [ ] 상담과 후속 상담 이력 migration을 작성한다.
- [ ] 최초 문의 매물은 선택 사항이며, 일반 상담은 매물 없이 저장할 수 있게 한다.
- [ ] 고객 식별명·연락처·유입 경로·희망 조건·상담일·다음 연락일·상태·메모 저장 기준을 확정한다.
- [ ] 전화·문자·방문·기타 후속 이력의 날짜·결과·내용·종료 사유 저장 기준을 확정한다.
- [ ] 상담 종료 시 다음 연락일을 해제하는 규칙을 구현한다.
- [ ] 연락처와 상담 내용이 매물 목록·오늘 할 일 기본 표에 나오지 않게 한다.

### 3-2. 화면과 업무 흐름

- [ ] 상담 목록의 검색·상태·유입 경로·다음 연락 필요 필터를 구현한다.
- [ ] 일반 상담과 매물 연결 상담의 등록·수정을 구현한다.
- [ ] 상담 상세에서 최초 문의 매물, 후속 이력, 다음 연락일, 계약 연결 결과를 보여 준다.
- [ ] 후속 통화·문자·방문 이력을 누적하고, 수정·삭제 때 최신 요약을 다시 계산한다.
- [ ] 일반 상담을 나중에 최초 문의 매물과 연결할 수 있게 한다.

**완료 확인**

- [ ] 매물 없는 일반 상담과 매물 연결 상담이 모두 저장된다.
- [ ] 후속 이력이 최초 상담 내용을 덮어쓰지 않는다.
- [ ] 다음 연락일이 있는 진행 상담만 다음 단계의 오늘 할 일에 나타난다.
- [ ] 연락처는 필요한 상담 화면에서만 제한적으로 보인다.

**이번 단계 제외:** 자동 문자 발송, 고객 공개 페이지, AI 고객 추천.

## 4. P1 계약 관리 — 일정·상태·출처 상담

**목적:** 실제 계약 매물, 계약 일정, 금액, 중개 방식, 출처 상담을 한 기록으로 관리하고 잘못된 상태 변경을 막는다.

### 4-1. 데이터와 저장 규칙

- [ ] 계약과 계약 단계 이력 migration을 작성한다.
- [ ] 실제 계약 매물은 필수, 출처 상담은 선택으로 한다.
- [ ] 계약 유형·중개 방식·계약 진행일·정식 계약일·입주일·만료일·계약 상태 저장 기준을 확정한다.
- [ ] 계약금 전체·가계약금·추가 수령 예정일·잔금·잔금 예정일의 금액·날짜 검증을 구현한다.
- [ ] 가계약·정식계약·잔금 예정·계약 완료·해지 단계 이력을 누적한다.
- [ ] 계약과 출처 상담의 최초 문의 매물이 달라도 저장을 막지 않는다.

### 4-2. 화면과 상태 변경 확인

- [ ] 계약 목록·검색·상태·일정 필터를 구현한다.
- [ ] 매물 또는 상담 상세에서 계약 등록으로 이동할 수 있게 한다.
- [ ] 계약 상세에서 연결 매물·출처 상담·일정·금액·단계 이력을 보여 준다.
- [ ] 계약 완료·해지·만료 때 영향을 받는 매물·상담 상태를 확인 창에 설명한다.
- [ ] 사용자가 확인한 경우에만 연결 매물 상태 또는 출처 상담 상태를 반영한다.
- [ ] 계약 기록을 삭제하는 경우 매물·상담 원본은 삭제하지 않는다.

**완료 확인**

- [ ] 계약이 실제 계약 매물과 선택한 출처 상담에 정상 연결된다.
- [ ] 계약 완료·해지 자체만으로 매물 상태가 몰래 바뀌지 않는다.
- [ ] 사용자가 상태 반영을 확인하면 선택한 결과만 저장된다.
- [ ] 날짜·금액 오류가 저장되지 않고, 계약 이력이 보존된다.

**이번 단계 제외:** 다건 입금 내역, 수수료 자동 계산, 계약서·신분증 파일 저장.

## 5. P1 오늘 할 일 — 오늘·지연 업무와 완료 체크

**목적:** 매물 재확인, 사진·현장 확인, 퇴실, 계약 일정, 상담 다음 연락을 날짜 기준으로 한 화면에서 확인한다.

### 5-1. 업무 계산

- [ ] 매물 재확인일이 오늘이면 오늘, 과거면 지연 업무가 되게 한다.
- [ ] 사진 보유 여부와 현장 상태에 따른 확인 필요 업무를 계산한다.
- [ ] 퇴실 예정 D-7·당일, 계약금·잔금·계약 종료일 같은 계약 일정을 계산한다.
- [ ] 진행 중 상담의 다음 연락일을 오늘·지연 업무로 계산한다.
- [ ] 광고비와 광고 문구 생성은 오늘 할 일에 자동으로 넣지 않는다.

### 5-2. 완료 체크와 화면

- [ ] 계산된 업무의 완료 여부만 저장하는 `task_completions` migration을 작성한다.
- [ ] 완료 체크가 원본 매물·상담·계약의 날짜나 상태를 바꾸지 않게 한다.
- [ ] 완료 업무는 기본으로 숨기고 필요할 때 다시 볼 수 있게 한다.
- [ ] 각 업무에서 원래 매물·상담·계약 상세로 이동하게 한다.
- [ ] 기본 표에 연락처·비밀번호·내부 메모가 나오지 않게 한다.

**완료 확인**

- [ ] 기준 날짜를 바꾸면 오늘과 지연 업무가 정확히 나뉜다.
- [ ] 완료 체크·해제 뒤 원본 기록이 바뀌지 않는다.
- [ ] 상담·계약·매물 업무가 원래 상세 화면으로 연결된다.

**이번 단계 제외:** SMS·카카오 알림, 개인별 푸시 알림, 별도 할 일 직접 입력.

## 6. P1 광고비·광고 문구·Excel 내보내기

**목적:** Streamlit에서 쓰던 월별 광고비 기록, 직접입력 문구 생성, 업무용 자료 내보내기를 웹에서도 제공한다.

### 6-1. 월별 광고비

- [ ] `monthly_advertising_costs` migration을 작성한다.
- [ ] 기준연월·채널·월 광고비·메모를 저장한다.
- [ ] 같은 기준연월과 채널은 한 건만 저장하고, 다시 입력하면 수정한다.
- [ ] 광고비는 매물·상담·계약과 자동 연결하거나 성과를 계산하지 않는다.

### 6-2. 직접입력형 광고 문구

- [ ] 지역·방 형태·가격·입주 조건·옵션·강조점 입력 화면을 구현한다.
- [ ] 사실 확인되지 않은 거리·도보 시간·옵션을 자동으로 넣지 않게 한다.
- [ ] 제목과 본문을 생성 뒤 사용자가 직접 수정하고 복사할 수 있게 한다.
- [ ] 입력값과 생성 결과를 DB에 저장하지 않는다.
- [ ] 비밀번호·연락처·내부 메모를 문구에 넣지 않도록 안내한다.

### 6-3. Excel 내보내기

- [ ] 매물·계약·상담·오늘 할 일 화면에서 현재 검색 결과만 내보내게 한다.
- [ ] 각 파일에 포함·제외할 민감 정보 기준을 문서로 확정한다.
- [ ] 파일 생성 전 외부 공유 금지 또는 내부 업무 전용 경고를 표시한다.
- [ ] 내보낸 파일에 비밀번호·내부 메모·불필요한 연락처가 섞이지 않는지 확인한다.

**완료 확인**

- [ ] 같은 월·채널 광고비 중복이 저장되지 않는다.
- [ ] 광고 문구를 만들거나 복사해도 DB 상태가 바뀌지 않는다.
- [ ] 각 Excel 파일에 허용되지 않은 민감 정보가 포함되지 않는다.

**이번 단계 제외:** 매물별 광고 채널 상태, 외부 광고 등록, 광고 클릭·전환 성과 분석.

## 7. P2 통합 검증·Preview·Production 전환

**목적:** 실제 업무를 시작하기 전에 권한·조직 분리·화면 사용성·Production 보안을 확인한다.

### 7-1. 가공 계정과 업무 흐름 검증

- [ ] admin, staff, inactive, 멤버 없음, 다른 조직 가공 계정을 준비한다.
- [ ] 각 계정이 허용된 화면과 데이터만 접근하는지 확인한다.
- [ ] PC에서 매물 등록 → 검색 → 수정 → 상담 → 계약 → 오늘 할 일을 확인한다.
- [ ] 휴대폰에서 로그인 → 검색 → 상세 확인 → 간단 수정을 확인한다.
- [ ] 저장 중 중복 클릭, 빈 화면, 오류, 권한 없음, 확인 창을 점검한다.

### 7-2. Preview·Production 준비

- [ ] Preview가 Dev·Production과 다른 Clerk·Supabase 환경을 쓰는지 확인한다.
- [ ] Preview와 Dev에 실제 데이터가 없는지 확인한다.
- [ ] Clerk Production, Supabase Production, Vercel Production을 분리 준비한다.
- [ ] Clerk–Supabase Native Integration과 Production RLS를 준비한다.
- [ ] 조직별 SELECT·INSERT·UPDATE·DELETE와 INSERT/UPDATE `WITH CHECK` 정책을 검증한다.
- [ ] 일반 CRUD가 secret/service-role 키를 사용하지 않는지 확인한다.

### 7-3. 운영 시작 승인

- [ ] lint, typecheck, build, 관련 테스트 결과를 기록한다.
- [ ] 수용 테스트의 Blocker·Critical 오류가 0건인지 확인한다.
- [ ] Production 릴리스 체크리스트를 완료한다.
- [ ] 운영 조직과 첫 admin·staff의 접근 방식을 승인한다.
- [ ] 실제 데이터는 웹에서 새로 등록하는 방식이 준비됐는지 확인한다.

**완료 확인**

- [ ] 다른 조직·비활성·미로그인 사용자가 업무 데이터를 볼 수 없다.
- [ ] Production RLS와 조직 분리 테스트를 통과한다.
- [ ] 실제 데이터 입력 전 모든 필수 테스트가 통과한다.
