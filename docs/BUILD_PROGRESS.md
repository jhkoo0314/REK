# 웹 재빌드 진행 현황

> 최종 갱신: 2026-08-26
>
> 기준: `REBUILD_MASTER_SPEC.md`

## 현재 상태

- Streamlit 시스템을 기준으로 웹을 처음부터 다시 구현하기로 결정했다.
- 기존 Next.js 코드·가공 화면·기존 기능 구현은 재사용하지 않는다.
- Clerk·Supabase의 원격 설정, 로컬 `.env.local`, `docs/Design_guide/`, 문서와 Git 이력은 보존한다.
- 기존 로컬 migration과 seed는 재빌드 기준으로 삭제했다. Dev DB의 초기화·새 migration 적용은 아직 승인되지 않았다.
- 기존 Streamlit SQLite 데이터는 읽기 전용으로 보관하며 자동 이관하지 않는다.
- 화면 컨셉을 목록 중심 부동산 업무 CRM으로 확정했다. 상담 관리를 대표 업무 화면과 로그인 후 시작 화면으로, 매물 관리를 상담에 제시할 재고 관리로 정했다.
- 오늘 예정 업무는 대시보드가 아니라 오늘·지연 업무를 원래 상담·계약·매물 기록으로 연결하는 작은 보조 화면으로 정했다.
- 루트 폴더에 Next.js 16·TypeScript·Tailwind 기반과 Clerk Development 로그인·보호된 업무 화면 그룹을 구현했다. Supabase DB는 변경하지 않았다.
- 가공 목업 데이터로 상담 중심 CRM의 주요 화면과 상담 → 매물 검색 → 제안 → 계약 연결 흐름을 구현했다. 실제 저장 기능은 없다.
- Streamlit 상담 관리의 일반 상담/매물 상담 구분과 고객·상담·희망 조건·다음 연락일 입력 흐름을 확인해, 웹의 `새 상담 등록` 저장 전 목업 화면에 반영했다.
- P0 데이터 항목을 확정했다. 조직·멤버, 건물, 호실, 매물, 제한 연락처, 호실 출입 정보의 상태값·중복 규칙·금액·날짜 기준은 `P0_DATA_FIELD_SPEC.md`를 따른다. DB는 아직 변경하지 않았다.
- P0 migration 파일 `20260826000100_create_p0_core_schema.sql`을 작성했다. 이 파일에는 Dev RLS 명시적 비활성화와 가공 연락처·출입 비밀번호의 제한 테이블이 포함된다. 사용자가 Supabase Dev에 수동 적용했고, Production에는 적용하지 않았다.
- `DEV_DB_APPLY_PRECHECK.md`에 가공 seed와 초기화 영향 범위를 기록했다. seed 입력·제약 검증은 아직 하지 않았다.
- 새 출발 기준의 Dev 초기화·migration 수동 적용 절차는 `DEV_DB_RESET_AND_APPLY.md`에 기록했고, 사용자가 Dev에 적용을 완료했다. Production에는 적용하지 않는다.
- 2-1 매물 목록·검색 구현을 완료했다. 서버가 Clerk 활성 조직과 DB active 멤버십을 확인하고 현재 조직의 매물만 읽으며, 검색·필터 조건은 URL에 남긴다. `M-000001` 표시번호용 추가 migration과 가공 seed 적용·실조회 검증은 남아 있다.
- 2-2 신규 매물 등록 화면과 서버 저장 처리를 구현했고, 사용자가 브라우저에서 정상 동작을 확인했다. 저장 뒤 매물 상세 화면으로 이동하는 기능은 2-3에서 구현한다.
- 2-3 매물 상세·수정의 기본 흐름을 구현했다. 목록의 상세 보기에서 현재 조직의 매물만 열리며, 가격·상태·입주일·사진·확인 상태 등을 같은 현재 매물에 수정한다. 브라우저 저장·목록 반영 확인은 남아 있다.
- 매물 등록·수정 화면에 세대 비밀번호 제한 입력칸을 추가했다. 일반 목록·상세에서는 보이지 않으며, 신규 등록 시 별도 제한 테이블에 저장하려면 `20260826000600` migration을 Dev에 수동 적용해야 한다.
- 목록 행의 `비밀번호 보기`는 필요할 때만 서버에서 같은 조직의 해당 호실 비밀번호를 읽어 작은 확인창에 표시·복사한다. 목록 데이터 자체에는 비밀번호를 포함하지 않는다.
- 매물 등록·수정 화면에 임대인·세입자 연락처 제한 입력칸을 추가했다. 임대인은 건물 기준, 세입자는 호실 기준으로 분리한다. 세입자 호실 연락처 테이블을 만드는 `20260826000700` migration은 Dev 수동 적용 대기다.
- 현재 매물 조건에서 현장 상태 입력을 제거했다. 입주 조건은 즉시 가능·날짜 지정·확인 필요로 구분하며, 이 값을 위한 `20260826000800` migration은 Dev 수동 적용 대기다.
- 원룸·투룸 P0 화면에서는 전용면적 입력·표시를 제거했다. DB의 `listings.exclusive_area_m2` 칼럼은 아파트 등 후속 확장을 위해 보존하며, 기존 저장값은 수정 시 변경하지 않는다.
- 2-3 상세·수정·목록 반영은 브라우저에서 정상 확인 완료로 기록했다. 2-4는 목록의 빠른 수정부터 구현했으며, 상태·사진 상태·재확인일·보유처를 상세 이동 없이 수정할 수 있다.
- Clerk Development의 `REK_test` 조직과 현재 로그인한 사용자 1명을 Dev DB에 active admin으로 연결했다. 가공 건물·호실·매물 seed와 실제 목록·등록 검증은 남아 있다.
- 신규 매물 입력에서 숫자 호실의 층 자동 제안, 방향 선택값, 현재 매물 조건의 방 구조 표시를 반영했다. 호실 단계의 방 구조 입력은 제거했다. 방 구조는 원룸·투룸·투베이·쓰리룸·주인세대를 선택할 수 있으며, 추가 3개 값의 Dev DB 저장을 위한 `20260826000500` migration은 수동 적용 대기다.

## 이번 재빌드에서 확인한 사항

- 기존 웹 구현은 매물 P0 일부와 가공 화면이 섞여 있어, Streamlit 기능 기준으로 이어서 확장하면 문서·데이터·화면 기준이 달라질 위험이 있다.
- 따라서 코드만 비우고, 새 기준서와 실행 목록을 먼저 작성한 뒤 P0부터 다시 구현하는 방식이 적절하다.
- Streamlit의 광고 기능은 매물별 광고 상태가 아니라 월별 광고비와 직접입력형·비저장 문구 생성이다.
- 기존 1~13 문서는 이전 구현·축소 MVP·삭제된 migration을 함께 전제하고 있어 재빌드 기준으로 전면 교체했다. 이전 계획 문서 `TASK.md`, `MVP_REBUILD_PLAN.md`, `DEV_DB_SCHEMA_PENDING.md`는 제거했다.

## 다음 안전한 작업

2. 사용자의 별도 승인 후에만 Dev DB 초기화·migration 적용·가공 seed를 실행한다.

## 확인 결과

- 이번 작업에는 루트 Next.js 기반, Clerk Development 로그인, 보호된 업무 화면 그룹, 공통 App Shell 구현이 포함된다.
- DB migration 적용, RLS 변경, 배포, Git push, 실제 데이터 입력은 수행하지 않았다.
