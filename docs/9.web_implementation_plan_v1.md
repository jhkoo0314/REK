# 부동산 매물관리 웹서비스 — 구현 계획서 v1.0

> **2026-08-25 범위 정렬:** 웹 프로젝트의 기능 기준은 현재 `C:\realestate-main` Streamlit 시스템이다. P0에는 매물 기본 흐름 뒤 사진 보유 여부·재확인·현장 상태·보유처·빠른 수정·건물/호실 관리와 이력 확인을 포함한다. P1에는 상담 후속 이력, 계약 일정·단계 이력, 오늘 할 일 완료 체크, 월별 광고비·직접입력형 광고 문구·Excel 내보내기를 포함한다. 매물별 광고 채널 상태 관리, 사진 파일 업로드, 외부 광고 자동 등록, 성과 분석은 이번 전환 범위에서 제외한다. 이 기준은 이 문서의 상충되는 이전 설명보다 우선한다.

> 이 문서는 이전 구현 계획이다. 재빌드의 실제 순서·상태는 `REBUILD_MASTER_SPEC.md`, `TODO.md`, `BUILD_PROGRESS.md`에서 관리한다.

## 1. 문서 목적

이 문서는 앞서 확정한 기획·데이터·화면·기술 문서를 실제 개발 순서로 바꾼 실행 계획서다. 핵심 원칙은 다음과 같다.

- 현재 사용 중인 Streamlit 프로그램을 당장 중단하지 않는다.
- 가장 자주 쓰는 매물 업무를 먼저 웹에서 검증한다.
- 상담·계약·광고는 매물 업무가 안정된 뒤 연결한다.
- 실제 데이터와 Production 보안 전환은 기능 검증이 끝난 뒤에만 진행한다.

### 현재 구현 위치 (2026-08-18)

P0 매물 관리 진행 중이다. Dev DB migration `0001`~`0004`와 가공 seed를 적용했고, 로그인 조직의 매물 목록 조회·검색·상태/거래 유형 필터·신규 매물 일괄 저장을 구현했다. 현재 매물 상세의 실제 조회와 기존 매물 수정은 아직 미구현이다.

### 단계 2 — Dev 데이터베이스와 매물 핵심 구조

### 목적

건물→호실→매물이라는 기본 구조를 Dev Supabase에 만들고, 화면이 사용할 타입과 데이터를 준비한다.

### 구현 범위

| 구분 | 구현 내용 |
| --- | --- |
| Migration | `organizations`, `organization_members`, `buildings`, `units`, `listings` 생성 |
| 공통 열 | `organization_id`, 생성·수정 시각, 생성·수정 사용자 필드 적용 |
| 제약 | 건물/호실/현재 매물 관계, 금액·상태·날짜의 기본 검증 |
| 타입 | DB 스키마 기반 TypeScript 타입 생성 |
| 테스트 데이터 | 가공 건물·호실·매물과 admin/staff 멤버 생성 |
| 개발 보안 | Dev에서만 RLS 비활성화 가능. 화면·서버는 조직 ID 구조를 유지 |

### 우선 확인할 업무 규칙

1. 한 건물에는 여러 호실이 있다.
2. 한 호실에는 과거 매물이 있을 수 있지만, 현재 매물은 중복되지 않는다.
3. 가격·상태·입주 가능일의 변경은 기존 현재 매물 수정이다.
4. 다른 조직의 건물·호실·매물은 선택 후보에도 나타나지 않는다.

### 완료 기준

- SQL migration을 새 Dev 프로젝트에 적용해 같은 구조를 재현할 수 있다.
- 가공 데이터로 건물·호실·매물 관계를 조회할 수 있다.
- 기존 매물 수정이 새로운 매물 레코드를 만들지 않는다.
- 데이터 구조와 TypeScript 타입의 핵심 항목이 일치한다.

### 단계 3 — 매물 관리 P0 완성

### 목적

현재 Streamlit에서 가장 자주 하는 “매물 등록·검색·수정”을 웹에서 실제로 할 수 있게 만든다.

### 구현 순서

| 순서 | 기능 | 핵심 확인점 |
| --- | --- | --- |
| 3-1 | 매물 목록 | 상태·건물/호실·임대 조건·입주 가능일을 한 표에서 판단 |
| 3-2 | 검색·필터 | 건물명·주소·호실·매물번호 검색, 상태·유형·가격대 필터 |
| 3-3 | 신규 매물 등록 | 건물 검색/등록 → 호실 선택/등록 → 매물 조건 저장 |
| 3-4 | 매물 상세 | 기본 정보, 최신 상태, 최근 수정 시각 표시 |
| 3-5 | 전체 수정 | 임대 조건·입주일·옵션·메모 수정 |
| 3-6 | 빠른 수정 | 상태·가격·입주 가능일만 목록에서 빠르게 변경 |
| 3-7 | 안전장치 | 중복 현재 매물 경고, 삭제 확인, 필수값·금액 검증 |

### P0 사용자 검증 시나리오

| 번호 | 사용자가 하는 일 | 통과 기준 |
| --- | --- | --- |
| L-01 | 주소 일부와 호실로 매물 검색 | 원하는 매물을 찾을 수 있다. |
| L-02 | 공실 매물만 필터 | 결과가 즉시 좁혀진다. |
| L-03 | 기존 건물의 새 호실 매물 등록 | 건물을 중복 생성하지 않는다. |
| L-04 | 기존 호실의 가격·입주일 변경 | 기존 매물이 수정되고 연결 정보가 유지된다. |
| L-05 | 같은 호실에 현재 매물 등록 시도 | 중복 경고와 기존 매물 이동 선택지가 보인다. |
| L-06 | 계약·상담 연결이 있는 매물 삭제 시도 | 삭제 대신 상태 변경을 우선 안내한다. |
| L-07 | 목록 → 상세 → 뒤로 이동 | 기존 검색·필터·스크롤 위치가 유지된다. |

### 완료 기준

- 10개 이상의 가공 매물을 등록·검색·수정하는 실사용 흐름이 막힘없이 진행된다.
- 핵심 열만 보고 공실·가격·입주 가능일을 판단할 수 있다.
- 금액·날짜·상태 오류가 저장 전에 표시된다.
- PC와 휴대폰에서 목록·상세·간단 수정이 가능하다.

### 단계 4 — 대시보드와 오늘 할 일 P1

### 목적

저장된 매물·상담·계약 정보를 “오늘 해야 할 행동”으로 바꾼다.

### 구현 범위

| 항목 | 입력 기준 | 화면 결과 |
| --- | --- | --- |
| 입주 확인 | 입주일, 완료 체크 | 오늘/지연 업무 표시 |
| 퇴실·공실 확인 | 퇴실 예정일·확인 필요일 | 처리 대상 표시 |
| 매물 현황 | 매물 상태 | 공실·입주 가능 예정·계약 진행 건수 |
| 완료 체크 | `task_completions` | 원본 매물 삭제 없이 완료 기록 |
| 업무 이동 | 업무 유형과 연결 기록 | 매물/상담/계약 상세로 바로 이동 |

### 구현 주의점

- 업무 목록은 단순한 알림이 아니라, 해당 기록을 열어 처리할 수 있어야 한다.
- 완료 체크를 해도 매물·상담·계약 원본 상태가 임의로 바뀌지 않는다.
- 지연 업무가 오늘 업무보다 먼저 보인다.

### 완료 기준

- 날짜와 상태가 다른 가공 데이터로 오늘·지연 업무가 정확히 구분된다.
- 완료 처리 후 같은 업무가 목록에서 적절히 사라지거나 완료 상태로 바뀐다.
- 대시보드 숫자를 누르면 해당 필터가 적용된 목록으로 이동한다.

### 단계 5 — 상담 관리 P1

### 목적

문의부터 후속 연락·방문·계약 연결까지의 상담 흐름을 기록한다.

### 구현 범위

| 기능 | 구현 기준 |
| --- | --- |
| 상담 등록 | 고객 식별명, 문의 채널, 희망 조건, 문의일, 메모 |
| 매물 연결 | 0개 이상 매물 연결 가능. 연결 매물은 같은 조직 안에서 검색 |
| 이력 추가 | 통화·문자·방문·매물 제안 등 유형과 내용 기록 |
| 다음 연락일 | 상담별 후속 연락일 지정, 오늘 할 일에 반영 |
| 상태 | 신규 문의, 조건 확인, 매물 제안, 방문 예정, 계약 진행, 보류, 종료 |
| 목록 | 상태·문의 채널·다음 연락일 필터, 연락처 기본 마스킹 |

### 사용자 검증 시나리오

| 사용자가 하는 일 | 통과 기준 |
| --- | --- |
| 새 문의 고객과 예산·입주일 입력 | 상담 목록에 신규 문의로 보인다. |
| 매물 2개를 제안하고 이력 등록 | 상담 상세에서 제안 매물과 이력을 확인할 수 있다. |
| 다음 연락일을 오늘로 설정 | 대시보드에 상담 후속 업무가 표시된다. |
| 고객이 타사에서 계약해 종료 | 종료 사유가 남고 일반 후속 목록에서 빠진다. |

### 완료 기준

- 상담 상세에서 “다음에 무엇을 해야 하는지”를 알 수 있다.
- 상담과 연결된 매물·계약을 서로 이동할 수 있다.
- 고객 연락처와 긴 메모가 목록에 불필요하게 노출되지 않는다.

### 단계 6 — 계약 관리 P1

### 목적

계약의 일정·금액·입금 확인을 매물과 연결하고, 광고 종료 같은 후속 행동을 놓치지 않는다.

### 구현 범위

| 기능 | 구현 기준 |
| --- | --- |
| 계약 등록 | 매물 필수 연결, 상담 선택 연결, 계약 조건·일정 입력 |
| 상태 관리 | 가계약/계약 진행/계약 완료/취소 등으로 관리 |
| 일정·입금 | 계약일, 잔금일, 입주일, 계약금·잔금 확인 여부 |
| 매물 연동 | 계약 완료·취소 시 매물 상태 변경을 제안하되 자동 확정하지 않음 |
| 목록 | 계약 상태·일정·입금 확인 필터 |
| 대시보드 | 당일 계약·입주·입금 확인 업무 표시 |

### 완료 기준

- 계약 하나를 매물과 상담에 연결해 등록·수정할 수 있다.
- 계약 상태가 바뀔 때 매물 상태 변경 여부를 선택할 수 있다.
- 오늘 확인해야 할 계약 일정과 미확인 입금이 대시보드에 나타난다.
- 계약 완료 매물의 광고 확인 작업이 생성된다.

---

### 단계 7 — 광고 현황과 문구 생성 P1

### 목적

광고를 직접 자동 등록하지 않고도, 매물별 채널 상태와 반복 문구 작성 업무를 줄인다.

### 구현 범위

| 기능 | 구현 기준 |
| --- | --- |
| 광고 채널 상태 | 매물별 당근·네이버·직방 등 채널, 등록 상태, 마지막 확인일, 메모 |
| 광고 현황 목록 | 게시 중·수정 필요·종료 대상 필터 |
| 상태 경고 | 계약 완료/보류 매물인데 게시 중인 광고를 상단 경고 |
| 문구 템플릿 | 원룸·투룸·쓰리룸 등 템플릿과 강조 포인트 선택 |
| 문구 생성 | 최신 매물 조건으로 제목·본문 생성, 복사 버튼 제공 |
| 저장 원칙 | 문구 생성만으로 매물 DB는 수정하지 않음 |

### 완료 기준

- “계약 완료인데 게시 중인 광고”를 한 목록에서 찾을 수 있다.
- 템플릿과 강조 포인트를 바꿔 광고 문구를 생성·복사할 수 있다.
- 공실이 아닌 매물에 새 광고 문구 생성을 시도하면 상태 확인 안내가 나온다.

### 단계 8 — 통합 테스트와 사용성 보완 P2

### 목적

기능별 성공이 아니라, 실제 하루 업무를 처음부터 끝까지 처리할 수 있는지 검증한다.

### 핵심 테스트 흐름

| 흐름 | 시작 | 끝 | 확인할 점 |
| --- | --- | --- | --- |
| 신규 매물 | 건물 검색 | 매물 등록 후 광고 문구 복사 | 중복 방지·가격·상태·표시 정보 |
| 기존 매물 변동 | 호실 검색 | 가격·입주일·상태 수정 | 기존 상담·계약·광고 연결 유지 |
| 신규 문의 | 상담 등록 | 매물 제안·다음 연락일 설정 | 대시보드 후속 업무 반영 |
| 계약 | 상담/매물에서 계약 등록 | 입금 확인·계약 완료·광고 종료 확인 | 상태 자동 변경 오작동 없음 |
| 업무 시작 | 대시보드 열기 | 지연·오늘 업무 완료 | 완료 기록과 원본 상태 분리 |
| 권한 | admin/staff/멤버 없음 로그인 | 허용된 화면만 확인 | 메뉴·서버·데이터 모두 같은 기준 |

### 사용성 점검 질문

- 새 매물을 등록할 때 현재 Streamlit보다 입력이 더 많거나 느리지 않은가?
- 매물 목록의 열만 보고 전화할 매물을 고를 수 있는가?
- 오늘 해야 할 일을 종이나 기억에 의존하지 않고 찾을 수 있는가?
- 상태 변경 후 “무엇을 다음에 해야 하는지”가 보이는가?
- 잘못 누른 삭제·상태 변경을 막는 안내가 충분한가?

### 완료 기준

- 실제 사무실 업무와 비슷한 가공 시나리오를 admin과 staff 계정으로 각각 통과한다.
- P0/P1 오류는 수정하거나 명확한 제한으로 문서화한다.
- 수정 요청은 “업무상 반드시 필요한가” 기준으로 P0/P1/P3로 다시 분류한다.

### 단계 9 — Production 보안 전환과 신규 운영 시작 P2

### 목적

기능이 검증된 뒤 Production 환경을 안전하게 열고, 웹서비스에서 새 매물을 처음부터 등록해 운영을 시작한다.

### 사전 조건

- P0/P1 기능과 통합 테스트가 통과했다.
- `supabase_security_transition_plan.md`의 완료 기준을 충족할 준비가 되었다.
- Clerk Production, Supabase Production, Vercel Production 환경이 Dev와 분리되어 있다.
- 운영 관리자와 staff 계정이 확정되어 있다.

### 실행 항목

| 순서 | 작업 | 결과 |
| --- | --- | --- |
| 1 | Production 프로젝트와 환경 변수 준비 | Dev와 분리된 운영 환경 |
| 2 | Clerk–Supabase Native Integration 연결 | 운영 로그인 인증 문맥 확인 |
| 3 | Production DB migration 적용 | 운영용 스키마 생성 |
| 4 | RLS·Storage 정책 적용 및 교차 조직 테스트 | 다른 조직 접근 차단 확인 |
| 5 | 운영 조직·admin·staff 멤버 등록 | 실제 권한 구조 준비 |
| 6 | 운영 시작 기준과 첫 등록 절차 확인 | 실제 매물을 새로 등록할 준비 완료 |
| 7 | 기존 SQLite 원본 백업·보관 | 과거 운영 기록을 보존 |
| 8 | 제한 운영 | 새로 등록한 실제 매물로 핵심 업무와 오류 확인 |
| 9 | 기본 업무 도구 전환 | 웹서비스를 주 사용 도구로 전환 |

### 기존 SQLite 데이터 처리 원칙

기존 SQLite 데이터는 Supabase로 이관하지 않는다. 웹서비스는 운영 시작일부터 건물·호실·매물·상담·계약을 새로 등록한다.

| 항목 | 기준 |
| --- | --- |
| 기존 SQLite | 과거 기록 확인용으로 읽기 전용 백업 보관 |
| 웹서비스 시작 | 실제 업무에 필요한 매물을 우선순위에 따라 새로 등록 |
| 진행 중인 업무 | 필요한 경우 웹서비스에 새 상담·계약 기록으로 직접 등록 |
| 데이터 비교 | 이관 건수 비교는 하지 않음. 웹서비스에 새로 입력한 정보의 정확성만 확인 |
| Python | 데이터 이관 목적으로 사용하지 않음 |

### 완료 기준

- Production RLS를 끈 상태로 실제 데이터를 운영하지 않는다.
- admin·staff·비활성 사용자·다른 조직의 접근 테스트가 모두 통과한다.
- 운영 시작에 필요한 실제 매물·상담·계약을 웹서비스에 새로 등록해 정상 처리할 수 있다.
- 기존 Streamlit SQLite 원본은 읽기 전용 백업으로 보존되어, 과거 기록이 필요할 때만 확인할 수 있다.

| AI 광고 문구 보조 | 현재 템플릿 문구만으로 부족한 변형 요구가 확인될 때 |
| Python 일괄 도구 | OCR·사진 보정처럼 웹 요청에 맞지 않는 작업 발생 시 |

## 4. 작업 관리 방식

### 4.1 기능 단위 작업 카드 형식

각 구현 작업은 아래 형식으로 기록한다.

| 항목 | 작성 내용 |
| --- | --- |
| 작업명 | 예: `매물 목록 — 상태·입주 가능일 빠른 수정` |
| 목적 | 어떤 반복 업무를 줄이는지 |
| 입력 | 사용자가 넣는 값 |
| 처리 | 서버 검증·DB 변경·업무 규칙 |
| 출력 | 사용자가 보는 결과 |
| 완료 기준 | 직접 확인 가능한 조건 |
| 제외 범위 | 이번 작업에서 하지 않을 것 |
| 연결 문서 | 화면 ID, 데이터 테이블, 테스트 항목 |

### 4.2 변경 요청 판단 기준

| 질문 | 판단 |
| --- | --- |
| 매일 또는 매주 반복되는 업무인가? | 그렇다면 우선 검토 |
| 지금 기능이 없어서 업무가 멈추는가? | P0 또는 P1 가능 |
| 현재 수동 작업이 1~2번으로 끝나는가? | 기능 추가보다 보류 |
| 자동화가 잘못될 경우 매물·계약 상태를 틀리게 만들 수 있는가? | 자동 실행하지 않고 확인 단계 유지 |
| 기존 화면에서 더 적은 클릭으로 해결되는가? | 현재 방식 유지 또는 화면만 개선 |

### 4.3 완료의 정의

기능은 코드가 작성됐다고 완료가 아니다. 아래를 모두 만족해야 완료다.

- [ ] 화면 명세의 목적과 행동이 구현됐다.
- [ ] 정상 입력과 잘못된 입력을 모두 확인했다.
- [ ] admin/staff 권한 기준을 확인했다.
- [ ] 목록·상세·대시보드처럼 영향받는 화면이 함께 갱신된다.
- [ ] 실제 업무 시나리오로 한 번 이상 사용해 봤다.
- [ ] 이번 범위에서 하지 않는 일은 문서나 작업 카드에 남겼다.

## 6. 구현 계획 완료 기준

- [ ] P0→P1→P2→P3 순서가 지켜진다.
- [ ] Streamlit은 웹서비스 전환이 검증될 때까지 기존 업무 도구로 유지된다.
- [ ] 매물 관리 P0를 먼저 실제 시나리오로 검증한다.
- [ ] 상담·계약·광고는 매물 데이터 구조 위에 순서대로 추가한다.

- [ ] 모든 단계에 사용자가 직접 확인할 수 있는 완료 기준이 있다.
- [ ] 후속 기능은 반복 업무와 운영 필요성이 확인된 뒤에만 추가한다.
