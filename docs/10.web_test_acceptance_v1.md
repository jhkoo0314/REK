# 부동산 매물관리 웹서비스 — 테스트·수용 기준서 v1.0

## 1. 문서 목적

이 문서는 부동산 매물관리 웹서비스가 실제 사무실 업무에 투입 가능한지 판단하기 위한 테스트 기준이다. 단순히 버튼이 눌리는지를 확인하는 데 그치지 않고, 매물·상담·계약·광고 업무가 연결된 상태에서 정확히 처리되는지를 확인한다.

### Dev 실행 기록 (2026-08-18)

| 항목 | 결과 | 비고 |
| --- | --- | --- |
| Clerk admin 로그인 | 통과 | 가공 조직 A admin 연결 |
| 조직 A 목록 조회 | 통과 | 현재 가공 매물 6개 확인 |
| 동일 호실 중복 차단 | 통과 | DB 제약과 등록 흐름에서 차단 확인 |
| 중복 호실 자체 팝업 | 재확인 대기 | 화면 하단 오류 안내는 확인됨 |
| 신규 등록 성공 흐름 | 재확인 대기 | 기존/신규 건물·호실 조합별 확인 필요 |
| TypeScript 전체 검사 | 보류 | Windows의 Next 모듈 인식 문제 |

### 수용 원칙

- P0(매물 관리) 오류가 남아 있으면 운영 시작하지 않는다.
- 다른 조직 데이터가 보이거나 수정되는 보안 문제는 즉시 운영 중단 수준으로 본다.
- 테스트는 Dev/Preview에서 가공 데이터로 수행하고, 실제 고객·계약·출입 정보는 Production 보안 전환 전까지 사용하지 않는다.
- 웹서비스는 기존 SQLite 데이터를 이관하지 않는다. Production 운영 시작 시 필요한 매물·상담·계약을 새로 등록하는 흐름을 테스트한다.

## 2. 테스트 환경과 역할

### 2.1 환경별 테스트 범위

| 환경 | 사용 데이터 | RLS 상태 | 테스트 목적 |
| --- | --- | --- | --- |
| Local | 가공 테스트 데이터 | 개발 중 비활성화 가능 | 개발 중 빠른 기능 확인 |
| Preview | 가공 테스트 데이터 | 개발 단계 기준, 운영 전에는 활성화 검증 | PC·모바일 업무 흐름과 UI 검토 |
| Production 후보 | 제한된 가공 검증 데이터 | 활성화 필수 | Clerk·RLS·환경 변수·조직 분리 최종 확인 |
| Production 운영 시작 | 새로 등록한 실제 업무 데이터 | 활성화 필수 | 최소 기능 정상 동작 확인 |

### 2.2 테스트 계정

| 계정 | 조직 | 역할/상태 | 사용 목적 |
| --- | --- | --- | --- |
| `admin-A` | 조직 A | admin / active | 사용자 관리와 전체 업무 테스트 |
| `staff-A` | 조직 A | staff / active | 일반 업무 CRUD 테스트 |
| `inactive-A` | 조직 A | staff / inactive | 비활성 사용자 접근 차단 테스트 |
| `staff-B` | 조직 B | staff / active | 조직 A 데이터 교차 접근 차단 테스트 |
| `no-member` | 없음 | 로그인만 가능 | 멤버십 없는 사용자 차단 테스트 |

모든 이름·연락처·주소·금액·사진은 가공값으로 준비한다.

### 2.3 기본 테스트 데이터

| 데이터 | 최소 준비량 | 포함해야 할 상태 |
| --- | --- | --- |
| 건물 | 3개 이상 | 같은 이름과 비슷한 주소를 포함해 검색 혼동 확인 |
| 호실 | 건물별 3개 이상 | 현재 매물 있음/없음 혼합 |
| 매물 | 15개 이상 | 공실, 입주 가능 예정, 협의 중, 계약 진행, 계약 완료, 보류 |
| 상담 | 5건 이상 | 다음 연락일이 오늘/과거/미지정, 종료 상태 포함 |
| 계약 | 3건 이상 | 계약 진행, 완료, 취소 및 입금 미확인 포함 |
| 광고 현황 | 6건 이상 | 게시 중, 수정 필요, 종료 포함 |
| 조직 B 데이터 | 매물 3개 이상 | 조직 A 사용자가 보지 못해야 함 |

## 3. 테스트 수행 방식

### 3.1 결과 기록 형식

각 테스트는 다음 항목으로 기록한다.

| 항목 | 기록 내용 |
| --- | --- |
| 테스트 ID | 예: `L-03` |
| 실행 환경 | Local / Preview / Production 후보 |
| 실행 계정 | `admin-A`, `staff-A` 등 |
| 결과 | 통과 / 실패 / 보류 |
| 실제 결과 | 기대 결과와 다른 내용 |
| 증빙 | 필요 시 화면 캡처 또는 오류 기록 |
| 조치 | 수정할 작업 또는 보류 사유 |
| 재테스트 | 수정 후 통과 여부 |

### 3.2 오류 등급

| 등급 | 의미 | 운영 시작 기준 |
| --- | --- | --- |
| Blocker | 로그인 불가, 다른 조직 데이터 노출/수정, 데이터 유실, 배포 불가 | 0건 필수 |
| Critical | 매물 등록·검색·수정·계약의 핵심 업무 불가 또는 잘못 저장 | 0건 필수 |
| Major | 우회는 가능하지만 일상 업무가 크게 불편하거나 잘못 판단할 위험 | 원칙적으로 0건. 예외 시 명확한 수동 절차 필요 |
| Minor | 문구·정렬·간격 등 사용성 저하 | 운영 후 개선 가능 |

### 3.3 수용 판정 방식

| 판정 | 조건 |
| --- | --- |
| 승인 | Blocker/Critical 0건, Major가 없거나 명확히 합의된 보완 계획 존재, 핵심 시나리오 전부 통과 |
| 조건부 승인 | 실무를 멈추지 않는 Minor만 남아 있고, 운영 시작 후 수정 항목이 기록됨 |
| 보류 | 보안·권한 문제, 데이터 오류, P0 핵심 흐름 실패, 해결되지 않은 Major 존재 |

### 초기 성능 체감 기준

정밀 부하 테스트보다 실제 사무실 사용에서 기다림이 업무를 방해하지 않는지를 우선 확인한다.

| 상황 | 수용 기준 |
| --- | --- |
| 매물 목록(가공 매물 300건 이하) | 일반 사무실 인터넷에서 로딩 상태가 보이고, 업무상 답답하지 않게 결과 확인 가능 |
| 검색·필터 | 입력 후 결과가 혼란 없이 갱신되고 이전 결과와 섞이지 않음 |
| 저장 | 저장 중임이 명확하고 성공/실패 결과를 확인 가능 |
| 대시보드 | 오늘 할 일과 현황을 한 번에 읽을 수 있음 |

속도가 불편하다고 느껴지면 먼저 불필요한 열·쿼리·재렌더링을 줄이고, 인프라를 추가하기 전에 원인을 확인한다.

## 14. 운영 시작 수용 체크리스트

### P0 기능

- [ ] 매물 등록·검색·필터·상세·수정 테스트가 모두 통과했다.
- [ ] 일반 가격·상태·입주 가능일 수정이 새 매물을 만들지 않는다.
- [ ] 중복 현재 매물 등록을 막거나 명확히 경고한다.
- [ ] 대시보드의 오늘·지연 업무가 정확히 표시된다.

### P1 연결 기능

- [ ] 상담의 다음 연락일과 매물 연결이 정상 동작한다.
- [ ] 계약의 일정·입금·완료/취소 처리가 정상 동작한다.
- [ ] 계약 완료 시 광고 종료 확인을 놓치지 않는다.
- [ ] 광고 상태와 문구 생성이 매물 데이터를 임의 변경하지 않는다.

### 보안·운영

- [ ] RLS가 활성화된 환경에서 S-01~S-12를 모두 통과했다.
- [ ] Blocker와 Critical 오류가 0건이다.
- [ ] 실제 데이터는 웹서비스에서 새로 등록하는 방식이 확인됐다.
- [ ] 기존 SQLite 원본은 과거 기록 확인용으로 보관한다.
- [ ] Production 환경 변수와 실제 운영 계정이 Dev와 분리되어 있다.
- [ ] 운영 중 오류를 확인할 로그와 배포 되돌리기 기준이 있다.
