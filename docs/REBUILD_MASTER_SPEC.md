# 웹 재빌드 기준서

> 기준일: 2026-08-25
>
> 상태: 코드 재빌드 시작 전
>
> 이 문서는 현재 `C:\realestate-main`의 Streamlit 업무 시스템을 웹으로 다시 구현하기 위한 단일 기준이다.

## 1. 목표와 판단 기준

이 프로젝트는 고객 공개용 매물 사이트가 아니다. 초대된 사무실 직원이 **상담을 시작으로 매물 제안과 계약까지** 안전하게 처리하는 내부 업무 웹서비스다. 매물은 상담 중 제시할 상품 재고이며, 상담 관리는 대표 업무 화면이다.

기능·입력 항목·업무 순서는 Streamlit의 `README.md`, `AGENT.md`, 데이터 정의서와 업무 흐름서를 기준으로 한다. 구현 기술만 Next.js, Clerk, Supabase로 바꾼다.

업무 화면의 우선순위는 상담 흐름, 계약 연결, 오늘의 후속 행동, 매물 재고 관리, 건물·호실 관리 순서다. 다만 개발 시에는 상담이 연결할 최소 건물·호실·매물 기반을 먼저 안전하게 준비한다. 모든 단계에서 데이터 손실·잘못된 상태 변경 방지와 민감 정보 보호를 우선한다.

### 2-1. 화면 컨셉 고정

- 서비스 전체는 **목록 중심 부동산 업무 CRM**으로 만든다. 통계 카드·차트가 많은 대시보드를 기본 첫 화면으로 만들지 않는다.
- 로그인 후 기본 화면은 상담 목록(`/consultations`)이다. 리드, 상담 단계, 다음 연락, 이력, 연결 매물과 계약 결과를 관리한다.
- 오늘 예정 업무(`/dashboard`)는 오늘·지연된 상담 후속 연락, 방문·계약 일정, 매물 확인만 짧게 모아 원래 기록으로 연결한다.
- 매물 목록(`/listings`)은 상담에 제시할 재고를 검색·비교·수정하는 표 중심 화면이다.
- 건물·호실(`/buildings`)은 건물 → 호실 → 현재/과거 매물을 따라가는 별도 탐색기다.
- 계약(`/contracts`)은 실제 계약 매물과 출처 상담을 구분해 연결하고 단계 이력을 남기는 화면이다.
- 자세한 화면 역할과 정보 보호 기준은 `7.web_screen_spec_wireframe_v1.md`를 따른다.

## 3. 반드시 지킬 업무 규칙

- 모든 업무 데이터는 `건물 → 호실 → 매물` 관계를 따른다.
- 가격·관리비·상태·입주 가능일 같은 일반 변경은 같은 현재 매물을 수정한다. 새 매물은 자동으로 만들지 않는다.
- 매물 수정은 연결된 상담·계약·이력을 삭제하거나 새로 만들지 않는다.
- 계약의 실제 계약 매물과 출처 상담의 최초 문의 매물은 달라도 된다.
- 계약 진행·완료·해지·만료는 계약관리에서만 처리한다. 계약 상태 또는 단계 이력을 저장할 때 영향과 결과를 확인한 뒤 연결 매물 상태를 정해진 규칙으로 반영하고, 계약 완료 시 출처 상담을 종료하며 다음 연락을 해제한다.
- 광고 문구는 유형별 읽기 전용 기본 양식에서 확인한 값만 넣어 만든다. 선택·복사만으로 다른 상태를 바꾸지 않으며, 사무실 공용 템플릿 저장·관리 기능은 제공하지 않는다.
- 매물의 제한 연락처·출입 비밀번호·내부 메모는 매물 목록·오늘 예정 업무·광고 화면에 표시하지 않는다. 고객 연락처는 후속 연락을 위해 같은 조직 직원의 상담 기본 목록과 상세에서 표시한다.
- Excel·CSV 다운로드는 MVP에서 제공하지 않는다. 향후 자료 반출이 필요하면 기본 다운로드 금지, admin 승인, 허용 항목, 민감정보 제외와 기록 방식을 별도 승인한다.
- 금액은 만원 단위 정수, 업무 날짜는 시간 없는 날짜로 저장한다.

### 3-2. 최신 Streamlit 기준 대조 후 확정 사항 (2026-08-31)

- 계약 정보와 상태 전환은 현재 웹 기준을 유지한다. 즉, 계약 진행·완료·해지·만료는 계약관리에서만 확정하며, 출처 상담 종료도 현재 웹의 `계약 완료` 규칙을 유지한다. Streamlit의 계약 진행·잔금 예정부터 상담을 종료하는 규칙은 적용하지 않는다.
- 매물 접수일은 별도 입력·DB 열을 만들지 않고 웹의 매물 생성 시각으로 표시한다.
- 매물 보유처는 Streamlit의 선택값 `크린주택관리`, `삼성주택관리`, `한빛주택관리`, `국제주택관리`, `개인매물`, `직접입력`을 웹 등록·수정·필터에 적용한다. 직접입력 값은 계속 허용한다. 빠른 수정에서는 보유처를 바꾸지 않는다.
- 빠른 수정의 관리 종료는 종료일과 `타 부동산 계약`·`기타` 사유, 사용자 확인을 받은 뒤 현재 재고에서만 제외한다. 계약 완료는 계약관리에서만 처리하며 관리 종료 사유로 선택하지 않는다.
- 계약 등록은 실제 계약 매물을 매물번호·건물명·주소·호수로 검색해 선택한다. 기본 검색은 현재 매물이며, 필요할 때 과거 매물 이력도 선택할 수 있다. 과거 이력에 계약 단계를 기록해도 해당 매물을 다시 현재 재고로 열지 않는다.
- 사진 유무와 재확인일은 웹 업무·DB에서 제거한다. 상태값은 공실·계약 진행·계약 완료·보류·종료를 유지한다.
- 상담은 Streamlit 기준의 상담일 후 24시간·72시간 집중 대응 표시를 추가한다. 계약 성사 안내·목록 제외는 위 웹 계약 완료 규칙으로 상담이 종료된 경우에만 적용한다.
- 광고 문구는 최신 Streamlit의 방 구조별 제목·본문 구성, 지역별 확인 문구, 입력 항목과 결과 수정·복사 흐름을 적용한다. 결과는 DB에 저장하지 않고, 연락처·비밀번호·내부 메모는 계속 차단한다.
- SQLite 자동 백업, OneDrive, Tailscale, Excel·CSV 내보내기와 기존 SQLite 데이터 이관은 웹 MVP에 추가하지 않는다.

## 3-1. 향후 매물 종류 확장 준비

P0의 실제 입력·화면·검증 대상은 원룸·투룸 중심으로 유지한다. 다만 DB 이름, 상태값, 공통 화면 구조는 아파트·오피스텔·상가·사무실까지 수용할 수 있게 만든다.

- 매물에는 `property_type`(원룸 / 투룸 / 아파트 / 오피스텔 / 상가 / 사무실) 구분값을 둔다.
- 원룸·투룸 같은 방 구조는 주거형 매물에만 쓰는 별도 값으로 두며, 상가·사무실에는 비워 둘 수 있다.
- 상태는 공실, 계약 진행, 계약 완료, 보류, 종료처럼 모든 매물 종류에 쓸 수 있는 공통 표현을 사용한다.
- 주소, 호실, 층, 면적, 가격, 관리비, 거래 방식, 입주 가능일은 공통 항목으로 유지한다.
- 아파트의 단지·동·공급면적, 상가의 권리금·부가세·용도 같은 전용 항목은 지금 추가하지 않는다. 실제 도입 전 별도 데이터 모델·화면·테스트 승인 뒤 migration으로 추가한다.
- 종류별 특수 항목을 이유로 일반 매물 테이블에 미리 많은 빈 열을 만들거나, 의미 없는 범용 메모 칸에 구조화된 정보를 넣지 않는다.

## 4. 데이터와 보안 기준

- 모든 업무 테이블은 `organization_id`를 포함한다. 브라우저에서 받은 조직 ID를 신뢰하지 않는다.
- 서버는 Clerk 로그인과 활성 멤버십을 확인한다. Production에서는 Supabase RLS도 함께 통과해야 한다.
- secret/service-role 키는 브라우저 또는 일반 CRUD에 사용하지 않는다.
- Local·Dev·Preview에는 가공 데이터만 사용한다.
- 기존 Streamlit SQLite 원본은 읽기 전용 보관 자료다. 자동 이관하지 않는다. 실제 이관은 별도의 범위·백업·검증·사용자 승인이 있어야만 검토한다.

## 5. 새 코드 구조

```text
app/                         라우트 조립과 서버 페이지
components/ui/               기본 UI
components/shared/           앱 셸·상태 배지·표 틀·민감정보 표시
features/listings/           매물·건물·호실 업무
features/consultations/      상담과 후속 이력
features/contracts/          계약과 단계 이력
features/tasks/              오늘 할 일
features/advertisements/     광고비·유형별 문구 템플릿
lib/                         Clerk·Supabase·권한·날짜·금액 공통 함수
supabase/migrations/         순서가 있는 DB 변경 파일
```

각 `app/**/page.tsx`는 화면 조립만 한다. 큰 카드·표·폼은 해당 `features` 폴더에 둔다. `docs/DESIGN_BUILD_PREP.md`와 `docs/FINAL_CRM_UI_CONCEPT.html`의 색상·글꼴·정보 위계·업무 흐름을 사용한다.

### 코드 분리 원칙

- 한 화면 파일에 화면·입력 검증·DB 저장·표·다이얼로그를 모두 작성하지 않는다.
- 화면 단위 기능은 `features/<기능>/` 아래에 두고, 화면 부품은 `components/`, 서버 처리와 조회는 `server/`, 입력 검증은 `schemas/`처럼 역할별로 나눈다.
- 둘 이상의 업무 화면에서 같은 역할을 하는 UI는 `components/shared/`에 한 번만 둔다.
- 기본 버튼·입력칸·다이얼로그 같은 작은 기반 부품은 `components/ui/`에 둔다.
- 공통 권한·날짜·금액·DB 연결은 `lib/`에 둔다.
- 파일 하나가 두 가지 이상의 큰 역할을 하거나 읽기 어려울 정도로 길어지면 분리한다. 반대로 재사용되지 않는 아주 작은 표시 요소까지 억지로 공통 파일로 만들지는 않는다.

## 6. DB 재시작 원칙

코드 재빌드와 Dev DB 초기화는 별도 작업이다.

1. 로그인·프로젝트 뼈대 뒤 전체 화면을 가공 목업 데이터로 먼저 완성하고 브라우저에서 검토한다. 이 단계는 DB를 읽거나 바꾸지 않는다.
2. 디자인 검토가 끝난 뒤 새 P0 데이터 모델과 migration 순서를 문서로 확정한다.
3. migration 파일을 작성한다. 이 단계에서는 Dev DB를 바꾸지 않는다.
4. 사용자가 명시적으로 승인한 경우에만 Dev DB를 초기화하고 새 migration을 적용한다.
5. 가공 조직·가공 계정·가공 매물 seed를 넣고 실제 데이터 흐름을 확인한다. Production DB·Clerk Production·기존 SQLite는 이 과정에서 절대 바꾸지 않는다.

기존 재빌드 전 migration과 seed는 삭제했다. 새 P0 데이터 모델 검토 뒤, 새 migration과 가공 seed를 처음부터 작성한다.

## 7. 완료 기준

- P0: 가공 계정으로 새/기존 건물·호실 매물 등록, 검색, 상세, 수정, 빠른 수정과 민감 정보 숨김을 확인한다.
- P1: 상담 후속 이력, 계약·출처 상담·일정, 오늘/지연 업무·완료 체크, 월별 광고비·유형별 문구 템플릿을 각각 가공 데이터로 확인한다.
- P2: admin/staff/inactive/다른 조직 계정, PC·모바일, 저장 오류·빈 화면·권한 없음, RLS와 Production 전환 조건을 확인한다.

모든 단계는 lint·typecheck·build·관련 테스트와 실제 브라우저 확인을 구분해 기록한다.
