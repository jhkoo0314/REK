# 매출 현황 화면 기준

> 기준일: 2026-09-01  
> 상태: 첫 버전 구현 완료, 실제 Dev 데이터 확인 대기  
> 대상 화면: 매출관리 아래 `매출 현황`  
> 전제: 현재 구현된 계약·중개수수료 정산·실제 수납·환불 데이터를 사용한다.

## 1. 목적

`매출 정산`은 계약별로 수수료를 입력하고 실제 수납·환불을 기록하는 화면이다. `매출 현황`은 이 기록을 모아 **누가, 어떤 매물에서, 어느 달에 얼마를 수납·환불했는지** 조회하는 화면이다.

광고비와 상담 유입경로 분석은 이미 광고관리에서 가능한 범위를 유지한다. 별도 데이터를 가져와 비교·해석하는 매출 분석은 향후 독립 기능으로 검토하며, 이 화면에는 섞지 않는다.

## 2. 화면 구성안

```text
매출관리
 ├─ 매출 정산      계약별 수수료·수납·환불 입력과 월별 목록
 └─ 매출 현황      입력된 기록을 담당자·매물 형태·월별로 조회
```

- `매출 정산`: 기존 `/revenue` 화면을 유지한다.
- `매출 현황`: `/revenue/status` 화면으로 추가했다.
- 상단 메뉴에서 `매출관리`를 열면 두 하위 메뉴를 선택할 수 있다.

## 3. 현재 데이터로 가능한 현황 조회

모든 금액은 중개수수료 정산에 입력한 **원 단위 실제 수납·환불**을 기준으로 계산한다. 약정 수수료는 예상·미수금 확인에만 사용하며, 월 매출로 바로 합산하지 않는다.

| 분석 | 표시 내용 | 기준 데이터 |
| --- | --- | --- |
| 담당자별 매출 | 담당자별 계약 건수, 실제 수납, 환불, 순매출, 계약 1건당 평균 매출 | 계약 담당자와 수납·환불 기록 |
| 월별 매출 추이 | 선택 기간의 월별 수납, 환불, 순매출, 미수금 | 실제 수납일·환불일 |
| 매물 형태별 매출 | 원룸·투룸·아파트·오피스텔·상가·사무실별 계약 건수와 순매출 | 매물의 종류와 수납·환불 기록 |
| 수수료 구성 | 임차인 수수료, 임대인 수수료, 약정 수수료 합계, 실제 수납, 미수금 | 계약별 정산 기록 |
| 계약 상태별 확인 | 진행·완료·해지·만료 계약의 수납·환불 현황 | 계약 상태와 수납·환불 기록 |

### 담당자별 매출의 의미

- admin은 사무실 전체를 보고 담당자별로 비교한다.
- staff는 다른 직원의 정보 없이 **본인 계약 건수·본인 배분 순매출·본인 평균 매출**만 본다.
- 담당자 매출은 실제 수납액에서 해당 계약에 저장된 담당자 비율로 계산된 금액을 합산한다.
- 환불은 환불일이 속한 달의 매출에서 차감한다.

## 4. 첫 화면에 표시할 항목

처음에는 그래프를 많이 넣지 않고, 판단에 필요한 숫자와 짧은 성과 요약을 중심으로 구성한다. 전체 표는 기본으로 펼치지 않는다.

### 4-1. 상단 요약

선택한 기간의 아래 다섯 가지를 카드로 표시한다.

1. 실제 수납액
2. 환불액
3. 순매출(실제 수납액 - 환불액)
4. 미수금(약정 수수료 - 누적 수납 + 누적 환불)
5. 계약 건수

staff 화면에서는 사무실 전체 금액 대신 본인 배분 순매출과 본인 계약 건수만 표시한다.

### 4-2. 전체 성과 요약

담당자·매물 형태·월별 결과는 상위 3개로 자르지 않고 기본 화면에서 모두 보여 준다. 각 행에는 이름, 계약 건수, 순매출만 간결하게 표시한다.

| 표 | admin 표시 열 | staff 표시 열 |
| --- | --- | --- |
| 담당자별 | 담당자, 계약 건수, 실제 수납, 환불, 담당자 순매출, 평균 매출 | 본인 요약만 표시 |
| 매물 형태별 | 매물 형태, 계약 건수, 실제 수납, 환불, 순매출 | 본인 계약 기준 동일 표시 |
| 월별 | 월, 실제 수납, 환불, 순매출, 계약 건수 | 본인 배분 기준 동일 표시 |

### 4-3. 미수금 확인 목록

약정 수수료가 있으나 실제 수납·환불을 반영한 뒤 아직 남은 금액이 있는 계약만 보여 준다.

| 표시 항목 | 용도 |
| --- | --- |
| 계약 번호·매물 정보 | 어느 계약인지 확인 |
| 담당자 | admin의 후속 확인 대상 판단 |
| 약정 수수료 | 원래 받기로 한 금액 확인 |
| 누적 수납·환불 | 지금까지 실제 기록 확인 |
| 남은 미수금 | 다음 수납 입력이 필요한 금액 확인 |

## 5. 필터 기준

아래 필터를 구현했다. 복잡한 조합 필터는 실제 사용 필요가 확인된 뒤 추가한다.

| 필터 | 기본값 | 설명 |
| --- | --- | --- |
| 기간 | 이번 달 | 실제 수납일·환불일 기준으로 월 또는 시작일~종료일 선택 |
| 담당자 | 전체(admin만) | 특정 담당자만 보고 싶을 때 사용. staff에게는 노출하지 않음 |
| 매물 형태 | 전체 | 원룸, 투룸 등 매물 종류 비교 |
| 계약 상태 | 전체 | 진행·완료·해지·만료를 구분해 확인 |

기간에는 두 가지 기준이 섞이지 않게 한다.

- 매출 표·월별 추이는 실제 수납일 또는 환불일 기준이다.
- 미수금 목록은 선택 기간과 무관하게, 현재도 수납이 남은 계약을 별도 확인하는 방식이 적절하다.

## 6. 현재 데이터만으로는 하지 않는 분석

아래는 데이터가 없거나 이번 업무 목적을 벗어나므로 첫 버전에 포함하지 않는다.

| 제외 항목 | 이유 |
| --- | --- |
| 사무실 전체 손익 | 임대료·인건비·기타 경비 자료가 없음 |
| 급여·인센티브 자동 계산 | 담당자 매출과 급여 규칙은 별도 업무 기준이 필요함 |
| 광고 매체별 계약 매출 기여 | 상담 유입경로와 최종 계약의 연결이 모든 계약에 보장되지 않음 |
| 계약 전환율 | 전체 상담·제안·계약의 연결 기준을 별도로 확정해야 정확함 |
| 세금·부가세·회계 장부 | 세무·회계 처리 범위를 벗어남 |

광고비와 상담 유입경로는 현재 광고관리의 월별 광고비·상담관리의 유입경로로 확인하는 수준을 유지한다. 이를 매출 분석에 억지로 합산하지 않는다.

## 7. 권한과 안전 기준

- 모든 분석은 로그인 사용자의 조직 데이터만 조회한다.
- admin은 사무실 전체와 담당자별 결과를 본다.
- staff는 서버 조회 단계부터 본인 담당 계약의 본인 배분 금액만 받는다. 다른 직원 이름·금액·사무실 전체 합계는 화면에 보내지 않는다.
- 담당자가 없는 과거 계약은 admin에게만 `담당자 미지정`으로 보이며, staff 매출에는 포함하지 않는다.
- 해지·만료 계약의 과거 수납과 환불은 삭제하지 않고 분석에 남긴다.

## 8. 구현 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 분석용 서버 집계 작성 | 완료. 기간·권한 조건에 따라 담당자·매물 형태·월별 숫자를 집계 |
| 2 | 매출관리 하위 메뉴 추가 | 완료. `매출 정산`, `매출 분석` 이동 가능 |
| 3 | 분석 화면과 필터 구현 | 완료. 상단 요약, 분석 표, 미수금 목록 표시 |
| 4 | 권한 확인 | 코드 구현 완료. 실제 Dev 데이터로 admin/staff 확인 대기 |
| 5 | 수납·환불 검증 | 실제 Dev 데이터 확인 대기 |
| 6 | 문서·검사 갱신 | 완료. 코드 검사와 DB 변경 없음 상태 기록 |

이 기능은 현재 저장 구조만 사용하므로, 첫 버전에 새 DB 항목은 추가하지 않았다. 기존 기록으로 계산할 수 없는 항목이 확인될 때만 별도 migration 계획을 먼저 작성한다.

## 9. 이번 초안의 확정 제안

첫 버전은 아래 다섯 가지를 구현한다.

1. 실제 수납·환불·순매출·계약 건수·평균 매출 핵심 수치
2. 담당자별 계약 건수·순매출·평균 매출
3. 매물 형태별 계약 건수·순매출
4. 월별 실제 수납·환불·순매출
5. 미수금 총액·건수와 계약 목록

이 범위는 현재 데이터만으로 숫자의 의미가 분명하고, 실제 수수료 입력 업무와 바로 연결된다. 광고 효과, 손익, 급여 계산은 별도 기준과 데이터가 준비된 뒤 검토한다.
