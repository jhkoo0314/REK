## 현재 상태

- Streamlit 시스템을 기준으로 웹을 처음부터 다시 구현하기로 결정했다.
- 기존 Next.js 코드·가공 화면·기존 기능 구현은 재사용하지 않는다.
- Clerk·Supabase의 원격 설정, 로컬 `.env.local`, `docs/Design_guide/`, 문서와 Git 이력은 보존한다.
- 기존 로컬 migration과 seed는 재빌드 기준으로 삭제했다. Dev DB의 초기화·새 migration 적용은 아직 승인되지 않았다.
- 기존 Streamlit SQLite 데이터는 읽기 전용으로 보관하며 자동 이관하지 않는다.
- 화면 컨셉을 목록 중심 부동산 업무 CRM으로 확정했다. 상담 관리를 대표 업무 화면과 로그인 후 시작 화면으로, 매물 관리를 상담에 제시할 재고 관리로 정했다.
- 오늘 예정 업무는 대시보드가 아니라 오늘·지연 업무를 원래 상담·계약·매물 기록으로 연결하는 작은 보조 화면으로 정했다.
- 루트 폴더에 Next.js 16·TypeScript·Tailwind 기반과 Clerk Development 로그인·보호된 업무 화면 그룹을 구현했다. Supabase DB는 변경하지 않았다.
- 가공 목업 데이터로 상담 중심 CRM의 주요 화면과 상담 → 매물 검색 → 제안 → 계약 연결 흐름을 구현했다. 실제 저장 기능은 없다.

- `DEV_DB_APPLY_PRECHECK.md`에 가공 seed와 초기화 영향 범위를 기록했다. seed 입력·제약 검증은 아직 하지 않았다.
- 새 출발 기준의 Dev 초기화·migration 수동 적용 절차는 `DEV_DB_RESET_AND_APPLY.md`에 기록했고, 사용자가 Dev에 적용을 완료했다. Production에는 적용하지 않는다.

- 4-2 계약 화면과 상태 변경 확인을 완료했다. 실제 계약 목록의 검색·상태·일정 필터, 상담 출처 자동 선택 새 계약 등록, 계약 상세·수정·삭제, 단계 이력 저장을 구현했다. 계약 진행·잔금 완료 계약을 삭제하면 현재 매물은 공실로 되돌리고, 계약 완료 과거 이력은 다시 열지 않는다. 사용자가 브라우저에서 삭제·공실 복귀 흐름을 정상 확인했다.
- 계약 데이터의 거래 방식과 계약 구분을 분리했다. 계약의 거래 방식은 매물과 동일하게 월세·전세·매매·확인 필요를 쓰고, 계약 구분은 신규 계약·재계약으로 별도 저장한다. 새 계약에서 매물을 고르면 거래 방식이 자동으로 채워지며 필요하면 변경할 수 있다. 기존 Dev DB에는 `20260826001700_split_contract_transaction_and_kind.sql` 수동 적용이 필요하다.
- 5-1 구현 전 Streamlit 오늘 할 일 화면을 비교했다. 웹에는 기준일 변경, 퇴실 D-7~당일, 계약 4종 일정과 잔금 D-1 알림을 반영한다. 사용자 결정에 따라 상시 확인 필요·다음 재확인일은 웹에서 제외하고, 상담 연락처 표시와 상담·계약 상태 변경은 웹에도 구현한다. `next_check_date`는 추가하지 않는다.
- 5-1 업무 계산을 완료했다. 중요 업무 알림은 기준일 변경, 지연·오늘 구분, 진행 중 상담의 다음 연락일과 고객 연락처, 퇴실 D-7~당일, 계약의 정식 계약·추가 수령·잔금·만료 일정을 계산한다. 사진·현장 상태·매물 재확인·광고 업무는 제외한다. 상태·다음 연락일을 화면에서 바로 변경하는 기능은 화면 상호작용인 5-2로 이어서 구현한다.
