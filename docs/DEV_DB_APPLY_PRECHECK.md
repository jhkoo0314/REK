# Dev DB 적용 전 확인서

> 상태: 1-3 사전 확인 및 사용자의 Dev DB 수동 적용 완료 / `REK_test` 조직·현재 admin 멤버 연결 완료 / 가공 건물·호실·매물 seed 미입력
>
> 적용 대상: Supabase **Dev** 프로젝트만. Production, Clerk Production, 기존 Streamlit SQLite는 적용 대상이 아니다.

## 1. 적용할 파일과 순서

1. `DEV_DB_RESET_AND_APPLY.md`에 따라 Supabase Dev의 `public` 스키마만 초기화한다.
2. `supabase/migrations/20260826000100_create_p0_core_schema.sql`을 한 번 적용한다.
3. 가공 seed를 넣는다.
4. 테이블·중복 방지·조직 연결·Dev RLS 비활성화 상태를 확인한다.

초기 P0 migration(`20260826000100`)과 매물 목록용 표시번호 migration(`20260826000200_add_listing_reference_number.sql`)은 사용자가 Dev에 적용했다. 신규 매물 저장 함수(`20260826000300`)와 Dev 테이블 접근 권한(`20260826000400`)을 포함한 등록 흐름은 브라우저에서 정상 동작을 확인했다. 새 방 구조 값(`20260826000500`), 세대 비밀번호 등록 저장(`20260826000600`), 호실별 세입자 연락처(`20260826000700`), 입주 조건 구분(`20260826000800`), 기존 계약 완료 테스트 매물의 과거 이력 전환(`20260826000900`)은 별도 수동 적용 대상이다. 관리 종료 사유 저장(`20260826001000`)은 사용자가 Dev에 적용하고 브라우저에서 정상 확인했다. P1 상담·후속 이력(`20260826001100_create_p1_consultations.sql`)은 파일 작성만 완료했으며, 다음 Dev 수동 적용 대상이다. `20260826001100`을 적용한 뒤에는 고객 이름 선택 입력을 허용하는 `20260826001200_allow_consultation_customer_name_blank.sql`을 이어서 적용한다. Production DB에는 어떤 명령도 실행하지 않는다.

## 2. 가공 seed 계획

| 구분 | 가공 데이터 | 목적 |
| --- | --- | --- |
| 조직 | Clerk Development의 `REK_test` 1개 | Dev DB `organizations` 연결 완료 |
| 사용자 | 현재 Clerk Development 사용자 1명, admin | Dev DB `organization_members` active admin 연결 완료 |
| 건물 | 2개 | 건물 중복 확인 |
| 호실 | 건물당 2~3개 | `302`와 `302호` 중복 방지 확인 |
| 매물 | 원룸·투룸의 현재 매물과 종료 매물 | 현재 매물 한 건·목록·수정 확인 |
| 연락처 | `010-0000-0001` 같은 명백한 가공 번호 1건 | 건물 상세 저장·재조회 확인 |
| 출입 정보 | `TEST-0000` 같은 명백한 가공 비밀번호 1건 | 호실 상세 저장·재조회 확인 |

- 실제 사람 이름, 실제 전화번호, 실제 주소, 실제 출입 비밀번호, 실제 계약 정보는 넣지 않는다.
- 가공 연락처·출입 정보도 기본 목록·검색·오늘 예정 업무·광고 문구·내보내기에는 포함하지 않는다.
- `REK_test` 조직 생성은 확인했다. seed 실행 직전 현재 로그인한 사용자 ID만 추가로 확인한다. ID 값은 문서·로그에 기록하지 않는다.
- 다른 조직·staff·inactive 접근 차단 검증은 여러 개발용 계정이 필요해지는 P2 통합 검증 단계까지 보류한다.

## 3. Dev DB 초기화 영향

초기화는 **지정한 Supabase Dev 프로젝트의 `public` 데이터와 스키마만** 비우거나 다시 만드는 작업이다. 현재 Dev DB의 가공 테스트 데이터는 사라질 수 있다.

| 대상 | 영향 | 처리 |
| --- | --- | --- |
| Supabase Dev DB | migration 적용 및 가공 seed 입력 | 사용자 승인 후에만 실행 |
| Supabase Production DB | 영향 없음 | 명령 대상에서 제외 |
| Clerk Development | 가공 조직·계정 확인만 필요할 수 있음 | 사용자 승인 전에는 변경하지 않음 |
| Clerk Production | 영향 없음 | 대상에서 제외 |
| Streamlit SQLite | 영향 없음 | 읽기 전용 보관, 대상에서 제외 |
| 로컬 웹 코드·문서 | 영향 없음 | 이번 DB 적용 작업에서 삭제·수정하지 않음 |

## 4. 적용 뒤 확인할 항목

- 조직 → 건물 → 호실 → 매물 연결이 같은 조직 안에서만 되는지 확인한다.
- 같은 건물의 `302`와 `302호` 중복이 막히는지 확인한다.
- 같은 호실에 현재 매물 두 건이 생기지 않는지 확인한다.
- 음수 금액과 거래 방식에 맞지 않는 금액이 막히는지 확인한다.
- `building_contacts`, `unit_access_details`에 가공 값을 저장하고 상세에서 다시 읽을 수 있는지 확인한다.
- Dev의 P0 테이블에서 RLS가 비활성화 상태인지 확인한다.
- Production DB에 실행 기록이나 변경이 전혀 없는지 확인한다.

## 5. 승인 필요 항목

아래 작업은 사용자가 직접 실행했다.

- Supabase Dev `public` 스키마 초기화
- P0 migration 적용

조직·admin 연결 seed는 입력을 완료했다. 가공 건물·호실·매물 seed를 넣고 제약을 검증하는 작업은 다음 단계에서 진행한다.
